Plan 9's native syscall ABI, and running -H2 binaries under emulation
========================================================================

Scope: this file is about Plan 9's own syscall interface -- the
convention a -H2 (native, headerless) binary uses to ask the kernel
(or an emulator standing in for one) to do something -- as opposed to
docs/claude_notes/notes_exec_elf.txt/notes_exec_macho.txt/
notes_exec_pe.txt, which are about the *executable-file* formats used
for non-Plan-9 targets. Plan 9 has no separate "exec format" note of
its own (see docs/claude_notes/notes_os_plan9.txt) because -H2 has
stayed simple enough not to need one; what actually turned out to have
real, non-obvious content was the syscall convention itself, and the
machines/5i and machines/vi emulators' own bugs in interpreting it.
See lib_core/libc/9syscall/sys.h, machines/5i/, machines/vi/, and
tests/s/mini/hello_plan9_{arm,mips}.s.

The syscall numbering table, and its coupling to principia
------------------------------------------------------------------

lib_core/libc/9syscall/sys.h assigns one number per syscall (NOP=0,
RFORK=1, EXEC=2, ..., up through ERRSTR=39), grouped by comment into
process/memory/file/directory/namespace/time/ipc/concurrency/security
syscalls. The file's own first line is a "coupling: principia, must be
kept in sync" comment -- this numbering is not this project's own
invention to change freely, it has to match principia-softwarica's
copy exactly, because a -H2 binary built by this toolchain and a -H2
binary built by principia's own tools both need to mean the same thing
by "syscall number 11". A machine-readable copy of this table (or its
name-to-number mapping, sysctab[]) is duplicated into every consumer
that needs to decode or print syscalls -- machines/5i/syscall.c and
machines/vi's own equivalent both `#include` this same header rather
than each maintaining their own numbering.

Calling convention: number in a register, arguments on the stack, trap
------------------------------------------------------------------------------

Unlike Linux's per-arch conventions (register-passed arguments, see
docs/claude_notes/notes_exec_elf.txt), every Plan 9 syscall stub in
this toolchain follows the same shape regardless of argument count:
the syscall number goes in a fixed register, the arguments are written
to the stack starting 4 bytes past the frame pointer (leaving the
first word for what the trap handler needs), and a trap instruction
hands control to the kernel/emulator. Concretely, from
tests/s/mini/hello_plan9_{arm,mips}.s:

  - arm: syscall number in R0, arguments stored at 4(R13), 8(R13), ...
    (R13 is SP), trap via `SWI $0`.
  - mips: syscall number in R1, arguments stored at 4(R29), 8(R29), ...
    (R29 is SP), trap via `SYSCALL`.

No x86 Plan 9 emulator exists in this repo, so hello_plan9_386.exe
stays build-only -- there's no way to verify what convention it would
need at runtime here, only that 8l can produce the -H2 bytes.

Four bugs found bringing hello_plan9_{arm,mips}.exe up under 5i/vi
------------------------------------------------------------------------

Building these -H2 binaries had worked for a while; actually *running*
them under the 5i (arm) and vi (mips) emulators had not been exercised
end to end until it was, which immediately surfaced four independent
bugs (one commit, 80f819d11, fixed all four together):

1. **A `bool` truncation corrupted the ARM instruction decoder itself,
   not just syscall handling.** 5i's `bool` is `uint8` (see u.h), and
   expressions like `x & (1<<N)` for N>=8 have no bits at all in the
   low byte -- narrowing the result into a `bool` local silently
   zeroed it every time. This zeroed `prebit`/`ubit`/`bbit`/`wbit`/
   `lbit` in Iswap()/Imem1()/Imem2(), which turned a PC-relative
   literal load (`LDR $hello(SB), R1`, exactly what the hello test
   uses to find its own string constant) into a *store* instead --
   silently overwriting the very code that follows it in memory.
   Fixed by retyping those locals to plain `int`. Not a syscall bug at
   all, but found in the same bring-up pass and worth knowing about if
   you're debugging 5i and a `bool` local is involved in bit
   manipulation.

2. **ulong sign-extension corrupted vi's instruction dispatch.**
   ifetch()/getmem_w()/getmem_4() composed a 32-bit instruction or
   memory word the obvious way (`va[0]<<24 | va[1]<<16 | ...`), computed
   as a 32-bit `int`, then returned it through `ulong` -- 64 bits on
   these hosts, unlike the 32-bit hosts this code was written for. A
   result with the high bit set reads as negative as an `int`, and
   sign-extends when widened to a 64-bit `ulong`, corrupting the top 32
   bits of what's supposed to be a plain 32-bit word. Harmless in 5i
   (every consumer there re-masks with an explicit 32-bit constant
   before use) but fatal in vi's own unmasked `itab[(ir)>>26]` opcode
   dispatch -- an arbitrary 64-bit index into a small table, segfaulting
   on a wild access. Fixed by retyping the instruction/`reg.ir` fields
   and these three functions to `u32int`, matching the int32 migration
   already underway elsewhere in this codebase (see
   docs/claude_notes/notes_arch_amd64.txt's long-vs-int32 story for the
   same underlying "code assumed a 32-bit host" theme, in a completely
   different part of the tree).

3. **syswrite() forwarded the emulated PWRITE offset into the real
   host pwrite(2) on stdout/stderr, which don't support seeking.** The
   emulated program's Plan 9 PWRITE offset argument was passed straight
   through to the host's own `pwrite(2)` on fd 1 -- fine when fd 1 is a
   real seekable file, but `ESPIPE` (and a silently dropped write, since
   the return value wasn't checked) when it's a pipe, which is exactly
   what test harnesses and CI redirect stdout to. Also corrupts
   ordering against bout/bioout's own sequential writes on a regular
   file. Fixed by routing fd 0/1/2 through plain `write()` instead,
   which ignores the offset the way a terminal or pipe expects.

4. **The test source files themselves had a stale, wrong syscall
   number in a comment -- and it was actually used.**
   tests/s/mini/hello_plan9_{arm,mips}.s hardcoded `MOVW $9 /*PWRITE*/`
   -- but 9 is FD2PATH in the current sys.h numbering (see the table
   above); PWRITE is 11. This isn't a bug in sys.h or in either
   emulator, it's a bug in the hand-written test assembly itself,
   presumably stale from an earlier numbering. Both hello files were
   fixed to use the real PWRITE (11).

Verifying these actually worked meant running the emulators against
the real binaries and checking output, not just checking that they
built -- see docs/claude_notes/notes_libmach.txt's own "verify with
real binaries" lesson, which this bring-up reinforces from the
emulator-execution side rather than the object-file-decoding side.
tests/vi/smoke.sh previously pinned bug #2's wrong entry address as a
*documented limitation* (skipping the ':c' run-to-completion command
entirely) rather than as a known bug to fix -- worth remembering that
a test explicitly working around a known-wrong value is a signal that
whatever it's dodging is still there to fix, not that it's been
accepted as correct behavior.

What's not exercised at all
--------------------------------

Only PWRITE and EXITS have ever actually been exercised end to end
(that's all hello-world needs). Every other syscall in sys.h --
RFORK, EXEC, the whole namespace/mount family, NOTIFY/NOTED, the
segment family, RENDEZVOUS/SEMACQUIRE -- has a number and a name in
sysctab[] but no confirmed-working emulation path in 5i or vi. Treat
any of those the way a freshly-added Optab row on a real arch would be
treated before its first test (see docs/claude_notes/notes_wasm.txt's
own framing of this): plausible, not proven.

lib_core/libc gets real Plan9 file syscalls (open/close/pread/pwrite/
seek/exits), and a genuine 5i decoder bug found along the way
------------------------------------------------------------------------

Added July 2026, extending lib_core/libc's write/exit-only Linux+Darwin
support (docs/claude_notes/notes_libc_selfhost.txt) to a third GOOS,
for arm and mips. sys.h moved from machines/5i/sys.h to
lib_core/libc/syscall/os/plan9/sys.h (matching the syscall/os/$OS/
layout linux/darwin already use, not its own syncweb chunk name's
"9syscall/" path, which is left alone per this project's own "never
edit s:/e: markers" rule -- that mismatch is expected, not a bug);
machines/5i/syscall_posix.c and machines/vi/syscall.c's own #includes
were updated to the new path, both rebuilt+reverified via `mk
objtype=boot-gcc install`.

Structurally different from Linux/Darwin: Plan9's own syscall ABI
(number in a register, args already sitting on the stack exactly where
this compiler's own calling convention puts a function's own
parameters -- see syscall/os/plan9/svc_arm.s's header comment) needs no
shared _syscall6-style trampoline at all. open/close/pread/pwrite/exits
are hand-written one-per-syscall raw stubs directly under their real
public names (adapted from ~/principia-softwarica/lib_core/libc/
9syscall/mkfile's real, working per-syscall generator -- this project
is meant to interoperate with principia, not vanilla Plan9 4th edition,
per explicit user direction); read/write/exit are thin C wrappers
(pread/pwrite with a -1 "current offset" sentinel, adapted from
principia's own lib_core/libc/9sys/{read,write}.c) living in a
companion header (syscall_plan9_$cputype.h) included by an otherwise-
empty decl-generated zsyscall_plan9_$cputype.c, reusing the existing
generation machinery without needing a plan9-specific carve-out in
lib_core/libc/mkfile. seek's own raw stub is the one genuinely tricky
one: a vlong return doesn't fit one register, so the compiler passes a
hidden result-pointer as the function's own first argument (same
register-spill dance as every other stub), and the raw syscall itself
returns a small 0-or-(-1) status.

CORRECTION (July 2026). This file previously recorded the opposite of
the truth here, and the code matched it, so read this carefully before
touching seek's stub again. The claim was that principia's generator
wrote the result back on the wrong condition and that goken should
write back whenever the raw result is NOT -1. That is backwards. THE
KERNEL ITSELF WRITES THE 8-BYTE RESULT through the hidden pointer:
principia's kernel/files/sysfile.c sysseek() validates arg[0], calls
sseek(arg) -- which reads the offset from arg[2]/arg[3] and stores the
new position through arg[0] -- and only then `return 0`s. The return
register therefore never carries an offset at all; it carries 0, or -1
via Plan9's general error-note convention. So the stub must write back
ONLY on error, to turn that -1 into a -1-valued vlong the caller can
see, and must leave the kernel's own write untouched on success --
exactly what principia's generator emits ("CMP $-1,R0; BNE 4(PC)").
principia was right; goken's inversion silently overwrote every
successful seek's correct result with whatever the return register held
(under 5i, the stale syscall number). Both svc_arm.s and svc_mips.s are
now fixed to match principia.

Second bug, in 5i rather than in libc, found in the same pass:
machines/5i/syscall_posix.c's sysseek() read the offset with
getmem_v(REGSP+16) when the kernel's own sseek() reads arg[2]/arg[3],
i.e. SP+12 -- confirmed against 5c's actual output for seek(fd, 6, 0),
which emits "MOVW R3,12(R13)" and "MOVW R4,16(R13)" for the two halves
and whence at 20(R13). Reading from +16 picked up
(whence<<32)|offset_high instead, so seek(fd, 6, 0) silently went to 0
and seek(fd, 3, SEEK_CUR) to 1<<32. machines/vi/syscall.c already had
+12, which is what settled it; principia's own machine/5i/syscall.c
still carries +16, a real divergence from its own kernel and NOT
something to sync back.

Both were invisible for the same reason: every seek in this tree was
seek(fd, 0, 0), where all the misread slots are zero anyway and nothing
inspected the return value. tests/c/hello_libc/io.c now seeks to a
nonzero offset and checks what seek() returns.

port/seek.c's portable lseek()-renaming shim must not be linked for
this GOOS, since Plan9's own seek(2) is already named/shaped exactly
like the public seek() -- doing so would fail to resolve `lseek` (plan9
has no such symbol) or silently conflict with the real one. That
exclusion was originally a `#ifndef plan9` inside the file; it now
lives in lib_core/libc/mkfile's PORTPOSIXOFILES instead, to keep port/
free of GOOS branching (see CLAUDE.md).

A genuine, previously-undiscovered bug in 5i itself, found while
verifying the above: machines/5i/run.c's Ib()/Ibl() (the B/BL
instruction decoders) mask the 24-bit branch offset but never
sign-extend it, so any *backward* branch -- including the utterly
mundane "loop: B loop" every arch/$cputype/rt0.s here falls back to
after main() returns -- computed a huge *positive* offset instead of a
small negative one, sending the emulated PC to a wild address far past
the program's own text segment and crashing 5i itself (SIGSEGV in
ifetch(), confirmed via gdb) rather than the emulated program. Never
caught before because every prior hand-written Plan9 test's own
trailing "loop:" sits after an EXITS syscall that never actually
returns (a real Plan9 process just terminates there), so a real
backward branch was never actually executed until a genuine
libc-linked program's rt0.s hit it -- isolated with a two-line, single-
file repro (`loop: B loop` with nothing else) before touching any of
the new syscall code, confirming it was a pre-existing decoder gap, not
something the new file-syscall work introduced. Fixed with the
standard mask-then-sign-extend idiom in both functions; rebuilding 5i
and rerunning the same repro now loops harmlessly (as the code says to)
instead of crashing.

Verification and what's still broken
------------------------------------------

Confirmed via real `5i`/`vi` execution (not just compile-and-link):
lib_core/libc builds cleanly for `objtype=arm cputype=arm GOOS=plan9`
and `objtype=mips cputype=mips GOOS=plan9`. A minimal libc-linked
program (empty main(), relying on rt0.s -> exit(0) -> exits(0)) runs to
completion under 5i with no crash. A print() call with NO format
specifiers also prints correctly. But: a print() call WITH a format
specifier (e.g. "%d") fails on both arches once GOOS=plan9 -- on arm it
silently skips substitution (prints the literal "%d" instead of the
value, then still reaches exits() normally); on mips it hangs
indefinitely partway through the same call (confirmed via a real
timeout, not just "seemed slow"). Root cause NOT found this session --
ruled out so far: fmt/*.c's own #ifdef plan9 (there is none), and the
arm va_arg/va_start macros themselves (include/arch/arm/u.h's `&start`-
based approach, unmodified by this work and already proven correct on
linux/arm). Prime remaining suspects, untried: something in the
write()/pwrite() path corrupting fmtfd.c's internal buffering state
across the first vs second print() call specifically (the "plain
string, then one with %d" repro shows the FIRST call, no format
specifiers, succeeding, and the second, which does, failing) -- or a
stack-layout assumption elsewhere in the varargs chain that happens to
only bite once a real format-consuming va_arg() is hit. Not yet wired
into tests/c/hello_libc's mkfile or the mk test infra pending this fix
-- hello.c/io.c both use %d-style print() calls, so neither can pass as
a real regression gate yet.

machines/qi (PowerPC) and machines/ki (SPARC) bring-up (2026-08-31)
------------------------------------------------------------------------

Same bring-up pass as 5i/vi above, applied to the freshly-imported qi/
ki emulators, which had never been built or run at all (see
docs/claude_notes/notes_libmach.txt's own section on this bring-up for
the libmach-side half of the story -- crackhdr() couldn't even
recognize a q.out/k.out file before this work, independent of anything
below). The exact same bug *classes* 5i/vi already hit reappeared,
confirming these aren't one-off ARM/MIPS bugs but a real "porting an
old 32-bit-host Plan9 emulator to a 64-bit host" pattern worth checking
for on any future arch:

- **Registers.ir and Registers.r[32] were `ulong`/`long` (64 bits on
  this host) instead of a real 32-bit type**, in both power.h and
  sparc.h -- identical to arm.h/mips.h before their own fix. Retyped
  to `u32int` in both headers, plus ifetch()/getmem_4()/getmem_w() in
  both mem.c files. Confirmed by grep before fixing, not just by
  analogy: qi/iu.c's `rotl()` (used by rlwinm/rlwimi/rlwnm, gcc's usual
  lowering for PowerPC bitfield extracts and even plain register moves)
  computed `(v<<sh) | (v>>(32-sh))` -- the exact shape of 5i's Idp3()
  bug -- and ki/run.c's arithmetic-right-shift path had the matching
  `reg.r[rd] = reg.r[rs1]>>v | ~((1<<(32-v))-1)`. Unlike 5i's Idp3, the
  rlwinm-family bug happened to be masked in practice by rlwinm's own
  `& m` (m never has bits set above 31, so 64-bit leakage above bit 31
  gets masked away regardless) -- but Registers.r[] being the wrong
  width is still the right thing to fix everywhere, not something to
  leave in place because one particular caller happens to tolerate it.
- **ki/syscall.c and qi/syscall.c were still on the OLD syscall
  numbering** (`/sys/src/libc/9syscall/sys.h`, `_READ`/`_WRITE`/
  `OSEEK`/etc.) instead of lib_core/libc/syscall/os/plan9/sys.h's
  modern PREAD/PWRITE/SEEK numbering -- i.e. the exact pre-fix state
  5i/vi's syscall.c was in before its own port. Rather than re-deriving
  every fix independently, both were replaced wholesale with
  machines/vi/syscall.c's own already-fixed content (offset==-1
  "current position" handling, fd 0/1/2 routed through plain write(),
  getmem_v()/putmem_v() instead of the hand-rolled `union { vlong v;
  ulong u[2]; }` that assumed a 32-bit host), just substituting each
  arch's own REGSP/REGRET (qi: R1/R3, ki: R1/R7 -- already correct in
  the original files, unlike the syscall numbering) and trap-dispatch
  function name (`sc` for qi, `ta` for ki, matching each arch's own
  run.c decode table -- NOT `Ssyscall`, that's 5i/vi's own name).
  ki/mem.c had no getmem_v()/putmem_v() at all before this (qi/mem.c
  already had them, correctly ordered for big-endian) -- added,
  matching SPARC's big-endian word order (high word at addr, low at
  addr+4, same as MIPS/PowerPC -- the mirror image of 5i/mem.c's
  little-endian ARM version). Both syscall.c files also needed
  `#undef NOP` immediately before including sys.h: power.h/sparc.h
  each already define their own NOP (an opcode encoding, 0x80300000,
  live code in ki/run.c's nop-skip check, dead in qi's C sources but
  not worth removing from the header) which collides with sys.h's NOP
  (syscall number 0) if not undefined first.
- **Two qi-only build breaks, neither related to the syscall/register
  work above**: (1) `sync(ulong)` (a real PowerPC opcode, `sync`)
  collided with POSIX's own `sync(void)` pulled in via unistd.h on
  this host -- renamed to `psync` (declaration, decode-table entry,
  and definition; the *disassembled mnemonic string* stays "sync",
  only the C function renamed, same spirit as the pre-existing
  `sysbrk_` avoiding a `brk()` collision). (2) float.c/qi.c used
  `FPdbleword` and `FPAOVFL`/`FPAINEX`/`FPAUNFL`/`FPAZDIV`, which exist
  in include/arch/power/u.h -- but that header is for cross-compiling
  *target* PowerPC code, where its `ulong hi/lo` fields are 32 bits
  each (target ulong); qi is a *host* tool built with the host's own
  u.h, where `ulong` is 64 bits, so pulling that union in wholesale
  would silently double its size and break the `double x` aliasing.
  Added a host-safe copy locally to power.h using `u32int hi/lo`
  instead, plus the four FPA* macros as aliases of power.h's own
  existing FPS_OX/XX/UX/ZX. Also stubbed `getfsr()` (real hardware
  FPSCR read, meaningless off real PowerPC silicon) to return 0.
- **ki-only build break**: float.c/run.c both called `SET(op,
  takeit)`, a two-argument Plan9 idiom (mark both vars as
  intentionally-set, silencing an old compiler's "may be used
  uninitialized" warning) -- this codebase's own libc.h defines a
  different one-argument `SET(x)` (`((x)=0)`). Fixed as
  `SET(op); SET(takeit);`, which does what the two-arg form intended
  (pre-initialize both) using the macro that's actually available.

Trap instruction differs by arch -- there is no universal "SYSCALL"
mnemonic
------------------------------------------------------------------------------

Writing tests/s/mini/hello_plan9_power.s and hello_plan9_sparc.s (same
role as hello_plan9_{arm,mips}.s -- raw-syscall Plan9 hello-worlds,
run via `:c` under qi/ki respectively) surfaced that the "number in a
register, args on the stack, trap" shape above holds, but the trap
*instruction itself* is not uniform:

  - power: syscall number in R3 (REGRET), args at 4(R1), 8(R1), ...
    (R1 is SP), trap via the assembler's `SYSCALL` pseudo-op (real
    PowerPC `sc`).
  - sparc: syscall number in R7 (REGRET), args at 4(R1), 8(R1), ...
    (R1 is SP), trap via `TA <reg>` (real SPARC "trap always", operand
    is a software-visible trap vector, e.g. `MOVW $0x10,R11; TA R11`,
    matching the convention tests/s/mini/hello_linux_sparc.s already
    uses) -- assemblers/ka has no bare `SYSCALL` mnemonic at all,
    unlike every other arch's assembler here. ki decodes any `TA`
    (regardless of the trap-vector operand) as a syscall, so the exact
    vector value doesn't matter to the emulator, only to matching real
    hardware convention.

Also: **qi's -H2 default `-T`/`-R` matter, unlike the other arches
tried here** -- `ql`'s own -H2 defaults are INITTEXT=0x100020,
INITRND=0x100000 (1MB, not the usual 4K -- see linkers/ql/obj.c),
matching lib_toolchain/libmach/q.c's mpower.pgsize (already 0x100000).
Overriding `-T`/`-R` to a plain 4K-rounded address (tried first, by
analogy with the arm/mips recipes which don't need -T/-R at all)
reproduced the exact same class of txtaddr mismatch as vi's historical
mmips.pgsize bug (see the "Four bugs" section above), ending in qi's
"data_access_MMU_miss" instead of a clean run. Fixed by simply not
passing -T/-R at all and letting ql use its own defaults, same as the
arm/mips recipes already do. ki's own -H2 defaults are a plain 4K
(INITRND=4096, matching msparc.pgsize), so this particular gotcha is
power-specific.

Verification: both hello_plan9_power.exe and hello_plan9_sparc.exe run
to completion under qi/ki respectively (real "Hello, world" +
"exits(0)"), confirmed via tests/qi/smoke.sh, tests/ki/smoke.sh, and a
full top-level `mk test`. As with 5i/vi above, only PWRITE and EXITS
have been exercised end to end via the raw-.s route -- everything else
in sysctab[] beyond what hello_unix.c below exercises is unverified.

lib_core/libc GOOS=plan9 support for power/sparc, and three more real
bugs it surfaced
------------------------------------------------------------------------------

Added the same day as the qi/ki bring-up above: svc_power.s/
svc_sparc.s (raw per-syscall stubs, one function per syscall, same
shape as svc_arm.s/svc_mips.s -- see those files' own header comments)
plus syscall_plan9_{power,sparc}.decl/.h (the empty-decl + hand-written
read/write/exit wrapper pair every arch here needs, verbatim copies of
syscall_plan9_arm.h's own read()/write()/exit()). Register conventions
(power: REGARG==REGRET==R3; sparc: REGARG==REGRET==R7) and the seek()
CMP+BNE write-back guard were NOT derived by analogy with arm/mips --
they were transcribed directly from the real Plan9 4th edition source
(~/xxx/plan9/SRC/libc/9syscall/mkfile's own `case power`/`case sparc`
generator branches), and independently cross-checked against 'qc -S'/
'kc -S' on real two-argument probe functions. One real difference from
that transcription: sparc's real trap is `TA R0` (R0/%g0 is hardwired
zero, giving trap vector 0) -- NOT `TA $0x10` the way linux/sparc's own
svc_sparc.s traps; an earlier draft of tests/s/mini/hello_plan9_sparc.s
had copied the Linux convention (harmless there only because ki's own
ta() dispatch accepts any trap operand) and was fixed to match once the
real mkfile was consulted.

This uncovered three more genuine bugs, none related to syscall
marshalling at all -- getting a full C program (hello_unix.c) running
end to end exercises branches, comparisons and library-call chains a
raw hello-world .s file never does, the same lesson 5i/vi's own
register-width bugs (bdd07d321, "A genuine, previously-undiscovered
bug in 5i itself") already taught:

1. **qi: bx()/bcx() (machines/qi/branch.c) had the exact same missing-
   sign-extension bug as 5i's historical Ib()/Ibl()** -- "imm |=
   0xFC000000"/"0xFFFF0000" only set bits 25..31, leaving bits 32..63
   zero on this 64-bit host, so a negative (backward) branch offset
   read back as a huge positive number and reg.pc+imm landed nowhere
   near the real target. hello_plan9_power.s never triggered it
   (straight-line code, no backward branches); hello_unix.c's first
   loop did. Fixed by declaring `imm` as `int32` directly (not `long`)
   -- the OR then happens at genuine 32-bit width, and `ea = reg.pc +
   imm` sign-extends correctly when widening to ulong for the add.

2. **ki: call() (machines/ki/run.c) had a far more severe version of
   the same bug class -- it broke EVERY function call, not just
   backward ones.** The original "npc = (ir<<2) + reg.pc" neither
   masked out CALL's own 2 opcode bits nor sign-extended the 30-bit
   word displacement; on a 32-bit host both slips cancelled out via
   natural wraparound, but on this 64-bit host the opcode bit (always
   set, since CALL's own op is nonzero) survived into bit 32+,
   computing a target ~4 billion bytes past the real one on literally
   every call -- crashing on rt0.s's own first "call main". Fixed by
   masking to the real 30-bit displacement field and computing the
   shift in a genuine `int32`, matching the fix pattern above.

3. **qi: every SIGNED-comparison-adjacent function that copied
   reg.r[...] (u32int) into a `long` local had the mirror-image bug --
   zero-extension instead of missing sign-extension.** setcr()
   (int d, long r) -- called from ~15 record-form instruction sites to
   set CR0's LT/GT/EQ bits -- read a negative 32-bit result as a huge
   *positive* 64-bit number, so "r > 0" picked the wrong condition-code
   bit. cmp()/cmpi() had the identical bug for PowerPC's own SIGNED
   compare instructions (va/vb, v declared `long`, assigned straight
   from reg.r[]); twi()/tw() (trap instructions) too. Found via a real
   hang, not by audit: __fmtpad (int-to-decimal formatting's width-
   padding loop) read a small negative "remaining width" as huge-
   positive and looped until timeout instead of stopping immediately.
   Fixed the same way as (1)/(2) -- retyped the affected locals to
   `int32` (cmpl()/cmpli(), the UNSIGNED compare instructions, were
   already correctly `ulong` and needed no change).

4. **ki: SPARC v8's hardware umul/smul/udiv/sdiv (plus their .cc
   variants) were simply never implemented** -- op2[]'s op3 slots
   0x0A/0x0B/0x0E/0x0F and 0x1A/0x1B/0x1E/0x1F all carried a bare
   `{ undef, "" }`. Not a bug in existing code, a real missing feature:
   mkfiles/sparc/mkfile already documents passing kl `-M` specifically
   so it emits real hardware smul/sdiv instead of calls into
   nonexistent `_mul`/`_div` software helpers (see that mkfile's own
   comment) -- kc/kl already assumed ki could execute them, nothing in
   ki's own decode tables ever backed that assumption. Found via
   hello_unix.c's first `print("...%d", argc)` (int-to-decimal
   formatting divides by 10). Implemented directly in machines/ki/
   run.c using the host's own 64-bit arithmetic (%Y:rd as a 64-bit
   dividend/product) rather than writing a SPARC-assembly software
   division library -- reg.Y is not computed by these, since kl's own
   asm.c (cases 52-55) already emits the real "sra rs1,31,%y"/
   "wr %g0,%y" prelude before every divide, so it's already correct by
   the time udiv()/sdiv() run.

Also needed: arch/sparc/rt0_plan9.s, a SEPARATE rt0.s from arch/
sparc/rt0.s (which is genuinely Linux-specific, not just untested for
Plan9 -- it copies the real hardware %sp out of R14 into R1 to work
around a register-window save-area shift that only exists in the raw
Linux SPARC32 kernel entry ABI; Plan9's own process-entry convention,
already implemented in machines/ki/ki.c's initstk(), hands R1 a valid
value directly with argc at 0(R1)/argv at 4(R1) -- the same simple
shape arm/mips/power's own single rt0.s already read). Selected via
`RT0OFILE=arch/sparc/rt0_plan9.$O` on the mk command line, the same
override mechanism arch/amd64/rt0_darwin.s and arch/arm64/
rt0_darwin.s already use (see lib_core/libc/mkfile's own RT0OFILE
comment) -- see rt0_plan9.s's own header comment for why it still
needs the same two-TEXT-block (_main/_realmain) split linux/sparc's
rt0.s uses, for a completely different, GOOS-independent reason (kl's
own auto-prologue insertion for any TEXT containing a JMPL).

Net result: demos/mkfile's demo_plan9 target now runs hello_unix.c to
full completion (args/env/proc/mem/file/dir/ctime, same report as
arm/mips) under qi and ki both, matching arm/mips-level parity. Full
top-level `mk test` passes clean throughout.
