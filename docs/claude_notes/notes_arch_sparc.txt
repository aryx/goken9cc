sparc (kl/kc/ka): getting `mk objtype=boot-gcc` to build linkers/kl
=====================================================================

Starting point: `mk objtype=boot-gcc` from linkers/kl/ failed with dozens
of "undeclared identifier" errors compiling ../lk/elf.c (Progbits, Salloc,
Sexec, Strtab, ELFDATA2MSB, wput, ELFCLASS32, EXEC, PT_LOAD, R, X, ...).
kc and ka already built cleanly under boot-gcc -- kl was the only broken
piece of the sparc triad.

Root cause: kl/l.h simply never included "../lk/elf.h", even though
kl/mkfile already compiles linkers/lk/elf.c into kl (elf.$O is in
OFILES, via the generic `%.$O: ../lk/%.c` rule). Grepping every linker's
l.h (`grep -l elf.h */l.h`) shows 6l/7l/il/ql/vl/zl/5lk/8lk all include
it; kl/5l/8l/2l/el don't (el is wasm, genuinely doesn't need ELF; 5l/8l
have separate 5lk/8lk siblings that do; 2l is still mid-bring-up). kl has
no such sibling -- it's expected to emit ELF itself -- so the missing
include was a real gap, not an intentional split.

But the include was only the first layer: kl had NEVER been wired up to
emit ELF at all, unlike ql before its own similar fix (19940257, "power:
wire up ql -H7 (Linux ELF)"), which already had two other ELF-emitting
HEADTYPEs (5, 6) before that commit added a third (7). kl/asm.c only had
`lput` defined -- no cput/wput/wputl/lputl/llput/llputl/strnput at all --
and kl/obj.c's HEADTYPE switch only covered 0 (boot)/1 (garbage)/2 (plan9)/
3 (javastation boot), no ELF case whatsoever. Ported wholesale from
ql/vl's own working HEADTYPE-7 machinery (see linkers/lk/elf.c, the
shared elf32()/elf32phdr()/elf32shdr() emitter):

- kl/l.h: added `#include "../lk/elf.h"`; added `EXTERN long INITTEXTP`
  (physical text address, elf32()'s own PT_LOAD field -- every HEADTYPE-7
  arch has this, kl didn't); retyped lput's prototype long->int32 and
  added cput/wput/wputl/lputl/llput/llputl/strnput prototypes, matching
  every ELF-emitting sibling's l.h.
- kl/obj.c: added a `-P` flag (sets INITTEXTP, mirrors -T/-D/-R/-H
  parsing already there) and `if(INITTEXTP==-1) INITTEXTP=INITTEXT;`
  after the HEADTYPE switch; added `case 7:` with the same sizing every
  HEADTYPE-7 arch uses (HEADR = rnd(Ehdr32sz+3*Phdr32sz,16), INITTEXT
  default 0x00400000+HEADR, INITRND 4096 -- Linux's ELF loader needs
  PT_LOAD vaddr and file offset to agree mod page size, same reasoning
  as ql/vl's own case 7 comments).
- kl/asm.c: retyped lput long->int32; added cput/wput/wputl/lputl/
  llput/llputl/strnput (byte-for-byte copied from ql/vl's own, using
  this file's existing big-endian LPUT macro -- sparc is big-endian,
  same as power/mips); added `case 7:` to both mid-function seek()
  switches (data-segment seek, symtab seek -- `rnd(HEADR+textsize,
  INITRND)`, matching elf32()'s own PT_LOAD offset math) and to the
  final header-write switch, calling `elf32(SPARC, ELFDATA2MSB, 0, nil)`
  (SPARC=2, linkers/lk/elf.h's own e_machine constant).

Applied ql's OWN later-learned lesson up front, rather than
rediscovering it: ql's HEADTYPE-7 case originally set `debug['S']=1`
unconditionally, which corrupted the tail of .data whenever a build
stripped symbols (mkfiles/power/mkfile always does) -- see the "FIXED
(follow-up session)" section of notes_arch_power.txt for the full
root-cause writeup (elf32sectab()'s unrounded seek offset landing inside
the page-rounded, already-written .data). kl's own case 7 guards this
with `if(!debug['s']) debug['S']=1;` from the start, matching ql's fixed
version, not its original buggy one.

enam.c generation: separate pre-existing bug, same fix pattern as ql
------------------------------------------------------------------------

Once elf.c compiled, enam.c generation itself failed: `ed`'s substitution
in kl/mkenam never terminated the last string ("LAST) because
include/obj/k.out.h's final enum entry (ALAST) has no trailing comma, so
the `v/^	A/d` / `,s/,.*$/",/` pipeline had nothing to match on that
line. Diffing kl/mkenam against ql/mkenam (which builds fine) found the
fix already invented there: an extra `g/^	ALAST/s//&,/` line that
synthesizes the missing comma before the rest of the script runs. Copied
verbatim into kl/mkenam.

Verified: clean `mk objtype=boot-gcc` (rm *.o o.out enam.c first) builds
kl with no errors or warnings, links a working o.out, and running it with
no args prints the expected usage message. ka already built clean under
boot-gcc before this session; not touched. kc's own `mk objtype=boot-gcc`
run produced no error output either, which this session initially
misread as "already builds clean" -- see the correction below, it does
NOT actually build kc at all.

exit_linux_sparc.s: real ELF exit(42), verified under qemu-sparc
------------------------------------------------------------------

Follow-up session: wrote tests/s/exit/exit_linux_sparc.s and wired it
into that mkfile/EXITLINUXBINS + scripts/qemu-runner (`sparc) qemu=qemu-
sparc`), same shape as every other arch's own exit(42) test. First real
end-to-end exercise of the HEADTYPE-7 wiring above: `ka -c` + `kl -H7`
produce a genuine 32-bit big-endian SPARC ELF (readelf confirms EM_SPARC,
ELFDATA2MSB, entry point set correctly), and `qemu-sparc
./exit_linux_sparc.exe` exits 42. Full `tests/s` suite (`mk test`, every
arch, every sub-test) re-run afterward with sparc included: no
regressions.

Syscall ABI notes, since this port's own register story is unusual:

- Real Linux SPARC32 syscall convention (confirmed against this host's
  installed sparc64-linux-gnu cross headers, /usr/sparc64-linux-gnu/
  include/asm/unistd_32.h, and a real glibc checkout's sysdeps/unix/
  sysv/linux/sparc/sparc32/sysdep.h found on this machine): syscall
  number in %g1, args in %o0-%o5, trap via `ta 0x10`, errors signaled
  through the carry (icc.C) condition bit rather than a negative return
  value. __NR_exit is 1, same legacy/x86-style numbering SPARC Linux
  inherited, not a SPARC-specific table.
- This port's own registers (include/obj/k.out.h) are a flat R0-R31
  numbering that maps DIRECTLY onto the real 32-entry SPARC register
  file with no renaming layer: linkers/kl/asm.c's OP_IRR/OP_RRR macros
  splice p->from.reg/p->to.reg straight into the instruction's rs1/rs2/
  rd bit fields, and real SPARC register numbering is 0-7=%g0-%g7,
  8-15=%o0-%o7, 16-23=%l0-%l7, 24-31=%i0-%i7 -- so R1 really is %g1,
  R8 really is %o0, confirmed by decoding a compiled MOVW's actual
  opcode bits, not assumed. This port's OWN naming for these registers
  (REGSP=1, REGARG=7=%g7) has nothing to do with the real hardware ABI
  -- it's this compiler's internal convention for ITS OWN generated
  code (a flat, non-windowed calling convention that never emits SAVE/
  RESTORE for ordinary calls, unlike a real SPARC ABI's register-window
  rotation), irrelevant to hand-written asm, which just needs the right
  PHYSICAL registers loaded before the trap.
- kl has no immediate form of TA wired up: linkers/kl/optab.c has
  exactly one ATA row (`{ATA, C_REG, C_NONE, C_NONE, 33, 4, 0}`), and
  asm.c's case 33 (`o1 = opcode(ATA) | (p->from.reg<<14)`) only ever
  fills the rs1 field, leaving the instruction's imm7 bits at 0 -- so
  `TA Rx` assembles to real hardware `ta %rx + 0`, i.e. the trap number
  comes from whatever value is in the given register at trap time, not
  from a literal operand. Decoded by hand from asm.c's OPT(8) macro
  (0x81d02000 | (8<<25) = 0x91d02000) against the real SPARC v8 Ticc
  instruction format (op3=0x3A at bits24-19, cond=1000/"always" at
  bits28-25, i=1 at bit13) before writing the test, not by trial and
  error. So exit_linux_sparc.s loads 0x10 into a scratch register (R9,
  i.e. %o1) and does `TA R9`, rather than any single-instruction `ta
  $0x10` form.

kc/mkfile: NOT actually wired up, despite producing no error
------------------------------------------------------------------

Correcting an earlier claim in this same file: `mk objtype=boot-gcc` in
compilers/kc/ prints no error and exits 0, which this session initially
read as "kc already builds clean." It does NOT -- compilers/kc/mkfile
itself is a stale, never-ported Plan-9-native mkfile (`</$objtype/mkfile`
and `</sys/src/cmd/mkone`, absolute in-tree include paths that have never
existed in this goken layout, unlike every sibling compiler's own
`<$TOP/mkfiles/$objtype/mkfile` / `<$TOP/mkfiles/mkone`). mk just warns
"skipping missing include file" for both and falls through to the one
concrete rule left in the file (`$LIB:`, which builds the shared
compilers/cc/cc.a$O), so the recipe silently "succeeds" without ever
compiling a single kc/*.c file or producing a kc binary -- confirmed by
`which kc` finding nothing in ROOT/arch/boot-gcc/bin even after this
"successful" run. Not fixed this session (out of scope: this session's
new exit_linux_sparc.s test is hand-written assembly and never needed
kc), but a real gap for whoever next needs a compiled-C sparc test
(tests/c/mini-equivalent) -- porting kc/mkfile to the `<$TOP/mkfiles/...`
style every other compiler already uses is the fix, mirroring the
already-ported assemblers/ka/mkfile as the template.

What's still unverified / out of scope for this session
------------------------------------------------------------

- mkfiles/sparc/mkfile is a leftover, unedited copy of power's mkfile
  from the original import (cf54e8364) -- literally `CC=qc LD="ql -H7"
  AS=qa` and `-I$TOP/include/arch/power`, i.e. it points `mk
  objtype=sparc` at the POWER toolchain, not kc/kl/ka. Left unfixed
  deliberately: swapping in kc/kl/ka would immediately hit a much bigger
  gap than this session's scope -- lib_core/libc/arch/sparc/ doesn't
  exist at all yet (no rt0.s/setjmp.s/vlop.s, unlike power's own, see
  notes_arch_power.txt's "hello_libc" section for the shape of that
  work), so `mk objtype=sparc` can't actually link a runnable binary yet
  regardless of the mkfile fix. Fixing the mkfile without that runtime
  support would just trade one broken build for a different one.
- DONE (follow-up session): tests/s/exit/exit_linux_sparc.s now produces
  a real ELF that exits 42 under qemu-sparc, see the section above. No
  r0iszero-equivalent quirk was hit -- R0 reads as hardware-zero on
  SPARC (REGZERO=0, same convention as MIPS, not PowerPC's RA-field
  special case), so nothing analogous to power's -0 flag was needed.
- kl only has ONE real instruction verified end-to-end so far (MOVW
  $smallconst,Rx via the C_SCON optab row, exercised three times by
  exit_linux_sparc.s) plus TA's register form. kl/asmout.c and
  kl/span.c's much larger surface (loads/stores, branches, the
  SAVE/RESTORE-based real prologue path noop.c generates for non-leaf
  functions, floating point, MUL/DIV pseudo-op expansion) is completely
  unaudited and unexercised -- this session deliberately picked the
  smallest test that could validate the ELF plumbing without touching
  any of that.
- kc/mkfile needs the same `<$TOP/mkfiles/...` porting ka/kl's mkfiles
  already got, see the section above -- until then there is no way to
  compile real C for sparc, only hand assembly.
