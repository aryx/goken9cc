sparc (kl/kc/ka): getting `mk objtype=boot-gcc` to build linkers/kl
=====================================================================

Starting point: `mk objtype=boot-gcc` from linkers/kl/ failed with dozens
of "undeclared identifier" errors compiling ../lk/elf.c (Progbits, Salloc,
Sexec, Strtab, ELFDATA2MSB, wput, ELFCLASS32, EXEC, PT_LOAD, R, X, ...).
kc and ka already built cleanly under boot-gcc -- kl was the only broken
piece of the sparc triad.

Root cause: kl/l.h simply never included "../lk/elf.h", even though
kl/mkfile already compiles linkers/lk/elf.c into kl (elf.$O is in
OFILES, via the generic `%.$O: ../lk/%.c` rule). Grepping every linker's
l.h (`grep -l elf.h */l.h`) shows 6l/7l/il/ql/vl/zl/5lk/8lk all include
it; kl/5l/8l/2l/el don't (el is wasm, genuinely doesn't need ELF; 5l/8l
have separate 5lk/8lk siblings that do; 2l is still mid-bring-up). kl has
no such sibling -- it's expected to emit ELF itself -- so the missing
include was a real gap, not an intentional split.

But the include was only the first layer: kl had NEVER been wired up to
emit ELF at all, unlike ql before its own similar fix (19940257, "power:
wire up ql -H7 (Linux ELF)"), which already had two other ELF-emitting
HEADTYPEs (5, 6) before that commit added a third (7). kl/asm.c only had
`lput` defined -- no cput/wput/wputl/lputl/llput/llputl/strnput at all --
and kl/obj.c's HEADTYPE switch only covered 0 (boot)/1 (garbage)/2 (plan9)/
3 (javastation boot), no ELF case whatsoever. Ported wholesale from
ql/vl's own working HEADTYPE-7 machinery (see linkers/lk/elf.c, the
shared elf32()/elf32phdr()/elf32shdr() emitter):

- kl/l.h: added `#include "../lk/elf.h"`; added `EXTERN long INITTEXTP`
  (physical text address, elf32()'s own PT_LOAD field -- every HEADTYPE-7
  arch has this, kl didn't); retyped lput's prototype long->int32 and
  added cput/wput/wputl/lputl/llput/llputl/strnput prototypes, matching
  every ELF-emitting sibling's l.h.
- kl/obj.c: added a `-P` flag (sets INITTEXTP, mirrors -T/-D/-R/-H
  parsing already there) and `if(INITTEXTP==-1) INITTEXTP=INITTEXT;`
  after the HEADTYPE switch; added `case 7:` with the same sizing every
  HEADTYPE-7 arch uses (HEADR = rnd(Ehdr32sz+3*Phdr32sz,16), INITTEXT
  default 0x00400000+HEADR, INITRND 4096 -- Linux's ELF loader needs
  PT_LOAD vaddr and file offset to agree mod page size, same reasoning
  as ql/vl's own case 7 comments).
- kl/asm.c: retyped lput long->int32; added cput/wput/wputl/lputl/
  llput/llputl/strnput (byte-for-byte copied from ql/vl's own, using
  this file's existing big-endian LPUT macro -- sparc is big-endian,
  same as power/mips); added `case 7:` to both mid-function seek()
  switches (data-segment seek, symtab seek -- `rnd(HEADR+textsize,
  INITRND)`, matching elf32()'s own PT_LOAD offset math) and to the
  final header-write switch, calling `elf32(SPARC, ELFDATA2MSB, 0, nil)`
  (SPARC=2, linkers/lk/elf.h's own e_machine constant).

Applied ql's OWN later-learned lesson up front, rather than
rediscovering it: ql's HEADTYPE-7 case originally set `debug['S']=1`
unconditionally, which corrupted the tail of .data whenever a build
stripped symbols (mkfiles/power/mkfile always does) -- see the "FIXED
(follow-up session)" section of notes_arch_power.txt for the full
root-cause writeup (elf32sectab()'s unrounded seek offset landing inside
the page-rounded, already-written .data). kl's own case 7 guards this
with `if(!debug['s']) debug['S']=1;` from the start, matching ql's fixed
version, not its original buggy one.

enam.c generation: separate pre-existing bug, same fix pattern as ql
------------------------------------------------------------------------

Once elf.c compiled, enam.c generation itself failed: `ed`'s substitution
in kl/mkenam never terminated the last string ("LAST) because

Syscall ABI notes, since this port's own register story is unusual:

- Real Linux SPARC32 syscall convention (confirmed against this host's
  installed sparc64-linux-gnu cross headers, /usr/sparc64-linux-gnu/
  include/asm/unistd_32.h, and a real glibc checkout's sysdeps/unix/
  sysv/linux/sparc/sparc32/sysdep.h found on this machine): syscall
  number in %g1, args in %o0-%o5, trap via `ta 0x10`, errors signaled
  through the carry (icc.C) condition bit rather than a negative return
  value. __NR_exit is 1, same legacy/x86-style numbering SPARC Linux
  inherited, not a SPARC-specific table.
- This port's own registers (include/obj/k.out.h) are a flat R0-R31
  numbering that maps DIRECTLY onto the real 32-entry SPARC register
  file with no renaming layer: linkers/kl/asm.c's OP_IRR/OP_RRR macros
  splice p->from.reg/p->to.reg straight into the instruction's rs1/rs2/
  rd bit fields, and real SPARC register numbering is 0-7=%g0-%g7,
  8-15=%o0-%o7, 16-23=%l0-%l7, 24-31=%i0-%i7 -- so R1 really is %g1,
  R8 really is %o0, confirmed by decoding a compiled MOVW's actual
  opcode bits, not assumed. This port's OWN naming for these registers
  (REGSP=1, REGARG=7=%g7) has nothing to do with the real hardware ABI
  -- it's this compiler's internal convention for ITS OWN generated
  code (a flat, non-windowed calling convention that never emits SAVE/
  RESTORE for ordinary calls, unlike a real SPARC ABI's register-window
  rotation), irrelevant to hand-written asm, which just needs the right
  PHYSICAL registers loaded before the trap.
- kl has no immediate form of TA wired up: linkers/kl/optab.c has
  exactly one ATA row (`{ATA, C_REG, C_NONE, C_NONE, 33, 4, 0}`), and
  asm.c's case 33 (`o1 = opcode(ATA) | (p->from.reg<<14)`) only ever
  fills the rs1 field, leaving the instruction's imm7 bits at 0 -- so
  `TA Rx` assembles to real hardware `ta %rx + 0`, i.e. the trap number
  comes from whatever value is in the given register at trap time, not
  from a literal operand. Decoded by hand from asm.c's OPT(8) macro
  (0x81d02000 | (8<<25) = 0x91d02000) against the real SPARC v8 Ticc
  instruction format (op3=0x3A at bits24-19, cond=1000/"always" at
  bits28-25, i=1 at bit13) before writing the test, not by trial and
  error. So exit_linux_sparc.s loads 0x10 into a scratch register (R9,
  i.e. %o1) and does `TA R9`, rather than any single-instruction `ta
  $0x10` form.

tests/s/mini/hello_linux_sparc.s: .data segment + SB addressing, first try
------------------------------------------------------------------------------

Second follow-up session: wrote tests/s/mini/hello_linux_sparc.s (write()
+ exit(), the standard hello-world shape every other arch's own
tests/s/mini/hello_linux_*.s already follows) and wired it into that
mkfile's LINUXBINS, same recipe shape as tests/s/exit's own (`ka -c` +
`kl -H7 -o ... -E _start`). Passed on the FIRST assembly/link/run attempt
-- no new kl bugs found, unlike some other arches' own mini bring-ups.

This exercises real .data addressing for the first time (exit_linux_sparc.s
has no .data segment at all): `MOVW $setSB(SB), R2` loads kl's "static
pointer" register (REGSB=2, i.e. real hardware %g2) with the runtime data-
segment base biased by `BIG` (4088, `l.h`'s `BIG = 4096-8`), and `MOVW
$msg(SB), R9` then computes `msg`'s real address as `R2 + (msg's small
offset - BIG)` via a single ADD-immediate (span.c's aclass() classifies
this as C_SECON since msg's biased offset lands within ±BIG, exactly the
same "small external constant" addressing scheme every other HEADTYPE-7
arch here already uses under a different register).

claude: CORRECTION to an earlier version of this note -- while working out
the analogous m68k addressing later, a hand-disassembly of this binary's
actual .text bytes (sparc64-linux-gnu-objdump chokes on this ELF's
section-header layout, see notes_test_infra.txt-worthy detail: had to `dd`
the raw text segment out by program-header offset and decode by hand
against SPARC v8's real instruction encoding) turned up that this section
previously claimed span.c's aclass() C_SECON range check for D_CONST/
D_EXTERN was dead code that "never actually fires" for ordinary small
symbol references, always falling through to the trailing `return
C_LCON;` regardless. That claim was WRONG -- a plain misreading of the
control flow: the check is `if(cond) return C_SECON;` followed by
unconditional code, which is completely ordinary early-return, not dead
code hidden behind an unreachable condition. The disassembly proves this
directly: `$msg(SB)`'s load into R9 decodes to a single `add %g2, -4088,
%o1` (rs1=R2, imm13=-BIG, rd=R9) -- exactly the C_SECON path, no sethi
involved. `$setSB(SB)`'s own load into R2, by contrast, DOES decode to a
sethi+add pair (`sethi %hi(...), %g14` then `add %g14, ..., %g2` --
REGTMP=R14 confirmed as the sethi target, R2 as the final destination),
confirming it takes the C_LCON path -- but that's because setSB is a
deliberate special case: its own value is defined as exactly `0+BIG`
(pass.c's `xdefine("setSB", SDATA, 0L+BIG)`), so `instoffset =
s->value+a->offset-BIG` comes out to exactly 0, which the range check's
own `instoffset != 0` term deliberately excludes -- avoiding the
self-referential bootstrap problem of computing R2's own load relative to
R2 before it holds a valid value. So: no wart, no bug, nothing to fix.
The `instoffset != 0` exclusion is intentional and correct, and ordinary
small D_CONST/D_EXTERN references (msg included) correctly and
demonstrably take the C_SECON fast path today.

Verified: `ka -c` + `kl -H7` build a working ELF, `qemu-sparc

hello.expected.txt, full tests/s suite and top-level `mk test` re-run

kc: getting it to compile, link, and pass tests/c/mini
========================================================

Starting point: compilers/kc almost compiled (a prior commit,
c7d3b10ea, had already gotten most of it building) but two real bugs
remained, both compile/link-time, not codegen:

- swt.c's align()/maxround() were declared returning `long`/taking
  `long` params, but cc.h's own prototypes (shared by every arch) say
  `int32`. Every other arch's swt.c (5c/6c/7c/8c/vc) matches cc.h
  exactly (no explicit return-type keyword mismatch); kc's didn't.
  qc(compile-time) rejected this as "function inconsistently declared".
  Fixed by matching cc.h: `int32 align(int32, Type*, int)` / `int32
  maxround(int32, int32)`.
- gc.h declared `EXTERN int hintabsize;` where every other arch's gc.h
  (qc/7c/ic/vc, diffed directly) uses `extern int hintabsize; //
  defined in mul.c`. EXTERN expands to nothing in the one file that
  #defines it plain (see mul.c's own `int hintabsize = nelem(hintab);`
  at file scope), so kc's gc.h was silently creating a SECOND
  definition of the same global -- harmless under old-style C tentative
  definitions, but a hard "multiple definition" link error under
  modern gcc's default -fno-common. Fixed by matching the other archs'
  plain `extern`.

Also found and fixed a real config bug unrelated to kc's own sources:
mkfiles/sparc/mkfile was a stale, unedited copy of mkfiles/power/mkfile
(O=q, CC=qc, LD=ql -H7, AS=qa, CFLAGS -I.../arch/power) -- copy-pasted
during the initial sparc toolchain import and never adapted. Fixed to
O=k, CC=kc, LD=kl -H7, AS=ka, CFLAGS -I.../arch/sparc, matching the
arch-letter table (compilers/kc, assemblers/ka, linkers/kl all already
use 'k'). This file governs `mk objtype=sparc` (cross-building test
programs, tests/c/mini included) -- NOT how kc/ka/kl get built in the
first place, which is `mk objtype=boot-gcc` (uses the host gcc, see
mkfiles/boot-gcc/mkfile's own comment on the bootstrap chicken-and-egg).
Confusing the two costs a real debugging detour: running `mk
objtype=sparc` inside compilers/kc itself (before this fix) silently
compiled kc's OWN sources with the not-yet-built `qc` binary (leftover
from the copy-paste) rather than gcc, and the resulting `.q`-suffixed
objects/errors have nothing to do with kc at all.

kc -S on a hand-written two-arg function confirms the calling
convention entirely empirically rather than by inspecting cgen.c: the
first arg arrives in R7 (REGARG=REGRET=7), the second on the stack at
`count+4(FP)` -- same FP-relative convention xwrite_power.s /
xwrite_arm.s already use, so xwrite_sparc.s could be modeled directly
on xwrite_power.s. One real difference from power: kc lowers a C
function call to AJMPL (real SPARC "jmpl"/"call"), NOT ABL -- unlike
qc, where txt.c reuses ABL as the call pseudo-op, kc's ABL is a
genuine conditional branch (OLT's "branch if less", txt.c's own OLT
case), so reusing it for calls would collide with real Bicc branches.
Confirmed by grepping kc/txt.c's OFUNC case (`a = AJMPL`) versus
qc/txt.c's OFUNC case (`a = ABL`).

Wiring `.k` files into `iar`/ar archives (needed for tests/c/mini's
`iar rc libmini.a start_sparc.k xwrite_sparc.k xexit_sparc.k`) exposed
a separate, real gap: lib_toolchain/libmach already had kobj.c
(_isk/_readk, parses .k object files) sitting unused -- never wired
into obj.c's per-arch dispatch table (`static Obj obj[Maxobjtype]`),
never added to libmach/mkfile's OFILES, and its own `#include
"kc/k.out.h"` was already a dangling path (no such subdirectory --
should be `<obj/k.out.h>`, matching qobj.c's `#include <obj/q.out.h>`).
Without this, iar silently produced a libmini.a with no valid SYMDEF
header ("first entry not symbol header" from kl, since kl couldn't
resolve start_sparc.k's/xwrite_sparc.k's/xexit_sparc.k's symbols
through the archive at all). Fixed: added ObjSparc to mach.h's
Maxobjtype enum, `[ObjSparc] "sparc .k", _isk, _readk,` to obj.c's
table, kobj.$O to libmach/mkfile's OFILES, and the include path.
Rebuilt lib_toolchain/libmach and linkers/ar (`mk objtype=boot-gcc
install` in each) before iar could produce valid sparc archives.
Note this only wires up archive support (needed by ar/iar); kobj.c
does NOT give acid/5i-equivalent disassembly of .k files -- there is
no kdb.c/k.c yet, out of scope here.

The two hardest bugs were pure register-convention mismatches, found
by running under `qemu-sparc -strace` (immediate SIGSEGV, no syscalls
attempted) and `qemu-sparc -d cpu -one-insn-per-tb` (dumps full
register state after every single translated block -- essential here,
since this backend's REGSP has nothing to do with any real hardware
register the usual `-d in_asm` alone would explain):

1. REGSP=1=%g1 (this backend's own logical stack pointer, used for
   every C-generated function's frame) is NEVER initialized by the
   Linux kernel at process entry -- only the real hardware %sp (%o6,
   =R14 in this port's flat numbering) is. Confirmed R14 is otherwise
   just this backend's REGTMP ("used by the loader", i.e. genuinely
   free for the compiler to use as sethi/add scratch for large
   constants -- see the setSB decode note above), meaning the OS's
   initial %sp is simply never preserved by any kc-generated code
   either; it's fair game to read exactly once, at the top of _start,
   before it gets clobbered. This is genuinely sparc-specific: every
   other arch's start_$objtype.s (mips/alpha/riscv/...) needs no such
   copy because their own REGSP already IS the OS-initialized
   register. Symptom without the fix: main's own auto-generated
   prologue's first store ("SUB $8,R1" / "MOVW R15,0(R1)") underflows
   R1 from 0 to 0xfffffff8 and segfaults on the very first instruction
   of the whole program, before any syscall.
2. Getting the R14->R1 copy to actually run FIRST turned out to need
   its own fix: kl's noop.c inserts its own "SUB $frame,R1 / MOVW
   R15,0(R1)" prologue immediately after ATEXT, unconditionally, for
   any non-leaf TEXT (checked via `curtext->mark & LEAF`, cleared by
   ANY AJMPL in the TEXT regardless of its operands) -- BEFORE any
   hand-written instructions in that TEXT, regardless of their source
   order. So a straightforward `TEXT _start(SB),$0 / MOVW R14,R1 /
   MOVW $setSB(SB),R2 / JMPL main(SB)` still got the auto-prologue
   spliced in ahead of the R14->R1 copy, because the JMPL made _start
   non-leaf. Fixed by keeping _start genuinely leaf: load main's
   address into a register, then transfer control with the
   register-indirect AJMP form (`JMP (R8)`) instead of AJMPL --  AJMP
   does NOT clear LEAF (noop.c's switch just does branch-delay-slot
   bookkeeping for it, same bucket as the real Bicc branches), and
   _start never needs to return to itself anyway. AJMP has no
   symbol/C_LBRA addressing form in optab.c (only C_SBRA/C_SOREG), so
   this needs the explicit two-instruction load-then-jump-indirect
   form, not a bare `JMP main(SB)`.
3. R1 (REGSP) and the Linux SPARC32 syscall ABI's own %g1
   (syscall-number register) are the SAME physical register -- a
   genuine, unavoidable ABI collision specific to this backend's
   register choice. exit_linux_sparc.s/hello_linux_sparc.s (tests/s)
   never hit this because they're leaf code with no live stack across
   the trap. xwrite_sparc.s does have a live caller stack (main's own
   frame, needed again after xwrite returns) -- clobbering R1 with the
   syscall number and never restoring it corrupts main's REGSP for
   good, surfacing several instructions later as a segfault in main's
   *epilogue* (`MOVW 0(R1),R8` reading the saved link register from a
   garbage address) -- looks unrelated to the syscall at first glance.
   Fixed by saving R1 into a scratch out-register (R12) before setting
   up the syscall and restoring it right after the trap, before
   RETURN. xexit_sparc.s deliberately does NOT restore R1 -- exit()
   never returns, so REGSP never needs to be valid again.

Verified: `mk objtype=boot-gcc` builds and installs kc cleanly (both

kc: tests/c/mini2 (recursion, floats, 64-bit, printf varargs) -- passed with one real fix
---------------------------------------------------------------------------------------------

Follow-up session. tests/c/mini2's helloprintf.c/test.c/
print_nofloat_no64.c exercise everything the mini bring-up above
flagged as unverified: recursion (fact()), a for-loop (fact_iter()),
float64 (test_float() returns 2.2), a 64-bit constant (uvnan), and
printf-style varargs (%t/%x/%s/%d). All of it worked completely
unmodified except for one real gap: `fact`/`fact_iter`'s variable
(non-constant) integer multiply hit `kc`'s generic AMUL opcode, which
`kl`'s noop.c (initmuldiv()) tries to rewrite into a call to a software
`_mul` helper -- and this port has never had one anywhere in this
repo (confirmed by grepping for `TEXT.*_mul` across the whole tree; not
even Plan9's own historical distribution shipped SPARC C runtime source
here). Writing one from scratch turns out to be a trap: hand-writing
`_mul`/`_div`/etc using the SAME `AMUL`/`ADIV` mnemonics ka/kl already
support would recurse into itself, since noop.c's rewrite pass applies
to EVERY occurrence of these opcodes in the linked program, hand-
written or compiler-generated, with no way to distinguish the two.

The actual fix needs no new code at all: SPARC v8 (this backend's real
target) has genuine hardware smul/sdiv/udiv instructions, and kl/asm.c's
own opcode encoder (cases 52-55, the sra+wry+div/mul sequence) already
emits them correctly and UNCONDITIONALLY -- the only thing gating
whether that encoding is reached at all is noop.c's OWN `if(!debug['M'])`
check before triggering the call-rewrite in the first place. Passing
`-M` to kl (added to mkfiles/sparc/mkfile's `LD=`, same idea as power's
own `-0` on `LD=ql`) disables the rewrite entirely, so kc's AMUL/ADIV/
ADIVL/AMOD/AMODL just assemble straight to real hardware instead of
ever looking for `_mul`. Confirmed this is the right, permanent fix
(not a workaround) -- SPARC genuinely never needs a software multiply/
divide fallback the way ARM does (see tests/c/regressions/
arm_div_from_lib.c's own _div/_mod, hand-written because ARM32 truly
has no hardware divide).

Wrote tests/c/mini2/linux_sparc.s (exit/panic/write, `_main` entry)
directly reusing every convention already established and verified by
tests/c/mini's own start_sparc.s/xwrite_sparc.s/xexit_sparc.s -- same
