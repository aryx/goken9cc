The arm64 toolchain (7a/7c/7l): what the 9front unification landed
=====================================================================

Notes on 7a/7c/7l's codegen/ABI internals -- as opposed to the
Mach-O-specific work covered in docs/claude_notes/notes_exec_macho.txt (PIE,
dyld, code signing, the arm64-specific 7c frame-size and vlong-spill
bugs found while bringing up -H6, which live there because they were
found via macOS execution, not because they're macOS-specific bugs).
This file is about the fixes ported from 9front (Charles Forsyth's
arm64 port) via scripts/diff.rc during the July 2026 "big unification"
pass -- see plan9front.txt's arm64 section for the primary source and
todo.org's "arm64 toolchain" section for what's still open. See
compilers/7c/{cgen,txt,peep,reg}.c, assemblers/7a/, linkers/7l/.

Why 9front, and not some other lineage
------------------------------------------

Every other backend in this project has at least one same-era sibling
lineage to diff against (9cc, inferno, kencc, miller-riscv, ...).
arm64 doesn't: it postdates all of those, so 9front's arm64 port
(which is considerably more evolved than goken's own already-extensive
arm64 work) was the only real upstream to compare against. The diff
was large enough that several fixes below are "verbatim, well-reasoned
upstream fix for an objectively-wrong computation" but with **no
demonstrated behavioral difference** in this codebase after landing
them -- worth calling out explicitly, since it means "ported and
verified against the test suite" here sometimes means "confirmed to
not regress anything" rather than "confirmed to fix an observed bug",
unlike the atomics fix below, which is qemu-verified end to end.

gmove()'s long-to-pointer conversion, and usableoffset()'s inverted `||`
------------------------------------------------------------------------------

Two related bugs, both ported from 9front's b117d7014 in one commit:

- gmove() moved a 32-bit int-family value into a vlong/pointer-typed
  register with a plain 64-bit AMOV, which just copies the raw
  register bits instead of sign/zero-extending them. Not every arm64
  instruction leaves a properly extended 64-bit result (e.g. NEGW
  zero-extends), so a negative int used as a pointer offset could
  carry garbage in the high 32 bits. Fixed by introducing a real
  ASXTW (sign-extend word) opcode, which also meant teaching the
  peephole optimizer and register allocator (peep.c/reg.c) about it.

- cgen()/reglcgen() folded a constant array/pointer offset directly
  into a load/store's immediate field via ad hoc inline range checks
  (`v >= -4096 && v < 4096`) instead of calling the already-declared-
  but-never-called usableoffset(), which itself had an outright logic
  bug: `return o >= -256 || o < 4095*s;` (should be `&&`) -- true for
  essentially any offset -- and never checked the offset was a
  multiple of the access width, which arm64's scaled immediate
  encoding requires.

Extensive probing (misaligned/negative/large constant offsets, through
globals, struct fields, function parameters) never found a
reproducible pre/post difference here -- 7l's own aclass()/asmout()
addressing-mode selection appears to self-correct regardless of what
usableoffset() decides, so the practical effect may be codegen quality
rather than correctness (matching 9front's own commit message: "not
so optimal pointer arithmetic instructions"). Applied anyway on the
strength of the original `||` being unambiguously wrong. A *separate*,
still-unfixed bug was found along the way and left alone: a global
array accessed at a compile-time-constant misaligned offset (e.g.
`*(long long*)(buf + 4099) = v;`) fails to link outright with
"internal: miscalculated offset" -- that path goes through naddr()'s
direct D_EXTERN+offset construction, not the usableoffset()-guarded
paths this commit touches.

gmove()'s same-address fast path: a boolean typo that always evaluated true
---------------------------------------------------------------------------------

`if(a == AMOV || (AMOVW || a == AMOVWU) && ewidth[ft] == ewidth[tt] || ...)`
-- `AMOVW` alone is a nonzero enum constant, so `(AMOVW || a ==
AMOVWU)` is always true regardless of `a`, collapsing the guard for
*any* gmove opcode (including type-converting ones like int<->float/
vlong conversions right above it) down to just `ewidth[ft] ==
ewidth[tt]`. Any same-width conversion could spuriously take the
"already in place, skip it" fast path via samaddr() and silently drop
the actual conversion instruction. 9front's arm64 port has read
`(a == AMOVW || a == AMOVWU)` since its very first import -- this was
never broken there, so there's no dedicated fix commit to cite, just
the corrected boolean. No case constructing this failure was found
within budget, but the logic as written is unambiguously wrong.

Struct-copy trailing bytes, and two missed-optimization carve-outs
------------------------------------------------------------------------

- sugen()'s struct/union-copy fallback ("copy:", reached when neither
  side of a struct assignment is directly addressable) truncated the
  byte width via `w /= SZ_LONG;` with no handling for the remainder --
  any assignment whose size isn't a multiple of 4 bytes would silently
  drop its trailing bytes. Fixed with a byte-by-byte tail-copy loop for
  `w % SZ_LONG`, ported verbatim (same 9front commit as above).
  Despite probing across struct sizes (10, 30 bytes) and addressing
  shapes, buggy and fixed builds produced byte-identical assembly --
  the surrounding layout code apparently already over-covers its copy
  width independent of `w`, masking the bug in this codebase's current
  form.

- regopt()'s fixed `Rgn region[NRGN=1000]` array gave up (warn + stop
  optimizing, not a crash) past that many candidate regions -- same
  fix shape as mips's vc (below): grow it dynamically starting at 300,
  doubling via allocn(). Still pending in 5c/6c/8c/ic -- see
  docs/claude_notes/notes_shared_frontend_bugs.txt for the full
  per-backend status of this and several other kencc-lineage-wide bugs.

- mkvar() excluded every "."-prefixed pseudo-symbol from register-
  allocator tracking, including ".ret" -- carved out specifically so
  it stays eligible for optimization, mirroring vc's identical fix.
  Missed optimization, not a correctness bug.

Atomics: LDAR/STLR/LDXR/STXR/LDAXR/STLXR, broken in four independent ways
---------------------------------------------------------------------------------

The one fix in this file with a real, qemu-verified regression test
(the others above either have none or found no observable difference).
The load-acquire/exclusive and store-release/exclusive primitives spinlocks
and CAS loops need were broken in four unrelated ways simultaneously:

1. STLR/STLRB/STLRH/STLRW were grammared as the 3-operand exclusive-
   store form (same grammar as STXR/STLXR, which return a status
   register), instead of the correct 2-operand plain store-release
   form -- `STLR R2, (R1)` failed to *parse*.
2. ALDAR/ALDAXR/ASTLR/ASTLXR had no linkers/7l/optab.c entries at all
   -- even the mnemonics that did parse (ALDAR/ALDAXR) failed to link
   with no matching optab entry.
3. ALDAXRW was encoded with the wrong instruction-size bit in
   opload() (identical to ALDARW's bit pattern) -- had it linked, it
   would have silently executed as a plain load-acquire, dropping the
   "exclusive" semantics a CAS loop depends on for correctness.
   ASTLXP/ASTLXPW had their 32/64-bit size bits swapped in opstore().
4. asmout.c's stxr case encoded the status register from p->from3,
   which doesn't apply to STLR (2-operand, no status register) vs
   STXR/STLXR (3-operand, includes one) -- needed an arity-aware
   rewrite.

Also deliberately dropped, matching 9front rather than left as
silently-broken placeholders: STLXP/STXP/STXPW/LDXP/LDXPW/LDAXP/
LDAXPW, the register-*pair* atomics, since those need a genuinely
different 4-operand operand model this port doesn't have.

Ported from two combined 9front commits (223e8ad00, the one that
actually made STLR usable; 61f6376b1, which fixed LDAXR/STLXR
earlier). tests/s/features/arm64_atomic_ldxr_stxr.s: a real LDXR/STXR
compare-and-retry increment loop (the lock-code idiom), wrapped in an
LDAR/STLR pair, linked and run under qemu-arm64, checked against the
expected post-increment exit code -- confirmed the pre-fix build fails
outright at *parse* time on `STLR R2, (R1)`, a hard, unambiguous
regression check. Also documented in the test itself: the operand
carrying the store-conditional status result is the *third* operand of
STXR, not the first, despite naming conventions elsewhere in this
assembly suggesting otherwise.

7a's own long-filename stack overflow
------------------------------------------

assemble() had the exact same fixed `char ofile[100]`/raw strcpy()
stack buffer overflow already fixed in va (mips) -- found organically
when a feature-test source file happened to live at a long scratch
path and 7a crashed the same way ("*** stack smashing detected ***").
Same fix, same 9front origin: strdup()/smprint() instead of fixed
buffers. See tests/s/regressions/arm64_long_filename.s.tmpl.

bcomplex()'s vlong fast path: `if (x)` silently emitted no branch at all
---------------------------------------------------------------------------------

Not a 9front-diff fix -- goken-original, found while porting benchs/
compcert/vmach.c to build under goken's own toolchain (after widening
its `stack[]`/`sp` from `long` to `long long`, needed since this
compiler's `long` stays 4 bytes even on 64-bit arches -- see
notes_libc_selfhost.txt's vlong writeup). Presented at first as a
linker (7l) crash -- "illegal combination MOV REG NONE SBRA" from
linkers/7l/span.c's oplook(), on a MOV instruction whose destination
looked like a local variable but was classified as a branch target,
with the diagnostic printing a *different* garbage offset on each of
its two prints. Two false leads chased before finding the real cause,
both worth recording since they're easy to re-suspect from the
symptom alone:

- Suspected 7l/span.c's aclass()/oplook() combination-matching logic
  itself (misclassifying a large AUTO offset as C_SBRA) -- span.c
  behaves correctly on this input; the Prog it's classifying was
  already corrupted by the time it got there.
- Suspected the local variable being named `sp` colliding with the
  arch's real SP register once widened to 8 bytes -- a `/tmp`-isolated
  rename test appeared to fix it once, but repeated in-place testing
  showed the identical failure under any variable name, and eventually
  a nondeterministic *mix* of pass/fail on unchanged source across
  repeated builds -- which turned out to be an artifact of testing via
  `mk`'s full multi-program suite (parallel builds / stale `.7`/
  `.goken` artifacts from a previous run) rather than a fresh, isolated
  single-file rebuild. A clean `rm` + direct `7c`+`7l` invocation
  reproduced the *exact same* failure 100% of the time, no
  nondeterminism at all, once the parallel-suite noise was removed.

Root cause, found via `7l -a`'s disassembly listing plus `-g` codegen
traces compared side by side between 7c (fails) and 6c (works, same
source, `-Damd64` instead of `-Darm64`): `if (some_vlong_expr)` -- a
raw truthiness test on a `long long`/`vlong` value, with no explicit
comparison operator written -- goes through src/cmd/cc/pgen.c's
bcomplex() (shared by every "if"/"for"/"while" condition, called from
gen()'s OIF case in the same file). bcomplex() has a dedicated fast
path for vlong conditions on archs with native 64-bit register support
(`typev[n->type->etype] && machcap(Z)` -- true for every 64-bit-native
backend this project has, not just arm64): it synthesizes a
`left != 0` (ONE) comparison node and calls `cgen(b, Z)`. But
compilers/7c/cgen.c's own OEQ/ONE/... case, when handed `nn == Z`
(always true here, since bcomplex() always passes Z), does exactly
`nullwarn(l, r); break;` -- correct for that check's *other* caller (a
genuine `x == y;` expression-statement whose result is unused) but
here it means **no code gets emitted at all**. Control returns to
bcomplex(), which returns 0 as if a branch had been emitted; gen()'s
OIF case then grabs the compiler's global "last emitted instruction"
pointer (`p`) right after, assuming (correctly, for the *fallback*
path two lines below, `bool64(n); boolgen(n, 1, Z);`) that it's a
pending conditional branch to backpatch once the branch target is
known. With nothing actually emitted, `p` is left pointing at whatever
unrelated instruction preceded the "if" -- the later backpatch
(patch(), just two field writes: `to.offset`/`to.type = D_BRANCH`)
corrupts *that* instruction instead. The "if" body's own code then
runs completely unconditionally, spliced in right after the corrupted
instruction, since no branch exists to skip over it.

Confirmed 7c-specific despite bcomplex() living in shared kencc-lineage
code: 6c/amd64 hits the identical `typev[...] && machcap(Z)` condition
(machcap(Z) with a null node is an unconditional `return 1` on every
backend checked) but takes a visibly different route in its own
`-g` trace, going straight into boolgen() with no synthesized ONE node
at all. Traced to 6c linking against a *different* shared frontend
fork -- compilers/cck/pgen.c, not src/cmd/cc/pgen.c (7c/vc/ic still use
the latter; see todo.org's "migrate 7c/vc/ic off src/cmd/cc" item).
compilers/cck/pgen.c's own bcomplex() (behind an additional
`newvlongcode` gate, itself always true) calls `boolgen(b, 1, Z)`
directly instead of `cgen(b, Z)` -- already fixed there, just never
ported back to the copy 7c still builds against.

Considered switching 7c's mkfile wholesale to build against
compilers/cck instead of src/cmd/cc (matching 6c/8c's existing
precedent, and todo.org's stated direction) rather than patching
src/cmd/cc directly. Attempted live: cck's cc.h has real, non-cosmetic
differences from src/cmd/cc/cc.h (several `int32`-vs-`long` forward-
declaration mismatches needing mechanical fixup: outstring/gextern/
exreg/ncast) plus one non-mechanical gap -- cck has no `#pragma
textflag NOSPLIT` mechanism at all (no `textflag` global, ATEXT's flag
byte comes from a plain `profileflg`-derived NOPROF instead), which
compilers/7c/txt.c's gpseudo() relies on (a deliberate goken-specific
addition per its own "goken: new" comment, not upstream kencc/9front
behavior). A full migration is a real, separate, larger task -- not
attempted here; see todo.org for tracking it as its own item alongside
its already-listed vc/ic siblings.

Fixed instead with the minimal, surgical change: src/cmd/cc/pgen.c's
bcomplex() now calls `boolgen(b, 1, Z)` instead of `cgen(b, Z)` in the
vlong fast path, mirroring cck's already-proven-correct version
exactly. boolgen() always emits the compare-and-branch unconditionally
(only its own value-materialization epilogue is gated on `nn != Z`),
so it leaves the "last emitted instruction" state gen()'s OIF caller
actually needs. Verified: 30/30 clean rebuild-and-run of vmach.goken
(no nondeterminism at all once isolated from the parallel-suite
artifact issue above), all 18 previously-passing benchs/compcert
programs still pass after the fix, and
tests/c/regressions/arm64_vlong_if_branch.c (checks actual runtime
behavior, not just "did it link") fails against the pre-fix compiler
and passes against the fixed one, confirmed by temporarily reverting
the fix and rebuilding. Since bcomplex() is called for every "if"/
"for"/"while" condition project-wide, not just vlong ones, and the
buggy path only triggers for the specific `typev[...] && machcap(Z)`
combination (a raw truthiness test on a 64-bit-native value), this was
plausibly latent since arm64 support was first added and just never
exercised by a `if (some_vlong_var)` pattern with no explicit
comparison operator until vmach.c's widening surfaced it.

Large uvlong constants: two independent truncation bugs, one still open
---------------------------------------------------------------------------------

Not 9front-diff-derived (the mkvar() half is goken-original; the
addpool() half ports a relevant slice of an already-known 9front fix,
see below) -- found while porting benchs/compcert/sha3.c and
siphash24.c to build under goken's own toolchain. Both compute wrong
hashes despite building and running cleanly (no crash). Isolated in
tests/c/regressions/arm64_uvlong_shift32.c, which bundles both bugs
below; each was confirmed independently via its own minimal repro
before combining.

1. `x != 0x0123456789ABCDEFULL` (a plain constant failing to compare
   equal to itself, once assigned to a variable and reloaded): found by
   bisecting with `-N` (disables regopt() entirely -- correct) vs `-R`
   (runs regopt() but skips peep() -- already wrong), narrowing the bug
   into regopt()/reg.c specifically, not the peephole optimizer.
   compilers/7c/reg.c's mkvar() forces `et = TLONG` for any bare
   (symbol-less) constant being registerized, on the reasoning that
   naddr()'s OCONST case never sets `a->etype` (only ONAME does), so
   trusting it is unsafe -- true, but TLONG (4 bytes) is only a safe
   *default* when the constant's value actually fits in 4 bytes. Worse,
   mkvar()'s own local `o` (holding `a->offset`, the constant's real
   value) was declared `int32`, silently truncating any 64-bit constant
   right there regardless of `et`. Every consumer trusting the
   resulting Var's ->etype (addmove(), deciding AMOV vs AMOVW when
   reloading a registerized constant) inherited the wrong width. Fixed:
   `o` is now `vlong`, and `et` only defaults to TLONG when the value
   round-trips through a 32-bit sign extension
   (`(vlong)(int32)o == o`). 9front's own mkvar() also widened `o` to
   vlong and dropped the `et = TLONG` default (it's commented out, not
   deleted) -- but 9front's naddr() has the *identical* gap (never sets
   a->etype for OCONST either), so their version appears to rely on
   some other invariant not fully traced here rather than being a
   clean drop-in; this fix instead explicitly recomputes the width from
   the value, which doesn't depend on that invariant either way.

2. `s32 != 0x100000000ULL` (`1ULL << 32`, or any other 64-bit-valued
   constant consumed by something other than a plain assignment -- here
   a CMP): `7l -a`'s disassembly showed `CMP $4294967296,R9` encoded
   with a 4-byte literal-pool entry holding 0 (the low 32 bits of
   4294967296, which are all zero) instead of the real 8-byte value --
   linkers/7l/span.c's addpool() only widens a pool entry to 8 bytes
   (ADWORD) when the *instruction needing it* is itself AMOV; every
   other opcode (CMP, ADD, ...) always got a 4-byte (AWORD) entry
   regardless of whether the constant actually fit. This is the same
   shape bug 9front already fixed in 1d330c0bd ("7l: deal with huge
   (negative or > 24bit) register offsets, fix LACON, avoid DWORD in
   constant pool when we can sign extend") -- ported just the relevant
   condition (`cmp(C_VCON, c) && (uvlong)(a->offset & 0xFFFFFFFFULL) !=
   (uvlong)a->offset` as an additional `||` alternative alongside the
   existing `p->as == AMOV` check), not the rest of that commit's
   LACON/isaddcon rework, which doesn't apply cleanly to goken's
   current (pre-that-commit) addpool() shape.

Both fixes verified via tests/c/regressions/arm64_uvlong_shift32.c
(all four checks: constant self-compare, shift-by-4 sanity check,
shift-by-32, shift-by-33) and cross-checked with several additional
ad hoc repros covering adjacent operations that turned out fine and
are worth recording as ruled out: ROTL-by-32 (`(x<<32)|(x>>32)`,
siphash24.c's own idiom), XOR-assign and add with large constants,
global `const uint64[]` array initializers, and register-count
(variable-amount, not compile-time-constant) shifts up to 63 -- all
independently correct after the two fixes above.

sha3.c and siphash24.c were **not** unblocked by these two fixes alone,
despite being the motivating case: both still failed every single test
vector with just these two landed. sha3.c turned out to have a third,
unrelated bug (a project-wide lexer gap, not arm64-specific -- see
notes_shared_frontend_bugs.txt's "unsuffixed hex constant" entry) and
is now fixed and wired up in benchs/compcert/mkfile via a source-level
workaround. siphash24.c needed a fourth, distinct fix -- see below --
and both benchmarks are now fully wired up.

A 64-bit bitmask-immediate N-bit bug: 0xFF corrupting bits it never touched
---------------------------------------------------------------------------------

siphash24.c's SIPROUND does `v2 ^= 0xff;` on a 64-bit accumulator.
Differential tracing (see notes_debug_techniques.txt) localized the
remaining bug to exactly this line: after it, a byte in the *upper* 32
bits of v2 -- ones the source never touches -- came out corrupted too.
Several individually-tested primitives (basic 64-bit shift/rotate/add/
xor with large constants, ROTL-by-32 as its own idiom, global `const
uint64[]` array initializers, register-count shifts up to 63) all came
back correct in isolation, which is what made this one hard to spot:
it needed the *specific* combination of a small constant (0xFF) XORed
into a 64-bit destination.

Root cause, found by reading linkers/7l's raw (`7c -N`, no register
optimizer) disassembly line by line against a Python re-implementation
of SIPROUND used as ground truth: 0xFF is a genuine, self-contained
ARM64 64-bit bitmask immediate on its own (8 contiguous one-bits
starting at bit 0, no rotation needed) -- `findmask()` in linkers/7l/
bits.c correctly determines this, returning a mask with `e==64` (the
pattern requires the full 64-bit element size, since any smaller
repeating element would force the upper and lower 32-bit halves to be
identical, and they aren't: upper is all zero, lower isn't). But
linkers/7l/asmout.c's case 53 (the and/or/eor/bic-with-immediate
encoder) only set the ARM64 encoding's N bit -- which tells the
hardware "this pattern is a genuine 64-bit element, don't replicate
it" -- when the *raw constant value itself* had nonzero upper 32 bits:
`if(mask->e == 64 && ((uvlong)p->from.offset>>32) != 0) o1 |= 1<<22;`.
That extra condition is a false proxy: it happens to hold for most
large constants that need e==64, but 0xFF needs e==64 for a completely
different reason (it isn't a repeating pattern, not that it's "large")
and its upper bits are legitimately zero -- so N stayed 0, and the
hardware, seeing N=0, treated the pattern as a smaller repeating
element and replicated the low-byte value into the upper 32 bits of
the destination register too. Fixed by dropping the redundant/wrong
`(...>>32)!=0` half of the condition -- `mask->e==64` alone is exactly
the information needed, already computed by findmask() correctly.

Also hardened along the way, found while reading the surrounding code
rather than independently reproduced: isbitcon() (span.c, used by
aclass() to classify a constant during instruction selection) had a
second, latent path to the same class of bug -- a fallback that
accepts any value only expressible as a *32-bit*-replicated pattern
(`v|(v<<32)` found in the mask table even though `v` alone isn't), on
the theory that it might still be usable for a 32-bit-width
instruction. But aclass() classifies a constant without knowing which
instruction width will actually consume it, and linkers/7l/asmout.c's
own encode-time copy of this same fallback was applying it
unconditionally too -- both now require the encoding instruction to
actually be 32-bit-width (checked via asmout.c's own `s` variable,
already computed there) before trusting a 32-bit-only mask. This is
the "isbitcon() accepting oversized 32-bit bitmask immediates" item
already on this file's "what's landed vs. still open" list below,
originally scoped as needing a full isbitcon32()/isbitcon64() class
split threaded through optab.c -- landed here as a narrower fix
instead (tightening the two existing fallback call sites to check
instruction width, rather than introducing new operand classes), which
turned out sufficient for every case this session's test suite
exercises; the fuller class-split may still be worth doing for
completeness but no longer blocks anything found so far.

Verified: tests/c/regressions/arm64_bitcon_upper_bits.c (fails against
the pre-fix linker, passes after), all 21 benchs/compcert GOKENPROGS
(including sha3.c and siphash24.c) pass after the fix, confirmed via a
full clean rebuild-and-run, not just the one file that motivated
finding it -- this code path (immediate-operand AND/OR/EOR/BIC) is
exercised by any program using bitwise operators with a constant
operand, not just siphash24.c, so this had real reach across the
existing suite.

Large SB-offset load/store: dead case 47/48 finally wired up
------------------------------------------------------------------

Found chasing an arm64-only regression in three benchs/compcert
programs (nsieve.c, nsievebits.c, spectral.c): all three started
segfaulting right after commit 49e29b025 ("wire real argc/argv into
every arch's rt0.s") gave main() real parameters -- but the argc/argv
plumbing itself was a red herring. The actual trigger was that this
was the first time main() also called an external function (atoi())
from within a conditional expression; that call's mere *presence* (not
whether it ran) perturbed which order 7l's dodata() visits its symbol
hash table in, and that in turn decided whether fmt.c's small static
`fmtalloc` table landed *before* or *after* lib_core/libc/port/
minimal_malloc.c's 64MB `heap[]` array in the linked data/bss segment.
When it landed after, memset()ing into heap[] silently corrupted
fmtalloc's verb-lookup table, and the next printf() call walked off
the end of it into unmapped memory.

Root cause, once traced past the hash-order coincidence: linkers/7l/
asmout.c's case 30/31 (global-variable load/store through a `L(R)`
SB-relative operand) always materializes the target as REGSB + hi via
a single ADD-immediate (oaddi()), which can only encode ~16MB (imm12,
optionally <<12). Any symbol whose *linked* SB-offset exceeds that --
trivially true for anything placed after a >16MB global, or for
directly indexing more than ~16MB into one large array -- silently got
a wrong address, not a link error: oaddi()'s own overflow check
(`(v & 0xFFF000) != 0`) only tests bits [23:12], so a value like
0x4000000 (exactly 64MB, heap[]'s own size) has nothing set in that
narrow window despite needing bits well above it, and sailed through
as "fits directly", encoding 0 instead of erroring.

9front's own 7l already has the fix: case 30/31 checks
`if(v<0 || (v>>s) >= (1<<24)) goto Hugestxr/Hugeldxr;` and falls back
to a genuinely general form (materialize the offset via omovlit() --
which itself falls back to the literal pool for values too big to be
a plain immediate -- then a register-extended-offset LDR/STR via
olsxrr()). Goken's port turned out to already have cases 47/48 written
in this exact shape, just never reachable (case 30/31 never branched
to them) and with two of its own bugs on top: `omovlit(AMOVW, ...)`
instead of `omovlit(AMOV, ...)` (built only the low 32 bits of REGTMP
-- fine by coincidence for offsets that fit in 32 bits, but pointless
since REGTMP needs the full 64-bit value), and `olsxrr()` itself was
still a stub that unconditionally diag()'d. Three-part fix, all
verbatim-matching 9front (verified line-for-line against a local
9front checkout, not reconstructed from ARM64 docs alone):
1. linkers/7l/optab.c: add the LTO/LFROM flags to the plain-move
   (AMOVB/AMOVH/AMOVW/AMOV) C_LEXT rows -- 9front already has these;
   goken's port had them on AFMOVS's C_LEXT rows but not the integer
   ones, so span() never called addpool() for the integer case at all.
2. linkers/7l/asmout.c case 30/31: add the magnitude check + goto,
   ported verbatim from 9front.

DONE: 7l fails to link a function with ~4096+ bytes of stack-local arrays
whose address is passed to a call ("illegal combination DWORD NONE NONE LACON")
------------------------------------------------------------------------

Root cause and fix (2026-08, landed while runtime-testing the mk/rc
self-host build on real macOS/arm64 hardware -- mk.c's own functions
hit this identically, mixed with small offsets too, see below): NOT
actually an "offset too large to encode" problem despite the framing
this section originally shipped with. linkers/7l/span.c's addpool()
already resolves every C_UAUTO4K/C_UAUTO8K/.../C_LAUTO/C_LOREG (and
every other auto/oreg class) operand down to a plain integer pool
constant, via `instoffset`, which aclass() has already computed by the
time addpool() runs. C_LACON -- the class aclass() returns for
D_AUTO/D_PARAM under a "compute the effective address" context (this
file's own `aconsize:` label) -- was simply missing from that switch's
case list, so it fell through to `default: t.to = *a;`, which keeps
the ORIGINAL symbolic $var-offset(SP) operand instead of resolving it
-- and that symbolic form has no matching ADWORD optab row (only
C_VCON/C_LEXT/C_ADDR exist there), hence "illegal combination DWORD
NONE NONE LACON". Fix: add `case C_LACON:` to that same switch,
alongside C_LAUTO etc. -- confirmed against 9front's own span.c, which
already has C_LACON in that exact list (9front also adds an `offset
too large` overflow diag() there, not ported here, no repro for it
yet).

This also explains the "second local pushes the first past 4095"
framing below: that's just ONE way to land on a D_AUTO/D_PARAM operand
class of C_LACON specifically (versus one of the smaller-and-already-
handled UAUTO tiers) -- not the defining condition. Confirmed while
fixing this for mk.c: variables at small offsets (-64, -72, -88, -112,
-344 bytes) hit the identical "illegal combination DWORD NONE NONE
LACON" error alongside a genuinely large one (-52000 bytes) in the same
build, all fixed by the same one-line addition. This also unblocks
utilities/files/mv.c and utilities/kernel/data2s.c on arm64 (not
re-verified here -- this round's own verification was scoped to mk/rc,
see notes_libc_selfhost.txt).

How this was originally found and minimized (kept for the repro; the
"12-bit immediate limit" theory in the last paragraph below is
superseded by the actual root cause above -- C_LACON's magnitude was
never the issue, only whether aclass() returned that class at all):

Found while porting utilities/files/mv.c against the self-hosted libc
(unrelated task -- retrying it after unblocking cleanname()/EQ):
compiles fine under 7c, but 7l fails with

    __fmtunlock: illegal combination DWORD NONE NONE LACON
    (0)	DWORD	,$toname-4096(SP)

(the function name in the error is whatever symbol happens to be
resolving nearby at that point in the link, not the actual offending
one -- misleading, don't chase it literally). Minimized from mv.c's
mv1() (two `char[4096]` locals, `toname`/`fromname`, and a `memcmp()`
call taking `toname`'s address) down to a clean 8-line repro:

    void
    main(void)
    {
    	char toname[4096], fromname[4096];
    	toname[0] = 'a';
    	toname[1] = '\0';
    	print("%d\n", memcmp(toname, "a", 1));
    	exits(nil);
    }

A SINGLE 4096-byte local (no second buffer) does NOT trigger it --
tried first, linked fine -- so this isn't simply "any 4096-byte
array"; it's specifically about the STACK FRAME OFFSET at which the
address-taken local ends up landing once other locals are stacked
above/below it, consistent with ARM64's 12-bit unsigned immediate
limit on the ADD-from-SP addressing mode 7l uses to materialize a
stack-local's address (max encodable offset 4095) -- `toname` alone at
a small offset stays under that; with `fromname` also present, the
combined frame pushes `toname`'s own offset (-4096 in the repro, -4116
in the real mv.c) just past it. 7l's instruction selection has no
fallback (load the offset into a scratch register first, then add) for
this specific "DWORD NONE NONE LACON" addressing-mode combination when
computing the address of a stack local for a function-call argument.
Not investigated further (which pass emits the un-encodable form, or
what the correct 7l fix looks like) -- out of scope for the mv.c
porting task that found it. Affects amd64 too? Not checked -- the
repro above links fine on 6c/6l, so this looks arm64 (7l)-specific,
not a general "large stack frame" gap in every backend.
