m68k (2l/2a/2c): ELF HEADTYPE-7 wiring + exit_linux_m68k.s, first real bring-up
================================================================================

Unlike sparc's kl (see notes_arch_sparc.txt), 2l's `mk objtype=boot-gcc`
already compiled cleanly BEFORE this session (from the earlier "m68k: make
2l compile" / "m68k: add 2l in toplevel mkfile" commits) -- but that only
got the linker's OWN sources building, not producing any real Linux ELF
output. This session added that: HEADTYPE 7 wiring (matching every other
HEADTYPE-7 arch) plus a real hand-assembled exit(42) test verified under
qemu-m68k end-to-end. See linkers/2l/, assemblers/2a/, tests/s/exit/
exit_linux_m68k.s.

2l had no ELF support at all, same underlying gap as kl had
-----------------------------------------------------------------

2l/l.h never included "../lk/elf.h", and 2l/asm.c had only a bare `lput`
(no cput/wput/wputl/lputl/strnput/llput/llputl) -- 2l's own byte-output
convention is the CPUT(c) macro (`*cbp++ = c; if(--cbc<=0) cflush();`)
used inline everywhere rather than through named functions, so none of
elf.c's expected function names existed at all, not even by a different
name. 2l/obj.c's HEADTYPE switch only covered 0 (garbage unix)/1 (plan9
boot, data-in-text)/2 (plan9)/3 (NeXT boot, real Mach-O for 68040 --
confirmed by the 0xfeedface magic and segment/section command layout in
asm.c's case 3, matching NeXTSTEP's mach_header, not to be confused with
macOS's own later, different-arch Mach-O)/4 (pilot preprocess). No case 7.

Ported the same HEADTYPE-7 machinery already established for every other
Linux-targeting arch (elf32(M68K, ELFDATA2MSB, ...) -- m68k is big-endian):

- 2l/l.h: added `#include "../lk/elf.h"`; added `EXTERN long INITTEXTP`;
  retyped `lput`'s prototype long->int32 (matching every sibling linker,
  the same "long is 64-bit on this LP64 host" parity fix already applied
  elsewhere) and added cput/wput/wputl/lputl/llput/llputl/strnput
  prototypes.
- 2l/obj.c: added a `-P` flag (INITTEXTP, mirrors -T/-D/-R/-H already
  there) and the `if(INITTEXTP==-1) INITTEXTP=INITTEXT;` default after
  the switch; added `case 7:` with the standard HEADTYPE-7 sizing
  (HEADR=rnd(Ehdr32sz+3*Phdr32sz,16), INITTEXT default 0x00400000+HEADR,
  INITRND 4096).
- 2l/asm.c: added cput/wput/wputl/lputl/llput/llputl/strnput as thin
  wrappers around the existing CPUT macro (matching this file's own
  byte-at-a-time style rather than the LPUT-macro style kl/vl use);
  retyped lput long->int32; added `case 7:` to both mid-function seek()
  switches (matching elf32()'s own page-rounded PT_LOAD offset math,
  `rnd(HEADR+textsize,INITRND)`) and to the final header-write switch,
  guarding `debug['S']=1` with `if(!debug['s'])` from the start --
  applying ql's own later-learned lesson (see notes_arch_power.txt) up
  front rather than rediscovering the .data-corruption bug this session,
  same as kl's own bring-up did.
- 2l/mkfile: added `elf.$O` to OFILES (it compiles linkers/lk/*.c files
  generically via the `%.$O: ../lk/%.c` rule already present, but elf.$O
  was never actually listed as a real dependency, so `mk` never linked
  it in -- the build failed with "undefined reference to elf32" until
  this was added). Also fixed a stale `enam.c: $TOP/include/obj/z.out.h`
  dependency (copy-paste leftover naming alpha's z.out.h instead of this
  arch's own 2.out.h -- harmless for a fresh build since mkenam itself
  already correctly reads 2.out.h, but meant `mk` never noticed when
  2.out.h changed and wouldn't regenerate enam.c).

exit_linux_m68k.s: real ELF exit(42), verified under qemu-m68k
------------------------------------------------------------------

Wrote tests/s/exit/exit_linux_m68k.s and wired it into that mkfile's
EXITLINUXBINS + scripts/qemu-runner (`m68k) qemu=qemu-m68k`), same shape
as every other arch's exit(42) test.

Linux m68k syscall ABI (confirmed against a real glibc checkout found on
this machine, sysdeps/unix/sysv/linux/m68k/sysdep.h, and its bundled
m68k-linux-any/asm/unistd_32.h kernel header): syscall number in %d0,
args in %d1-%d5/%a0, trap via `trap #0`, errors signaled by a return
value in -4095..-1 rather than a separate carry-style flag. __NR_exit is
1, the same legacy/x86-style numbering every other arch in this session's
bring-ups has used.

This backend's assembler (assemblers/2a/lex.c) names the data registers
R0-R7 (not D0-D7) and address registers A0-A7 -- but unlike sparc's kl,
there is no renaming/flat-numbering indirection: these map straight onto
the real hardware d0-d7/a0-a7 registers, since m68k has no windowed-
register complication to abstract away. ATRAP's optab row (linkers/2l/
optab.c: `{ATRAP, AXXX, 0, 0, 30, 0x4e40}`) requires a D_CONST operand
(asm.c's case 30: `t |= p->to.offset & 0xf`), directly ORing the trap
vector into the base 0x4e40 (`trap #0`) opcode -- so `TRAP $0` assembles
to exactly the instruction Linux needs, no scratch-register workaround
required (unlike kl's TA, which only has a register-operand form -- see
notes_arch_sparc.txt).

Verified: `2a -c` + `2l -H7` produce a genuine 32-bit big-endian m68k ELF
(readelf confirms "Motorola m68k, 68020", ELFDATA2MSB, entry point set
correctly), `qemu-m68k ./exit_linux_m68k.exe` exits 42 on the first try
(no register-mapping puzzle to work through, unlike sparc's TA). Full
tests/s suite re-run afterward with m68k included: no regressions.

tests/s/mini/hello_linux_m68k.s: A6/static-base addressing, first try
------------------------------------------------------------------------

Follow-up session (same "do the same tests/s/mini bring-up" request
already applied to sparc): wrote tests/s/mini/hello_linux_m68k.s
(write()+exit(), the standard hello-world shape) and wired it into that
mkfile's LINUXBINS. Passed on the FIRST assembly/link/run attempt.

This exercises A6-relative addressing, m68k's counterpart to sparc's
REGSB (see notes_arch_sparc.txt): `MOVL $a6base(SB), A6` bootstraps A6
to `INITDAT+A6OFFSET` (A6OFFSET=32766, l.h) -- the exact idiom already
used, unmodified, by assemblers/2a/l.s's own "start" routine (a real,
working reference bundled with this port since the original import).
`LEA msg(SB), A1` then computes msg's real address: asmea()'s bare
D_STATIC/D_EXTERN case (linkers/2l/asm.c) encodes `msg(SB)` used WITHOUT
a `$` prefix as a signed 16-bit displacement off A6 (`sym->value +
offset - A6OFFSET`), so LEA resolves it to A6 + displacement =
`INITDAT + msg's data-segment offset` -- the real address, without ever
dereferencing (LEA's whole purpose). The address then has to move from
address register A1 into a data register (`MOVL A1, R2`) before the
syscall trap, since the raw Linux syscall ABI takes all five register
args in the data registers (%d1-%d5), never the address registers.

Note there IS a simpler alternative this test deliberately did NOT use:
`MOVL $msg(SB), R2` (WITH the `$`) hits asmea()'s I_ADDR|D_STATIC/
D_EXTERN case instead, which embeds msg's absolute address directly as
a 32-bit immediate -- no A6 or LEA needed at all. That form works too,
but going through A6/LEA instead was the deliberate choice here, to
actually exercise the SAME addressing convention 2c-generated code (and
the SB-relative convention every other HEADTYPE-7 arch's own hand-tests
already exercise) would really use for ordinary small-offset data
references, rather than taking the simpler-but-different absolute-
immediate shortcut.

Verified: `2a -c` + `2l -H7` build a working ELF, `qemu-m68k
./hello_linux_m68k.exe` prints "Hello, world" byte-matching
hello.expected.txt, full tests/s suite and top-level `mk test` re-run
afterward with m68k included in tests/s/mini's LINUXBINS: no
regressions.

2c: getting it to compile, link, and pass tests/c/mini
========================================================

Follow-up session, same shape as kc's own bring-up (notes_arch_sparc.txt):
compilers/2c/mkfile had already been ported to the modern
`<$TOP/mkfiles/$objtype/mkfile` style by the time this session started
(superseding this file's earlier claim above that it was still a stale
Plan-9-native mkfile -- that part is done), and 2c almost compiled under
`mk objtype=boot-gcc`. Two real bugs remained, the SAME class kc hit:

- swt.c's align()/maxround() were `long`-typed against cc.h's `int32`
  prototypes (identical mismatch to kc's own swt.c) -- fixed the same
  way, matching cc.h exactly.
- swt.c's outlstring() took `ushort*` and wrote 2 bytes/rune, but cc.h
  declares `long outlstring(TRune*, long)` and every OTHER arch's rune
  handling goes through cck/pswt.c's shared TRune*-based outlstring (4
  bytes/rune, TRune=Rune=unsigned int, see cck/cc.h). 2c doesn't pull in
  cck/pswt.c at all (OFILES has no pgen.$O/pswt.$O, unlike kc/7c/qc/...)
  -- it's a self-contained, older ("cc2"-generation) compiler with its
  own doswit/casf/nullwarn/ieeedtod, genuinely different from the
  cck-sharing archs, not just a stale duplicate. So the fix was NOT
  "wire in the shared version" (that would need a `g` register-variable
  parameter threaded through doswit/swit1 too, real surgery) but to fix
  outlstring's own signature+body in place to match cc.h's TRune* width,
  same shape as cck/pswt.c's version but living locally in 2c/swt.c.
- gc.h's `EXTERN int multabsize;` (mul.c's own multiply-strength-
  reduction table size, `int multabsize = sizeof(multab)/sizeof(multab[0]);`)
  hit the exact same EXTERN-vs-extern duplicate-definition bug kc's
  hintabsize did -- same fix, `extern int multabsize; // defined in
  mul.c`.

Also found and fixed, all copy-paste-vintage bugs predating this
session, same class as sparc's stale mkfiles/sparc/mkfile
(notes_arch_sparc.txt):

- mkfiles/mkfile.proto's CPUS list said `68020`, not `m68k` -- the name
  every OTHER file in this port (compilers/2c, assemblers/2a, tests/s/
  exit/exit_linux_m68k.s, tests/s/hello_arch/hello_linux_m68k.s, ...)
  actually uses. Fixed to `m68k`.
- mkfiles/m68k/ existed as an empty directory (no mkfile at all) --
  `mk objtype=m68k` couldn't work. Created mkfiles/m68k/mkfile modeled
  directly on the now-fixed mkfiles/sparc/mkfile: O=2, CC=2c, LD=2l -H7,
  AS=2a, CFLAGS -I$TOP/include/arch/m68k.
- `thestring` (this port's own arch-name string, used to build default
  library search paths) was hardcoded to the Plan-9-original `"68020"`
  in THREE places -- compilers/2c/txt.c, assemblers/2a/lex.c, linkers/
  2l/obj.c -- inconsistent with everything else already using `"m68k"`.
  Fixed all three to `"m68k"`.

2l had NO `-L` library-search-path support at all -- a real, load-bearing gap
---------------------------------------------------------------------------------

Unlike kl (which already got a modern `libdir[]`/`addlibpath()`/
`findlib()` mechanism during its own HEADTYPE-7 bring-up, apparently
ported in at the same time as the ELF work described earlier in this
file), 2l's `addlib()` -- the function that resolves a C source's
`#pragma lib "libmini.a"` reference at link time -- still used ONLY the
original, older Plan-9 mechanism: an object file's own embedded
"history" of compile-time include-path components (`histfrog[]`,
populated from ANAME records the assembler/compiler wrote into the .2
file), falling back to a HARDCODED `/m68k/lib` (or `/usr/2lib`) system
path whenever that embedded history didn't start with `/` or `.`.
`tests/c/mini`'s own `helloc.c` (`#pragma lib "libmini.a"`, no leading
`/` or `.`) hits exactly that fallback branch, and `2l -L. ...` silently
ignored `-L` entirely -- there was no `case 'L':` in 2l/obj.c's
ARGBEGIN at all. Result: "cannot open file: /68020/lib/libmini.a" (before
the thestring fix above) / "/m68k/lib/libmini.a" (after it) -- neither
existing on this machine, since the whole point of `-L.` is to point at
the just-built libmini.a sitting in the test's own working directory.

Fixed by porting kl/obj.c's own `-L`/`addlibpath()`/`findlib()` addition
into 2l/obj.c verbatim (same global shapes: `char** libdir`, `int
nlibdir`, `static int maxlibdir`, no l.h EXTERN needed -- kl doesn't
EXTERN them either, they're plain file-scope globals) plus a `search`
flag in `addlib()`: when the embedded history doesn't start with `/` or
`.`, try `findlib()` against the `-L`-supplied directories first,
falling back to the plain relative name (still checked against
`library[]` for dedup) if nothing matches -- exactly kl's own fn1/fn2/
search logic, adapted to 2l's own single-buffer `name[]` convention. Also
added the matching `addlibpath`/`findlib` prototypes to l.h (kl has
these too) since 2l/obj.c calls `addlibpath` from ARGBEGIN, textually
BEFORE its own definition further down the file, which gcc flags as a
conflicting-implicit-declaration warning without a prototype in scope
first.

tests/c/mini m68k bring-up: passed end-to-end on the FIRST try
------------------------------------------------------------------

`2c -S` on a hand-written two-arg function confirms this backend's own
calling convention empirically: UNLIKE kc/qc/7c/etc's register-based
first-arg convention (REGARG), 2c passes BOTH args on the stack
(`buf+0(FP)`/`count+4(FP)`) and returns in R0 (D0) -- much closer to a
textbook m68k C ABI, since args are PEA'd (pushed) by the caller and the
callee reads them FP-relative, matching real hardware stack-based
calling conventions rather than any register-window trick.

start_m68k.s/xwrite_m68k.s/xexit_m68k.s modeled directly on tests/s/
hello_arch/hello_linux_m68k.s's already-verified A6/a6base setup and
tests/s/exit/exit_linux_m68k.s's already-verified syscall convention
(d0=syscall#, d1-d5=args, `trap #0`). Unlike sparc's kc bring-up (three
real runtime bugs, all from REGSP=%g1 having no relation to any real
hardware register -- see notes_arch_sparc.txt), NONE of that class of
problem exists here:

- _start's `BSR main(SB)` is a genuine hardware call instruction that
  pushes/pops the real %sp (%a7) automatically -- no fake "REGSP" to
  initialize by hand, no auto-prologue-vs-hand-written-setup ordering
  puzzle to work around (2l's own auto-inserted frame setup, if any,
  never touches a register this file also needs to initialize first).
- xwrite_m68k.s's syscall clobbers R0/d0 with the syscall number, but
  R0/d0 is ALSO where 2c expects the C-level return value AND where the
  Linux syscall ABI already places the raw return value -- so unlike
  xwrite_sparc.s (whose REGSP/%g1 collision needed an explicit save-
  before/restore-after), the "collision" here is actually a coincidence
  that works in this stub's favor: the syscall's own return value in d0
  IS exactly the value 2c's caller-side convention expects, no extra
  move needed.

Verified: `mk objtype=boot-gcc` builds and installs 2c/2a/2l cleanly
from a clean tree; tests/c/mini's m68k target builds and passes byte-
exact under qemu-m68k (`Hello C World` / `It works!`, matching
helloc.expected.txt) on the first assembly/link/run attempt, both via
`mk objtype=m68k` directly and `mk test`'s full per-arch loop (ARCHS=
... m68k, clean rule's glob extended to include `2`); full top-level
`mk test` (tests/s) and tests/c/mini's own `mk test` across ALL other
arches (386/amd64/arm/arm64/mips/riscv/alpha/power/sparc) re-run
afterward with no regressions from the libmach/2l/mkfile.proto changes.
