Self-hosting a real libc.a: lib_core/libc/{fmt,port,syscall,arch}/, Linux + darwin/arm64 + darwin/amd64
==========================================================================================================

Notes on building a genuinely reusable, self-hosted C library --
lib_core/libc/, producing libc.a -- compiled entirely by goken's own
Xc/Xa/Xl toolchain (not gcc/clang), as opposed to every prior test in
this tree, which either links no library at all (tests/c/mini/) or
links against a hand-rolled, per-test assembly stub duplicated in each
test directory (tests/c/mini2/linux_$arch.s, tests/c/vlong/vlrt.c+
print.c). Linux: arm64, amd64, mips, riscv, riscv64, 386, and arm are
all done -- every arch this project's toolchain targets on Linux.
darwin: arm64 done too now (July 2026), the first non-Linux GOOS --
see its own section below. The directory layout (lib_core/libc/{os,arch,
syscall}/ split by $OS and $cputype) was built to make adding archs
additive, and stayed that way through all seven Linux arches; the same
discipline carried over to adding darwin as a second GOOS, with one
correction along the way (see "svc.s turned out not to be
OS-independent" below): verify every ABI claim empirically for the
new target (via `Xc -S` probes *and real execution*, not -S alone -- see below)
rather than assuming it matches an existing one. No two arches here
actually agree on every axis: arm64/mips/arm/riscv share register-
passing for the first arg, amd64/386 don't; arm64/amd64 share
uniform-8-byte slot width, mips/arm/386/riscv share natural-packing
instead; riscv alone additionally needs an 8-byte-alignment rule none
of the others have; 386/arm agree with mips on natural-packing but
(being little-endian, unlike mips) need little-endian sub-word
placement instead of mips's big-endian one.

Read docs/claude_notes/notes_arch_{amd64,mips,riscv,x86,arm}.txt's own
relevant sections for the full per-arch ABI write-ups (calling
convention, varargs slot layout); this file is the cross-cutting
design story and the bugs found along the way that weren't purely
arch-specific.

Why this exists: fmt/*.c wants a real libc, not a per-test stub
------------------------------------------------------------------------

lib_core/libc/fmt/*.c (Plan9's real, portable printf implementation)
is byte-identical to BOOT/lib9/fmt/*.c (symlinked, so gcc's BOOT build
and goken's own self-hosted build share one copy of the source) -- the
goal was to get goken's own Xc compilers to build *that*, plus enough
Linux syscalls (write, exit) to actually run a program, rather than
keep writing one-off minilibc stubs per test. tests/c/mini2/linux_$arch.s
and tests/c/vlong/vlrt.c+print.c stay exactly as they are; this is
purely additive infrastructure alongside them, not a replacement.

Hard constraint carried through every file added here: lib_core/ code
may only #include headers under include/, never a Unix/host header
directly (that's lib9/'s privilege, not lib_core/'s) -- see
include/arch/$cputype/u.h's own header comment on every arch.

Directory layout
------------------

    lib_core/libc/
      fmt/, utf/, math/     -- portable (symlinked from BOOT/lib9/{fmt,utf})
      port/                 -- portable, but goken-only (memmove.c,
                                strlen.c, ctype.c, vlrt.c, ... -- either
                                copied from ~/principia/lib_core/libc/port/
                                verbatim, preserving syncweb markers, or
                                new but OS/arch-independent)
      arch/$cputype/rt0.s   -- process startup (_main), one per arch
                                -- but NOT unconditionally OS-independent;
                                darwin/amd64 needs its own
                                arch/amd64/rt0_darwin.s, see "rt0.s
                                needed a GOOS-specific override too"
                                below. RT0OFILE in this mkfile picks
                                which one, same override mechanism as
                                CFLAGS_EXTRA.
      syscall/os/$OS/svc_$cputype.s      -- the *one* raw syscall
                                             trampoline per (OS, arch)
                                             pair (NOT arch-only -- see
                                             "svc.s turned out not to
                                             be OS-independent" below)
      syscall/os/$OS/*.decl              -- declarative syscall specs
      syscall/os/$OS/numbers_$cputype.h  -- syscall number constants
      syscall/os/$OS/zsyscall_$OS_$cputype.c -- generated (see below);
                                             committed to the repo

This $OS/$ARCH split (and the arch/$cputype/rt0.s + syscall/os/$OS/
naming specifically) traces back to how GO/pkg/runtime is laid out in
this same repo's own Go-era snapshot: GO/pkg/runtime/{linux,darwin,
...}/{amd64,386,arm}/{rt0.s,sys.s} -- confirmed by direct comparison
while bringing up darwin/amd64 (see below): GO/pkg/runtime/darwin/
amd64/sys.s uses the exact same `0x2000000`-prefixed BSD syscall
numbers this project's own svc_amd64.s independently converged on, and
GO/pkg/syscall/asm_darwin_amd64.s the same DI/SI/DX/R10/R8/R9 argument
registers and bare SYSCALL trap. The `//sys name(args) (ret) =
SYS_NAME` decl convention and scripts/mksyscall.sh are likewise
modeled on GO/pkg/syscall/mksyscall.sh and that package's own `//sys`
comments. Interestingly, that old Go snapshot's linux/amd64/rt0.s and
darwin/amd64/rt0.s are byte-identical ("Darwin and Linux use the same
linkage to main") -- true for Go at the time because 2010-era Darwin
executables used the static LC_UNIXTHREAD entry (kernel jumps straight
to your code, argc/argv already on the stack, exactly like Linux; see
docs/claude_notes/notes_exec_macho.txt's own account of why that
approach is dead on today's arm64 kernel). This project's own -H6 work
moved to the modern LC_MAIN/dyld-calls-you-with-registers convention
instead, something that old Go snapshot never had to handle (Apple
Silicon didn't exist in 2010) -- which is exactly why arch/$cputype/
rt0.s's original "one file, every GOOS" assumption, itself inherited
from that same old Go precedent, turned out not to survive amd64's
bring-up. Go wasn't wrong for its era; the ground moved.

include/arch/$cputype/u.h holds each arch's base scalar typedefs plus
va_list -- adapted from ~/principia/lib_core/libc/{arm,mips}/u.h and
include/arch/{arm,386}/u.h where an arch's own file already exists
there (mips's is copied close to verbatim; amd64 has no principia
equivalent, since principia never had an x86-64 arch, so it was built
fresh by empirical `6c -S` probing, following the same structure).
Trimmed relative to principia's fuller versions -- no Rune/jmp_buf/
mpdigit/FCR-FSR flags yet, since nothing under lib_core/libc uses them
so far; add them, matching principia's shape, when something does (the
user's stated intent is to eventually sync these files with principia
via syncweb the way mk/rc/the arm toolchain/utilities/ already are, so
staying close to principia's existing shape now, rather than
inventing a divergent one, is deliberate).

riscv/riscv64 have no principia or 9front equivalent to draw from at
all (see plan9front.txt's "riscv" section) -- their u.h files are
instead adapted from ~/xxx/miller-riscv/ROOT/{riscv,riscv64}/include/u.h
(Richard Miller's Plan9 riscv port), credited there. Same "adapt, don't
blindly trust" discipline applied: miller-riscv is a different,
independently-implemented compiler, so every va_start/va_arg claim
from it was re-verified against this project's own ic/jc -S output and
real qemu execution -- worth doing even when a seemingly-authoritative
reference exists, since it caught a genuine, riscv64-specific bug (see
below) that a straight copy would have carried over silently (miller's
own u.h actually gets it right; the bug was in an early draft of
*this* project's adaptation, not in the source being adapted from).

Declarative syscalls, Go-`mksyscall.sh`-style
------------------------------------------------

Per explicit design direction: a small `//sys name(args) (ret) =
SYS_NAME` comment spec (syscall_$OS_$cputype.decl), in the spirit of
GO/pkg/syscall/mksyscall.sh, parsed by scripts/mksyscall.sh (POSIX
sh+awk, matching this project's existing script-language convention --
no new language dependency) into a generated C file
(zsyscall_$OS_$cputype.c) with one thin wrapper per syscall, each just
calling a single generic `_syscall6(num, a1..a6)` trampoline (mirroring
Go's own Syscall6: always lower to the widest arity, pad unused
argument slots with 0, rather than one hand-written asm entry point
per syscall or per arity). Adding a syscall is then a one-line .decl
addition, no new assembly, *except* on mips, where a syscall needing a
5th/6th argument would need svc.s itself extended (see
notes_arch_mips.txt) -- not needed yet since only write/exit are
wired up.

Three arches need a variant of the generic wrapper shape: riscv64's,
arm64's, and amd64's `long` is only 4 bytes (see below and the
"vlong" section further down -- this was originally believed to be a
riscv64-only quirk, and wasn't, see that section for the correction),
so a pointer argument cast through the default `(long)` would
truncate before ever reaching _syscall6. scripts/mksyscall.sh takes an
optional 2nd positional argument (the cast type, default "long") for
exactly this -- lib_core/libc/mkfile passes "vlong" for riscv64/
arm64/amd64's generation rule (any arch where SZ_IND > SZ_LONG in that
arch's compilers/*c/gc.h). Deliberately a positional argument, not an
environment variable: this project's rc
(rc/unix.c) has a no-op Updenv(), so a `VAR=val cmd`-shaped mkfile
recipe silently fails to actually set the variable in the environment
a forked subprocess (like this script, or its own awk) sees -- a
positional argument has no such dependency and was not worth
re-verifying whether the bug still applies.

zsyscall_*.c is deliberately committed to the repo, unlike most
generated files in this tree (.gitignore excludes y.tab.[ch], for
instance) -- see lib_core/libc/mkfile's own comment on the generation
rule for the full rationale (small reviewable glue code; and once
syscall numbers stop being hand-written and start getting scraped from
each target OS's own kernel headers, generating this file will require
a host of that OS, so committing the output is what lets goken
cross-compile for an OS you don't have).

darwin/arm64: a second GOOS, and the vlong bug it exposed
------------------------------------------------------------

Added July 2026, on the strength of -H6 Mach-O output already working
(docs/claude_notes/notes_exec_macho.txt) and the user's own machine being
macOS arm64. Verification: lib_core/libc && mk 'objtype=arm64'
'cputype=arm64' 'GOOS=darwin' install, then tests/c/hello_libc's
test_macos_arm64 target (mk 'objtype=arm64' 'cputype=arm64'
test_macos_arm64) -- no qemu involved, this actually executes the
Mach-O binary on the real host, ad-hoc signed via scripts/macos-codesign.

GOOS is a real mk variable now, not a hardcoded "linux" throughout
lib_core/libc/mkfile: it defaults to linux (every existing caller
relies on this, unchanged behavior) and both lib_core/libc/mkfile
itself and tests/c/hello_libc/mkfile's test_macos_arm64 target pass
'GOOS=darwin' explicitly, positionally on the mk command line -- same
"rc's Updenv() is a no-op" reasoning as scripts/mksyscall.sh's own
cast-type argument above, not a coincidence: it's the same class of
footgun this codebase has already been bitten by once. Watch the `${GOOS}`
vs `$GOOS_` distinction in any path built by concatenating GOOS directly
against another variable with an underscore (e.g. zsyscall_${GOOS}_$cputype.c) --
`$GOOS_$cputype` silently parses as the variable named "GOOS_" (undefined,
empty) followed by $cputype, not as "$GOOS" + "_" + "$cputype". Caught during
this work because the mkfile's own SYSCALLOFILES referenced a file
that then failed to resolve ("mk: don't know how to make
'syscall/os/darwin/syscall_arm64.decl'" -- note the missing "darwin_"
in that message, the tell).

darwin/arm64's raw syscall convention (lib_core/libc/syscall/os/darwin/
numbers_arm64.h, svc_arm64.s) differs from linux/arm64's in exactly the
two ways already documented in notes_exec_macho.txt from the -H6
bring-up: the syscall number goes in R16 (not R8), and the trap is
SVC $0x80 (not SVC $0, which on Darwin is a different, Mach, trap
table). BSD syscall numbers, no class prefix (that's an amd64/x86
Darwin quirk, not an arm64 one). Everything else about the trampoline
-- args in R0-R5, num arriving in the caller's R0 unspilled, the whole
FP-vs-register story -- is a plain AAPCS64 calling-convention fact and
so is identical to linux/arm64's, confirmed by reusing arch/arm64/rt0.s
completely unmodified for both GOOSes (see "Directory layout" above).

svc.s turned out not to be OS-independent
--------------------------------------------

The original (Linux-only) directory layout put svc.s under
syscall/arch/$cputype/, i.e. one trampoline per arch, implicitly
assumed to be reusable across any future OS. Adding darwin/arm64
proved that assumption wrong immediately (see the register/trap
differences above), so svc.s moved to syscall/os/$OS/svc_$cputype.s --
one per (OS, arch) pair, alongside the other already-per-OS files
(numbers_$cputype.h, *.decl, zsyscall_*.c) it always logically
belonged next to. This was a pure `git mv` for all seven existing
Linux arches (386, amd64, arm, arm64, mips, riscv, riscv64) plus a
path fixup in their own header comments and lib_core/libc/mkfile's
SYSCALLOFILES/generation rule -- re-verified byte-for-byte unchanged
by rebuilding+relinking all seven afterward (see "Verification" below
for the caveat about not having qemu/Docker available to *run* six of
those seven during this particular session).

The pointer-truncation bug this exposed (arm64, and amd64 too)
-------------------------------------------------------------------

hello_libc's first real run on macOS printed nothing (exit 0, no
output) -- the exact "silently wrong, not crashed" symptom
notes_exec_macho.txt already warns about. lldb tracing (breakpoint on
the SVC instruction's address, not by symbol -- 7l's -H6 output has no
symbol table, see that file's own debugging section) showed write()'s
x0/x1/x2 arguments full of garbage in their upper 32 bits: e.g. fd=1
arrived as x0=0x100000001.

Root cause: this compiler defines `long` as 4 bytes on *every* arch
(SZ_LONG in compilers/*c/gc.h -- checked all seven: 386/arm/mips/riscv
have SZ_IND==SZ_LONG==4 too, genuinely fine, but arm64 and amd64 both
have SZ_IND=8 with that same SZ_LONG=4). _syscall6's prototype declared
its args as plain `long`, so `(long)buf` in the generated
zsyscall_*.c wrapper truncated a real 8-byte pointer to 4 bytes before
it ever reached the outgoing-call stack slot -- confirmed via `7c -S`:
the compiler correctly computes and sign-extends the value into a
64-bit register (`sxtw x9, w0`), then legitimately stores only the low
32 bits of it (`MOVW`, not `MOV`) into the argument's 8-byte-strided
stack slot, per its own (undersized) idea of the value's type. Not a
compiler bug -- 7c is behaving correctly relative to `long` genuinely
being 4 bytes here; the bug was in lib_core/libc's own choice of `long`
for _syscall6's prototype. The upper 4 bytes of each 8-byte slot are
simply whatever was already on the stack, never written. This is
*exactly* riscv64's already-known-and-fixed bug (see the "vlong" section
above), just never recognized as applying to arm64/amd64 too -- the
prior write-up's claim that "every other arch's `long` is already
pointer-wide" was empirically wrong for these two, just never caught
because nothing had actually run natively and looked at real (non-luckily-
zeroed) stack contents until this darwin bring-up. It silently existed
in linux/arm64's and linux/amd64's hello_libc this whole time too --
masked because a fresh Linux process stack happens to be zeroed in
exactly the region these outgoing-argument slots land in this early in
program execution, while macOS/dyld leaves real garbage there. Same
"Linux got lucky, macOS didn't" shape as the *unrelated*, already-
documented xwrite-stub bug in notes_exec_macho.txt -- a second,
independent instance of that general failure mode, not the same bug
recurring.

Fix: arm64 and amd64 now get the same treatment riscv64 already had --
scripts/mksyscall.sh's vlong argtype, and `vlong a1..a6` in their
_syscall6 prototype (syscall_$OS_$cputype.h) instead of `long`. Verified
via `7c -S` before/after: every outgoing-argument store for write()/exit()
changed from MOVW (32-bit) to MOV (64-bit); rebuilt+relinked and
confirmed hello_libc prints correctly on real macOS arm64 afterward.
amd64's linux/hello_libc could not be executed to confirm the runtime
fix on this session's host (no qemu-x86_64, no working Docker daemon --
see "Verification" below) -- the fix was applied there on the strength
of the identical root cause (SZ_LONG=4, SZ_IND=8, same `(long)buf`
truncation site, confirmed via `6c -S`), not from an observed amd64
failure of its own. mips/riscv/386/arm are genuinely unaffected
(SZ_IND==SZ_LONG==4 for all four) and keep the plain `long` prototype.

A second, unrelated build-hygiene footgun surfaced while testing this:
mksyslib's `$AR rc $LIBNAME $prereq` merges into whatever local libc.a
intermediate archive is already sitting in lib_core/libc/ instead of
starting fresh. Switching cputype or GOOS between builds without an
intervening `mk clean` (or, worse, a `clean` whose own `*.$O` glob only
matches the *current* $O suffix, so it never removes a differently-
suffixed stale object from a previous arch) leaves iar merging
incompatible members and failing with "inconsistent object file" --
and since $OFILES don't change between a linux and darwin build of the
same cputype, mk's own timestamp-based staleness check then considers
the already (possibly corrupt) installed $LIB up to date and skips
rebuilding it, silently linking against stale bits. tests/c/hello_libc/
mkfile's test_macos_arm64 target works around this with an explicit
`rm -f libc.a` plus `mk -a` (force) before every install -- not fixed
in mksyslib itself (shared by every library in the tree, most of which
never vary GOOS/cputype in a single session the way this one now does,
so a broader fix there wasn't attempted this pass).

Also fixed in passing: numbers_arm64.h, syscall_darwin_arm64.h, and
all seven of the just-moved svc_$cputype.s files' sibling .decl/.h
comments had a couple of stale `syscall/arch/$cputype/svc.s` path
references left over from the move above -- caught by grepping for the
old path across syscall/, not by a build failure (a comment typo, not
a code bug).

darwin/amd64: a fourth combination, tested via Rosetta 2 on Apple Silicon
---------------------------------------------------------------------------------

Added right after darwin/arm64, same session's later half. Verification:
lib_core/libc && mk 'objtype=amd64' 'cputype=amd64' 'GOOS=darwin'
'CFLAGS_EXTRA=-z' 'RT0OFILE=arch/amd64/rt0_darwin.6' install, then
tests/c/hello_libc's test_macos_amd64 and benchs/compcert's
test_goken_macos_amd64 -- both run the real Mach-O binary directly via
Rosetta 2 (`arch -x86_64 /usr/bin/true` confirms it's installed; no
extra setup needed once it is) since this session's host is Apple
Silicon, not a real x86_64 Mac. Three new things showed up that
darwin/arm64 didn't need, in the order they were found:

1. -H7 is not optional for the *existing* Linux path either. 6l/7l/8l
   (unlike vl/il/jl, which always default to ELF) fall back to the
   host's own compiled-in GOOS when no -H flag is given at all
   (linkers/{6,7,8}l/obj.c's HEADTYPE==-1 case) -- so tests/c/hello_libc/
   mkfile's hello.exe rule, which had never passed -H7 explicitly,
   silently built a Mach-O (not ELF) on this Darwin host. arm64 never
   exposed this (7c has no non-PIE-unsafe codegen path at all, so a
   stray implicit Mach-O still linked and ran fine there), but amd64
   immediately hit point 2 below and failed outright. Fixed by adding
   -H7 unconditionally to that one rule; re-verified the resulting
   binaries are real ELF for all seven Linux arches (`file` on each),
   not just compile-and-link success, since compile-and-link succeeding
   is not proof of the right output format (this is exactly how the
   386/arm ones would have silently mis-built too: 8l defaults to Plan 9
   format absent -H7, on this host or any non-Linux one; 5l defaults to
   Plan 9 unconditionally, regardless of host).

2. -z has to reach *every* 6c compile that ends up in the final
   binary, not just the test program's own. 6l -H6 is always PIE, but
   plain 6c folds a symbol's address into an instruction as an absolute
   immediate (e.g. fmt/fmt.c's fmtalloc, used for a CMPQ bounds check)
   -- 6l can't encode that against a PIE target ("doasm: notfound").
   `-z` (already implemented, see notes_exec_macho.txt's PIE section)
   makes 6c materialize such addresses into a register instead, but
   passing it only to hello.c's own compile still failed: libc.a's own
   fmt/fmt.c object needed it too. Fixed via lib_core/libc/mkfile's
   pre-existing CFLAGS_EXTRA extension point (originally added just for
   this kind of one-off flag injection, per its own header comment) --
   'CFLAGS_EXTRA=-z' on the install command line, no mkfile changes
   needed.

3. arch/amd64/rt0.s's argc/argv assumption doesn't hold for darwin.
   Found via a real SIGSEGV running fib.c (the first program wired up
   here that actually reads argc/argv -- hello.c's main() takes none).
   6c-compiled code, including this project's own main(), always
   expects its arguments passed on the stack by the immediate caller
   (see linux/amd64/rt0.s's own comment) -- true of a raw Linux ELF
   entry (kernel already lays out argc/argv on the stack) but not of
   dyld's LC_MAIN convention on amd64, confirmed via lldb breaking at
   _main's own first instruction (not at dyld's entry, which
   `process launch --stop-at-entry` stops at instead and gives
   misleading register contents for this purpose): RDI=argc, RSI=argv,
   RDX=envp, RCX=apple, a real C-ABI register calling convention,
   matching Apple's documented "looks like main()" contract for
   LC_MAIN. arm64 never needed this bridge -- not luck, but a real ABI
   coincidence: dyld's arm64 convention is also register-based (X0=argc,
   X1=argv), and 7c's own compiled calling convention *also* passes a
   function's first argument via X0 (see "Verifying an arch's calling
   convention" below), so forwarding X0 unmodified into `BL main`
   happens to already do the right thing there. amd64 has no such
   luck (6c's calling convention is stack-only, full stop -- see
   "Verifying an arch's calling convention" below for why), so
   arch/amd64/rt0_darwin.s is a genuine second file: move DI/SI into
   AX/BX, then write them to the stack slots a 6c-compiled main(int,
   char**) expects, before calling it. lib_core/libc/mkfile's new
   RT0OFILE variable selects it, same override-on-the-command-line
   idiom as CFLAGS_EXTRA above (see that mkfile's own RT0OFILE
   comment). envp/apple (RDX/RCX) are not forwarded -- nothing here
   reads them, and Plan9 C's traditional main() signature has no slot
   for them anyway. See this file's own "This $OS/$ARCH split... traces
   back to..." paragraph above for why old Go-era code in this repo
   never had to solve this: it predates LC_MAIN entirely.

None of these three are darwin/arm64-specific gaps rediscovered late;
they're genuinely new failure modes amd64 alone exposes (non-PIE-safe
default codegen existing at all, and a calling convention rt0.s must
actively bridge rather than being able to just forward registers
unchanged). benchs/compcert/mkfile's test_goken_macos_arm64 also picked
up an unrelated but real hardening fix in the same pass: it wasn't
force-rebuilding+reinstalling libc.a before linking (unlike tests/c/
hello_libc/mkfile's test_macos_arm64, which always has), so it could
silently link a Mach-O against whatever GOOS's libc.a happened to
already be installed at $ROOT/arch/arm64/lib -- caught as a real "Bad
system call" (SIGSYS) crash after a linux/arm64 libc.a was left
installed there by unrelated regression testing earlier in the same
session, executing real Linux syscall numbers under XNU. Same
shared-install-path story as the "A second, unrelated build-hygiene
footgun" paragraph above; fixed the same way (rm -f + mk -a install
every time, not just for amd64).

Verifying an arch's calling convention before trusting it
--------------------------------------------------------------

The one recurring risk in this work: assuming a new arch's ABI matches
an arch already done, instead of checking. The concrete methodology
used for amd64 and mips (and arm64 before them, in the original pass):
write a tiny throwaway .c file with a fixed-arg function taking mixed
types (int, long, double, in different orders) and compile it with
`Xc -S`, reading the emitted FP-relative offsets directly off the
listing -- this reveals both the per-argument slot width/padding rule
(arm64/amd64: uniform 8 bytes regardless of type; mips: exact
sizeof(), no padding) and, separately, whether the *first* named
parameter arrives via a register (arm64, mips: yes, via R0/R1 --
readable directly in hand-written asm with no compiler prologue, but
only spilled to its FP+0 home slot by a *compiler-generated* function,
and only if that function's own code takes the argument's address) or
purely via the stack like every other argument (amd64: yes -- the
caller writes even the callee's first argument to the stack before the
CALL, confirmed by probing a variadic call *site*, not just a
function's own prologue). This second fact directly decides whether
that arch's svc.s needs a register-vs-FP special case for `num` (arm64,
mips, riscv/riscv64: yes; amd64: no, `num+0(FP)` just works). Do not
skip this step for a future arch on the assumption that "it's another
32-bit RISC arch, it'll be like mips" or "it's another 64-bit arch,
it'll be like arm64" -- amd64 shares arm64's slot-width rule but not
its register-passing rule; mips shares arm64's register-passing rule
but not its slot-width rule; riscv shares mips's natural-packing rule
*and* needs an 8-byte-alignment rule neither arm64 nor mips has (see
notes_arch_riscv.txt). No two arches done so far actually match on
every axis -- and for riscv specifically, -S inspection alone once
gave a wrong answer that only real qemu execution caught (see that
same notes file); trust execution over static reading when the two
disagree.

Bugs found along the way (not arch-specific ABI facts -- see the per-arch notes for those)
------------------------------------------------------------------------------------------------

- fmt/fltfmt.c's xsub1() fell off the end after abort() with no
  `return` statement -- harmless (abort() never returns) and silent on
  gcc/7c, but 6c treats it as a hard error ("no return at end of
  function"). Fixed with an explicit unreachable `return 0;`. Trivial,
  no dedicated regression test (a missing-return compile diagnostic,
  not a behavioral bug).

- fmt/dofmt.c's __charfmt() (the `%c` format verb) silently wrote
  *nothing*, no error, whenever the byte handed to it had the high bit
  set (value >= 128 unsigned, negative as a signed char) -- found while
  unblocking benchs/compcert/mandelbrot.c, whose `putc(byte_acc,
  stdout)` inner loop (byte_acc built up bit-by-bit, so it takes on
  every value 0-255) silently lost every 128-255 byte, corrupting the
  PBM image output. Root cause: __charfmt() delegated to __fmtcpy(),
  which is written for copying UTF-8 *text* -- correct for its other
  callers (%s, %q, float-formatting suffixes) but wrong here: any byte
  >= Runeself (0x80) gets treated as the leading byte of a multi-byte
  UTF-8 sequence and handed to fullrune()/chartorune(), and for a
  single raw byte (the only byte %c ever has on hand) fullrune()
  correctly reports "not a complete sequence" -- so __fmtcpy() silently
  wrote nothing at all via its `else break;` path. %c's actual contract
  in this codebase (see include/APE/stdio.h's own comment on putc()) is
  "write exactly one raw byte, whatever its value" -- UTF-8 rune
  formatting is %C's (__runefmt()) job, a separate, already-correct
  function a few lines below in the same file. Fixed by having
  __charfmt() write the byte directly via the FMTCHAR macro (already
  used elsewhere in dofmt.c for plain non-rune output, e.g. numeric
  padding), bypassing __fmtcpy()'s UTF-8 decoding entirely -- keeps the
  same width-padding behavior, drops only the wrong rune
  interpretation. This is a runtime-library bug, not a compiler bug: it
  affects every program using %c/putc() with a byte value >= 128, on
  every architecture (fmt/ is shared, not per-arch), and needed a
  rebuilt libc.a, not a recompiled compiler, to pick up (`rm -f libc.a;
  mk -a 'objtype='$cputype 'cputype='$cputype ['GOOS='$goos] install`
  -- the `mk -a` matters here too, same "changing a shared .c file
  doesn't necessarily get noticed by a plain `mk install`" lesson as
  the macbody build-system gotcha in notes_shared_frontend_bugs.txt).
  Debugging path worth remembering: a 4096-byte tight loop
  (`putc((char)(i&0xff), stdout)` for i in 0..4095) made the pattern
  obvious once traced byte-by-byte -- contiguous runs of 0..127 came
  through correctly, every 128..255 byte in each 256-iteration cycle
  was simply missing, which is what pointed at a *value-dependent* bug
  in the formatting/write path rather than, say, a syscall-wrapper
  return-value bug (the initial, wrong theory -- the darwin syscall
  wrappers really do skip checking the carry-flag error convention, per
  this file's other notes, but that wasn't what was happening here).
  See tests/c/regressions/fmt_charfmt_high_bit.c (verified via
  snprint(), which exercises the identical dofmt()/__charfmt() code
  path without needing to capture a real fd's output) and its
  fmt_charfmt_high_bit.check_macos_arm64 target in tests/c/regressions/
  mkfile.

- compilers/cc/com64.c (the newer frontend) already handles a
  vlong-typed `?:` used as a call argument; src/cmd/cc/com64.c (the
  older, separate frontend that 7c/vc/ic actually build against) was
  missing the same OCOND/OLIST/OCOMMA cases and hit "unknown vlong
  %O". Only surfaced on mips (vc) and riscv (ic) because arm64/amd64
  are 64-bit-native and never enter this vlong-emulation code path at
  all (`machcap()` bails out immediately for them); ic/jc share the
  fix (both link against the same src/cmd/cc/cc.a) but needed a
  separate relink after the fix landed to actually pick it up -- an
  easy step to forget when a fix lands in a *library* multiple final
  binaries link against, not the binary you're testing directly. Full
  writeup, including exactly which nodes fail and why, in
  docs/claude_notes/notes_shared_frontend_bugs.txt.

- linkers/vl/obj.c's and linkers/il/obj.c's objfile() both resolved
  `-lXXX` straight to a hardcoded `/usr/{v,i}lib/libXXX.a`, never
  consulting the `-L` list at all (linkers/7l/pobj.c's equivalent
  already does this correctly via findlib()). Same fix ported to both
  (il needed one extra step: a forward declaration of findlib(), since
  unlike vl's file, il/obj.c defines objfile() textually before
  findlib()). This is now the *second* occurrence of this exact bug
  shape -- worth checking 5l/6l/8l before assuming they're fine. Full
  writeup in notes_arch_mips.txt (vl) and notes_arch_riscv.txt (il).

- riscv64: `long` stays 4 bytes there (like every Plan9 C compiler in
  this tree, on every arch -- see the "darwin/arm64" section below for
  the correction to this bullet's own original, too-narrow framing)
  despite riscv64 having 8-byte pointers, so anything typed `unsigned
  long`/`long` as a stand-in for "pointer-wide integer" (a va_arg
  alignment computation, a syscall trampoline argument) silently
  truncates. Not a compiler bug -- a real property of this arch that's

  GOOS, and the vlong bug it exposed" above.

- arm-only: a genuinely new linkers/5l bug, and the one item on this
  list that checked out and confirmed 5l specifically (per the "worth
  checking 5l/6l/8l" note above -- 6l/8l turned out fine, having no

  from an actual library (as opposed to a directly-named object file,
  what every prior arm test in this tree did) failed to link. Checked
  against both ~/xxx/9front/5l/ and ~/principia/linkers/5l/: same bug,
  present and unfixed in both -- this is goken-original work, not a
  ported fix. Full writeup, including why principia's own arm kernel
  build never happened to trigger it, in notes_arch_arm.txt.

File syscalls (open/read/close/lseek), and the syscall/ vs os/ split
------------------------------------------------------------------------

Added July 2026, extending the write/exit-only libc above to real file
I/O: open/read/close/seek, matching the Plan9-flavored API
include/os/file.h already declared (fdt open(char*,int) with
OREAD/OWRITE/ORDWR/OEXEC/OTRUNC/OCEXEC/ORCLOSE/OEXCL bits -- NOT POSIX's
open(2) shape) but that nothing had implemented yet.

This is also where lib_core/libc/os/ (previously an empty, uncommitted
scaffold dir) got its first real content, and its own purpose nailed
down precisely, per explicit user direction: syscall/ stays a *pure*
raw-syscall adapter, one thin wrapper per (OS, arch) with no API-shape
opinions; os/$GOOS/ is where a *different* API shape gets bridged on
top of it. Concretely:

- syscall/os/$GOOS/ (both linux and darwin) now also generates read(),
  close(), and a raw 3-arg-POSIX-shaped open() -- but named _sysopen(),
  not open(): Plan9's open() is 2-arg with a completely different flag
  encoding (OREAD=0/OWRITE=1/ORDWR=2/OEXEC=3 base mode, OTRUNC=16/
  OCEXEC=32/ORCLOSE=64/OEXCL=0x1000 extra bits), so the raw wrapper
  needed a different name to avoid an incompatible-signature symbol
  clash with the real, public open(). lseek() is generated too
  (Plan9 calls it seek(), see port/seek.c below). Linux's arm64/riscv/
  riscv64 have no legacy 3-arg open() syscall at all (removed from the
  "generic" ABI, openat()-only) -- their .decl generates openat() from
  SYS_openat instead, and syscall_linux_{arm64,riscv,riscv64}.h
  hand-adds a one-line _sysopen(path,flags,mode){return
  openat(AT_FDCWD,...);} shim so os/linux/open.c can call the same
  _sysopen() name uniformly regardless of which raw syscall backs it on
  a given arch -- keeping the os/linux/ glue arch-independent.

- os/$GOOS/open.c (linux and darwin, separately -- their O_TRUNC/
  O_EXCL/O_CLOEXEC numeric values genuinely differ) translates Plan9's
  mode bits into that OS's real O_* flags and calls _sysopen(). This is
  the directory the user asked to keep separate from syscall/
  specifically for this reason -- it was originally sketched as
  os/os/$GOOS/ (mirroring os/arch/$cputype/, itself mirroring
  syscall/'s own arch/os split) but flattened to os/$GOOS/ per follow-up
  feedback, since nothing lives under os/arch/ yet and the extra
  nesting bought nothing.

- port/seek.c is a third case: Plan9's seek(fdt,vlong,int) vs lseek()'s
  name is a *pure* rename with no OS-specific behavior (SEEK__START/
  CUR/END already equal POSIX's SEEK_SET/CUR/END numerically
  everywhere), so it's genuinely portable and lives in port/, not
  os/$GOOS/.

- read()/close() needed no glue at all -- their Plan9 and POSIX shapes
  are already identical (like write() already was), so syscall/'s
  generated wrappers serve directly as the public symbols.

Darwin's XNU carry-flag error convention (syscall/os/darwin/
svc_{amd64,arm64}.s) was also fixed in this pass: previously documented
as a known gap ("worth fixing before adding a syscall a caller actually
needs to detect failure from" -- exactly what open()/read() are).
JCC/NEGQ (amd64) and BCC/NEG (arm64) now negate the return value on
carry-set, matching Linux's already-negative-on-error convention
uniformly. This one stayed in syscall/, not os/darwin/, despite also
being about API-shape: the carry flag itself doesn't survive as
C-visible state past the trap instruction, so *something* has to decide
the return convention right there in the raw trampoline -- there's no
way to defer it to a higher glue layer. Unverified on real hardware
(no macOS available this session, same caveat as the rest of darwin/amd64's
history above) -- verify before trusting it.

A real, non-obvious bug found and fixed along the way: linux/mips's
svc_mips.s left the syscall's actual result in R2 ($v0, where the
Linux/mips o32 kernel ABI legitimately puts it) but this compiler's own
calling convention returns a function's `long` result via R1 -- and
R1, loaded with the syscall *number* at function entry, was never
touched again before RET. write()/exit() never surfaced this (nothing
ever inspected their return value), but open()'s fd and read()'s byte
count came back as literally the raw SYS_open/SYS_read constants
instead of real values -- caught by a debug build printing them
directly (4005/4003, the exact syscall numbers), not by static reading.
Symptom before the fix, for what it's worth: io.exe's write(1, buf, n)
with n==garbage-large dumped stack memory (visibly including envp
strings) well past the 256-byte buf, which is what first pointed at "n
is wrong", not "read failed". Fixed with one `MOVW R2, R1` before RET;
verified via a real qemu-mips run of tests/c/hello_libc/io.c
(open+read+seek+write+close against a real fixture file) after the fix,
not just recompiling.

Verification: `lib_core/libc && mk -a objtype=$arch cputype=$arch
install` then `tests/c/hello_libc && mk objtype=$arch cputype=$arch
test_one` (now builds+runs both hello.exe and the new io.exe) via real
qemu-user, for all seven Linux arches (arm64/amd64/386/arm/mips/riscv/
riscv64) -- all pass, including mips only after the svc_mips.s fix
above and amd64/386 only after the boot-gcc CFLAGS_ARCH fix below.

amd64/386's "bad mul alg" host-toolchain bug, and its real fix
------------------------------------------------------------------------

amd64/386 initially failed to build lib_core/libc entirely, at
math/lrand.c's `x = A*lo - R*hi;` ("bad mul alg" from 6c/8c) -- and
`git stash`-ing just compilers/{6c,8c}/mul.c confirmed the failure
predates this session (neither arch's libc.a had ever been built
before). The bug itself is real but NOT in mul.c's algorithm: its
Mparam.alg/Malg.vals fields are plain `char`, and mulgen1()'s "no cheap
multiply found, fall back to a real MUL" sentinel (`mp->alg = -1`)
relies on that staying negative -- true when `char` defaults to signed
(x86), false when it defaults to unsigned (arm64/AAPCS, this project's
own boot-gcc host), where -1 reads back as 255 and falls into an
unhandled switch default instead of the intended silent fallback.
compilers/8ck/mul.c already carried a comment about exactly this
("the use of -1 below requires -fsigned-char on arm64..."), and
BOOT/mkfiles/hostflags/{arm64,riscv,riscv64}/mkfile already set
`CFLAGS_ARCH=-fsigned-char` for exactly this reason -- but
mkfiles/boot-gcc/mkfile's own `<$TOP/mkfiles/hostflags/$cputype/mkfile`
include was missing a `BOOT/` path segment (mkfiles/hostflags/ has never
existed, only BOOT/mkfiles/hostflags/ does), so mk silently skipped it
("warning: skipping missing include file") and $CFLAGS_ARCH never
reached gcc at all -- meaning 6c/8c/8ck (built BY this boot-gcc step)
were *always* compiled with unsigned char on an arm64 host, this
bug included. A first attempt at fixing this by adding `signed char` to
the three affected mul.c fields directly (in all of 6c/8c/8ck) was
tried and confirmed working, then reverted in favor of the smaller,
already-intended fix once this was found -- editing mul.c wasn't
necessary and would have been redundant with -fsigned-char.

The fix has a second half beyond the path prefix: `mk objtype=boot-gcc
install` alone still didn't pick up CFLAGS_ARCH, because mk variables
come from the command line, not the shell environment -- env.sh's own
`export cputype=...` doesn't make mk see `$cputype` as a defined
variable inside `<$TOP/BOOT/mkfiles/hostflags/$cputype/mkfile`; that
needs `cputype=arm64` passed explicitly on the `mk` command line too
(`mk -a 'objtype=boot-gcc' 'cputype=arm64' install`), the same
"mk variables aren't environment variables" lesson this file's own
`GOOS`/cast-type discussion already covers elsewhere. Verified via a new
tests/c/regressions/mulconst_unsigned_char_host.c (built on 6c/8c/8ck,
run under qemu, checks the actual `A*lo - R*hi` arithmetic result) --
confirmed it fails without the fix (temporarily reverted just
compilers/*/mul.c and rebuilt) and passes with it, wired into that
directory's `test:V:` alongside the pre-existing, related mulzero.check.
After fixing, a full `mk -a objtype=boot-gcc all` plus reinstalling
6c/8c/8ck were needed to actually flow the flag into every already-built
boot-gcc binary, not just lib_core/libc's own compiles -- `all` alone
does NOT install (mkfiles/mkone's own `all:V: $O.out` vs `install:V:
$BIN/$TARG`), so each of 6c/8c/8ck still needed an explicit `mk install`
afterward for ROOT/arch/boot-gcc/bin/ to actually pick up the new build.

Darwin (amd64/arm64) was written the same way. Windows/amd64
(kernel32 CreateFileA/ReadFile/WriteFile/CloseHandle/SetFilePointerEx
via os/windows/winio_amd64.s + os/windows/open.c) started as the same
kind of best-effort, unwired, compile-untested draft (no macOS or
Windows host available that session) but was later wired up and
verified end to end on a real Windows/Cygwin host (2026-07-31, see
tests/c/hello_libc/mkfile's test_windows target). Windows is a bigger
gap than darwin in one structural way that bring-up confirmed: unlike
Linux/Darwin, there's no raw-syscall-number convention Windows
applications are meant to use directly, so it has no syscall/os/
windows/ layer at all -- kernel32 IS the ABI, called straight from
os/windows/'s glue, and lib_core/libc/mkfile's SYSCALLOFILES (which
every other GOOS points at syscall/os/$GOOS/svc_$cputype.$O +
zsyscall_${GOOS}_$cputype.$O) has to be overridden to empty on the
command line for GOOS=windows instead. Two more things fell out of
finishing the bring-up that the original draft's own header comments
didn't anticipate:
- exit() has no home either (same "no raw syscall" reason) -- added as
  a plain kernel32 ExitProcess() TEXT symbol directly in
  winio_amd64.s, rather than a separate rt0_windows.s: hello.c/io.c's
  main() takes no arguments, so arch/amd64/rt0.s's existing generic
  _main (CALL main(SB); MOVL $0,(SP); CALL exit(SB)) works unmodified
  once exit() itself has a real body -- no dyld-style argc/argv
  register bridging like rt0_darwin.s needed.
- port/seek.c's `#ifndef plan9` guard (see that file's own comment)
  had to become a second nested `#ifndef windows`: os/windows/open.c
  defines a real seek() itself (on top of _winseek), same situation as
  plan9's own real seek(2) syscall, so linking port/seek.c's
  lseek()-renaming shim in unconditionally produced a "duplicate text
  symbol: seek" archive error, not a missing-symbol one (windows has
  no `lseek` symbol at all for the shim to even resolve against).
- linkers/lk/pe.c's importfuncs[] table only listed the three imports
  (GetStdHandle/WriteFile/ExitProcess) every existing hand-rolled
  tests/c/mini*/tests/s/mini .s test needed -- io.exe's real
  open/read/seek/close needed CreateFileA/ReadFile/
  SetFilePointerEx/CloseHandle added to that table too (6l relinked
  and reinstalled after, since it's compiled-in to the linker itself,
  not read from a config file at link time).
lib_core/libc/mkfile also gained an OSEXTRAFILES override (same "leave
unset elsewhere" convention as ARCHEXTRAOFILES) since OSFILES's
default (os/$GOOS/open.$O, arch-independent on every other GOOS) has
no way to pull in windows' per-arch winio_$cputype.s otherwise.

Plan9 (GOOS=plan9) and principia: NOT started. This would be a third,
structurally different bring-up (no INT/SYSCALL-style raw trap --
number in a register, args written to the stack, single trap
instruction per docs/claude_notes/notes_abi_plan9.txt) rather than an

lseek's return width: a second trampoline, not a widened _syscall6
------------------------------------------------------------------------

Follow-up fix, same session as the file-syscall work above: lseek's
return value (a real 64-bit off_t) was truncated to 32 bits by
_syscall6's own `long` return type, on every arch -- flagged as a known,
accepted limitation when the file syscalls first landed. First attempt
widened _syscall6 itself to `vlong` everywhere (touching all 9 (OS,
arch) headers); reverted per explicit user pushback ("vlong is tricky,
long had some simplicity to it" -- tests/c/vlong's own history bears
this out) in favor of a second, separate trampoline (_syscall6v) used
only by lseek, leaving _syscall6 itself (used by write/read/close/
_sysopen/openat -- the common path) completely untouched.

_syscall6v is a byte-identical duplicate of _syscall6's body under a
new TEXT label per svc_$cputype.s (same register loads, same trap --
the raw hardware register already holds the kernel's full 64-bit
result regardless of what C prototype reads it, so no new logic is
needed, just a second symbol name for the caller to bind a wider
prototype to). Only added for the archs with a real 64-bit register to
return a `vlong` in a single piece: linux/{amd64,arm64,riscv64} and
darwin/{amd64,arm64} -- deliberately NOT 386/arm/mips/riscv(32), where
this compiler's `vlong` return convention would need a register PAIR
(e.g. AX:DX-style) that the hand-written trampoline doesn't populate,
and where the real 32-bit lseek syscall only returns a 32-bit off_t
anyway (nothing to gain). scripts/mksyscall.sh gained an optional
":trampoline" suffix on a decl line's SYS_NAME field (e.g.
"SYS_lseek:_syscall6v") to select this per-syscall, defaulting to
_syscall6 for every existing entry (fully backward compatible -- no
other .decl line needed to change). port/seek.c's own `extern lseek()`
declaration now has to match lseek's real per-arch return type exactly
(`vlong` on the 5 widened archs, `long` elsewhere) -- via nested
#ifdef/#else/#endif, not `#if defined(X) || defined(Y)`: 7c/vc/ic's
preprocessor doesn't understand `#if` with an expression at all
("unknown #: if"), only plain #ifdef, caught by a real build failure
across all 7 Linux arches before landing this.

Verified via a fresh `mk -a` install of all 7 Linux arches' libc.a plus
a full tests/c/hello_libc `mk test` run (all 7 pass, io.exe's seek()
call exercises the new _syscall6v path on arm64/amd64/riscv64) and
tests/c/regressions' `mk test` (no regressions). Darwin's own
_syscall6v (amd64/arm64) is written the same way but, like the rest of
this file's darwin work, unverified by execution -- no macOS host this
session.

create/remove/chdir: the file-system-modifying calls
------------------------------------------------------------------------

Added July 2026, following docs/claude_notes/plan_syscalls.txt's Tier 2
(read that file's number tables before adding access/dup, the two Tier
2 calls still outstanding). Landed on all 11 (OS, arch) combinations
plus windows/amd64. Interesting mostly because these three calls
happen to need all three of the implementation strategies the
syscall/ vs os/ split was designed around -- one call each:

- chdir: identical shape on every Unix AND on Plan9, so it is a plain
  .decl line generating the public symbol directly, on all 9 Unix
  (OS, arch) pairs. No glue anywhere.

- remove: Plan9's name for POSIX unlink(2); same shape, so also a
  plain .decl line -- except on arm64/riscv/riscv64, whose "generic"
  Linux ABI dropped every syscall that has an *at() form. There is no
  SYS_unlink there at all, only unlinkat=35. So those three .decl
  files generate unlinkat() and their syscall_linux_$arch.h hand-adds
  a remove(path){return unlinkat(AT_FDCWD,path,0);} shim -- the exact
  pattern _sysopen()/openat() already established, one level down.
  Worth internalizing: on those archs, "is there a syscall for X"
  usually resolves to "there is an Xat()".

- create: needs real translation and NO syscall number. Every Unix
  here does have a creat(2) (386/arm/mips: 8, amd64: 85), but it is
  useless -- creat() is hardwired write-only, while Plan9's
  create(char*,int,ulong) takes a full mode argument and is routinely
  called with OREAD or ORDWR. So it is _sysopen(path, flags|O_CREAT|
  O_TRUNC, perm&0777) in os/$GOOS/open.c. The unconditional O_TRUNC is
  the part that does not fall out of open()'s own flag translation:
  Plan9's create(2) truncates an existing file whether or not the
  caller passed OTRUNC.

Because create() and open() now share that mode-bit translation, each
os/$GOOS/open.c grew a static openflags() helper rather than a second
copy of the switch -- that per-OS table (Linux O_CREAT=0x40, mips
0x100, Darwin 0x200) being the whole reason the file is per-GOOS.

DMDIR was initially left as a documented gap (create() returned -1
rather than silently making a plain file) and was filled in immediately
after, by adding mkdir/mkdirat -- see the next section.

GOOS=plan9 is the sharpest illustration of the layering: all three are
plain raw kernel stubs in syscall/os/plan9/svc_{arm,mips}.s (CREATE=13,
REMOVE=14, CHDIR=15), with no os/plan9/ glue at all -- create()
included, DMDIR and all, since it is the API the rest of this tree was
already shaped to. 5i/vi needed no work either: machines/5i/
syscall_posix.c's syscreate/sysremove/syschdir already existed.

include/os/dir.h had to be made includable to land this. It declares
create/remove/chdir (and struct Dir, getwd, access, ...) but had never
been included by anything, and could not be: struct Dir has a `Qid
qid;` field and nothing in include/ ever typedef'd Qid or Dir. Both
typedefs added (Qid next to its struct in os/file.h, Dir in dir.h,
matching os/proc.h's own `typedef struct Waitmsg Waitmsg;`), and
libc.h's "directory" section -- empty until now -- includes the
header. Note most of what it declares still has no implementation
behind it; those need the stat(2) family first (plan_syscalls.txt's
Tier 3).

DMDIR: mkdir/mkdirat, and why remove() needed rmdir too
------------------------------------------------------------------------

Filling the DMDIR gap turned out to touch both ends of the API, not
just create(), because Plan9 collapses two POSIX distinctions that
POSIX keeps apart:

  Plan9                          POSIX
  create(p, mode, perm)          open(p, O_CREAT|O_TRUNC, perm)
  create(p, OREAD, DMDIR|perm)   mkdir(p, perm), then open(p)
  remove(p)  [file]              unlink(p)
  remove(p)  [empty directory]   rmdir(p)

So supporting DMDIR in create() without also teaching remove() about
rmdir would have produced directories nothing in this libc could
delete. Both halves landed together.

Numbers: mkdir is 39 on 386/arm, 4039 on mips o32, 83 on amd64, 136 on
Darwin; rmdir is 40/4040/84/137 respectively. The generic-ABI archs
(arm64/riscv/riscv64) need mkdirat=34 -- and get rmdir for FREE, since
this ABI expresses it as unlinkat(AT_FDCWD, path, AT_REMOVEDIR=0x200),
the same number unlink already uses. That is the whole reason
_sysunlink/_sysrmdir are separate names: on the legacy archs they are
two syscalls, on the generic ones they are one syscall and a flag.

create()'s directory path mirrors BOOT/lib9/open.c's p9create(),
including its refusal of any mode but OREAD for a directory create
(there is nothing to write to a directory through an fd, and Plan9
rejects it too) -- OCEXEC is allowed on top, since it says nothing
about access. After mkdir succeeds it reopens the path, because Plan9's
create() is defined to hand back the new object already open. On
windows that reopen needs FILE_FLAG_BACKUP_SEMANTICS: CreateFileA
refuses to return a handle to a directory otherwise, at any
dwDesiredAccess.

Keeping port/ free of #ifdef
------------------------------------------------------------------------

remove()'s POSIX bridge (try unlink, fall back to rmdir) is portable
given those two primitives -- no per-OS constants, no per-arch widths.
It was first written into port/remove.c behind a `#ifndef plan9 /
#ifndef windows` pair copied from port/seek.c, since neither GOOS wants
it: plan9's kernel provides remove(2) with exactly the Plan9 semantics
already (directories included -- it never had the unlink/rmdir split),
and windows has no raw-syscall layer, so os/windows/open.c defines
remove() itself over DeleteFileA/RemoveDirectoryA.

Per user direction, that was reworked: port/ should hold only clean
portable code, with the GOOS selection done around it rather than
branched inside it -- the Plan9 habit of choosing FILES in the build
instead of #ifdef'ing within them, which is exactly what this tree's
os/$GOOS/ and arch/$cputype/ directories already exist for. Both files
lost their GOOS guards, and lib_core/libc/mkfile grew:

  PORTPOSIXOFILES=`{if(~ $GOOS plan9 windows) echo -n; \
                    if not echo port/seek.$O port/remove.$O}

mk evaluates that backquote when the mkfile is read, by which point a
command-line 'GOOS=plan9' has already overridden the mkfile's own
default -- so callers need no override of their own, unlike
SYSCALLOFILES=/OSEXTRAFILES=, which the windows build still passes
explicitly. Verified with `mk -n` per GOOS: linux/darwin select both
files, plan9/windows select neither.

port/seek.c still carries #ifdefs, but only arch ones (lseek's return
type is vlong on amd64/arm64/riscv64 and long elsewhere), which are a
different problem -- they would need per-arch files, not per-GOOS ones,
to remove. Worth revisiting if that file grows.

access and dup: Tier 2 finished, and two more shapes
------------------------------------------------------------------------

These two complete plan_syscalls.txt's Tier 2, and between them they
add the two remaining ways a Plan9 call can fail to line up with a
POSIX one -- neither of which create/remove/chdir had shown:

- access() runs the OTHER way round from everything else here. Its
  Plan9 mode bits (AEXIST/AEXEC/AWRITE/AREAD = 0/1/2/4) are
  numerically identical to POSIX's F_OK/X_OK/W_OK/R_OK, so on Linux and
  Darwin it is a bare generated wrapper with no glue at all -- but
  PLAN9 ITSELF has no access(2) syscall. It is an ordinary libc
  function there, built over open(). So os/plan9/ gained its first real
  file (access.c, ported from principia's 9sys/access.c, omode[] table
  and "only approximate" caveats included), and the mkfile gained
  OSGOOSOFILES to select it -- the mirror image of PORTPOSIXOFILES,
  and the same file-selection-not-#ifdef habit.

  One deliberate gap: principia special-cases AEXIST via dirstat(),
  because "exists" and "can be opened for reading" are different
  questions. dirstat needs stat(2) (Tier 3), so AEXIST currently falls
  through to open(OREAD). Restoring that branch is the whole fix once
  stat lands.

- dup() is one Plan9 syscall covering what POSIX splits in two:
  newfd == -1 means "lowest free descriptor" (POSIX dup), anything else
  is dup2. Confirmed against principia's sysdup(), whose `if(fd != -1)`
  branch is exactly that split. So port/dup.c picks between
  _sysdup()/_sysdup2(), and on arm64/riscv/riscv64 -- which kept dup
  but dropped dup2 -- _sysdup2 is a dup3(old,new,0) shim. Worth
  knowing: dup3 is NOT a drop-in dup2, since dup3(fd,fd,0) fails EINVAL
  where dup2(fd,fd) returns fd.

Numbers: access 33 on 386/arm (4033 mips), 21 on amd64, 33 on Darwin;
dup 41/4041/32/41; dup2 63/4063/33/90. The generic ABI has dup=23,
dup3=24, faccessat=48.

windows gets access() (GetFileAttributesA, approximate -- existence and
the read-only bit only, since Win32 permissions are ACLs) but NOT
dup(), which cannot be honest until fd numbers stop being truncated
HANDLEs: dup(old, newfd) has to place a descriptor at a caller-chosen
number, which that model cannot express. Filed in todo.org.
tests/c/hello_libc/fd.c is therefore built for every GOOS except
windows -- easy because test_windows lists its binaries explicitly
rather than building `all`.

The mips o32 error convention: a real bug the new test found
------------------------------------------------------------------------

tests/c/hello_libc/dir.c is the first test in this tree to check a
*failing* syscall's return value, and it immediately failed on mips
only. The syscalls themselves were all correct -- a qemu-mips -strace
showed the kernel doing exactly the right thing (unlink = 0, then the
deliberate reopen = -1 errno=2) while the C caller saw a valid fd.

Cause: mips o32 is the only arch here that does NOT report errors by
returning a negative value. On 386/amd64/arm/arm64/riscv/riscv64 the
kernel returns -errno directly in the result register, so a caller's
`if(fd < 0)` just works. o32 instead reports failure out of band in
$a3 (R7): 0 on success, 1 on error, with $v0 holding a POSITIVE errno
when it is 1. syscall/os/linux/svc_mips.s ignored R7 entirely, so
open() on a missing file returned +2 (ENOENT) -- i.e. every error
check in libc read a failure as a valid small fd, on that arch alone.

Fixed in svc_mips.s by branching on R7 and negating $v0 into the
return register (`BEQ R7, ok; SUBU R2, R0, R1`), converting o32's
convention into the negative-errno one every other arch already
returns, so nothing above the trampoline has to know. This is the
third bug of exactly this shape in this one file (see the MOVW R2,R1
story in the file-syscalls section above, and Darwin's carry flag),
and the pattern is worth stating plainly: a raw syscall trampoline's
*error* path is invisible to any test whose syscalls all succeed.
hello.c and io.c only ever make calls that work, which is why both
earlier bugs and this one survived so long. See notes_arch_mips.txt
for the ABI fact itself.

Verified: full `mk test` in tests/c/hello_libc -- all 7 Linux arches
under qemu (386/amd64/arm/arm64/mips/riscv/riscv64) plus GOOS=plan9
arm and mips under 5i/vi, hello.exe + io.exe + the new dir.exe each.
mips passes only with the R7 fix. dir.c proves each call did something
rather than merely returning success: the created file is reopened and
read back, the removed one is reopened and required to FAIL, the
created DIRECTORY is proven to be one by putting a file inside it by
path (and by remove() then refusing to delete it while non-empty), and
chdir("..") is followed by opening a path that only resolves from the
parent. darwin (create/remove/chdir in
os/darwin/open.c and both .decl files) and windows are written but
unverified by execution -- no macOS or Windows host this session, same
standing caveat as the rest of those two targets in this file.

windows/amd64 needed a linker change too, which is worth knowing about
before adding any further Win32 call: linkers/lk/pe.c carries a
hardcoded list of kernel32 imports (importfuncs[]). Because this ?l
has no separate relocation pass, __imp_<name> must already exist when
instructions are encoded, so an import that is not in that list simply
fails to resolve -- it is not discovered from the object files.
Four were added there: DeleteFileA and SetCurrentDirectoryA for
remove()/chdir(), then CreateDirectoryA and RemoveDirectoryA for
create()'s DMDIR bit and remove()'s directory case. CreateFileA was
already present and covers both create() (which differs from open()
only in dwCreationDisposition, CREATE_ALWAYS vs OPEN_EXISTING) and the
directory reopen (which differs only in
FILE_FLAG_BACKUP_SEMANTICS). Note pe.c is shared by 6l and 8l, so both
must be rebuilt after editing it -- and tests/s/variants' golden
pe_amd64.exe has to be regenerated, since .idata grows with the list.

sbrk (Tier 1): why sbrk, not brk, is the portable primitive
------------------------------------------------------------

Tier 1 of plan_syscalls.txt, and the only item on that list that
actually blocked something: port/minimal_malloc.c is a 64MB
`static char heap[]` with a no-op free(), and principia's real pool.c
cannot replace it until libc can grow the heap.

The layering is the whole design, and it is worth stating plainly
because it looks backwards -- brk is the syscall, sbrk the library
function, yet sbrk is what the tree codes against:

  brk(addr)   absolute: "put the end of the data segment exactly here"
  sbrk(n)     relative: "grow by n, hand me a pointer to the new bytes"

sbrk's contract never promised the new block ABUTS the previous one.
That is precisely what lets it be backed by something other than a
break. brk's contract (one monotonically-moving boundary in a single
contiguous segment) cannot be honored by mmap without reserving an
address range up front. Since there is no usable brk on modern macOS at
all (SYS_break=17 survives in the BSD table but fails), exporting brk as
the universal primitive would have forced darwin to fake a contiguous
segment and then sit the real sbrk on top of that pretense -- two layers
of lying instead of one honest per-GOOS branch.

Confirmed all three in-tree callers treat each hunk independently and so
depend on nothing stronger: utilities/text/grep/sub.c's mal(),
utilities/byte/dd.c's ibuf/obuf, linkers/8lk/compat.c's mysbrk.

So, per GOOS (selected in lib_core/libc/mkfile's SBRKOFILES by choosing
FILES, not by #ifdef -- see CLAUDE.md):

  plan9    port/sbrk.c over the kernel's own BRK syscall, which is
           already exactly include/os/mem.h's brk() shape (0/-1). No
           glue at all. 5i/vi already implemented BRK, so no machines/
           work was needed either.
  linux    port/sbrk.c over os/linux/brk.c, which exists solely to
           bridge a return convention: Linux's brk(2) does NOT use
           negative-errno. It returns the NEW break, and reports failure
           by returning the UNCHANGED old one. The test is `< addr`, not
           `!= addr`, because the kernel rounds up to a page and may
           legitimately return more than requested.
  darwin   no brk at all, so port/sbrk.c is not built; os/darwin/sbrk.c
           hands out a fresh MAP_ANON region per call instead. NOTE
           MAP_ANON is 0x1000 here, not Linux's 0x20.
  windows  os/windows/sbrk.c over VirtualAlloc(NULL, n,
           MEM_COMMIT|MEM_RESERVE, PAGE_READWRITE) -- structurally the
           same as darwin's. Unlike dup(), nothing here is blocked by
           that port's fd-as-truncated-HANDLE simplification, since no
           descriptors are involved. MEM_COMMIT *and* MEM_RESERVE in one
           call matters: reserving without committing hands back an
           address that faults on first touch.
           This needed a linker change to exist at all -- linkers/lk/pe.c's
           importfuncs[] is a hardcoded list (no relocation pass, so
           __imp_<name> must exist before instruction encoding), so
           VirtualAlloc had to be added there, making it the 13th import
           and the first that is not a file operation. Shared by 6l and
           8l; tests/s/variants' pe_amd64 golden was regenerated, after
           validating the new image structurally (PE32+, import dir RVA
           matching .idata, 13 null-terminated IAT entries).

os/linux/brk.c is arch-independent and lives in os/$GOOS/ rather than
being copied into each of the seven syscall_linux_$cputype.h shims: only
the syscall NUMBER differs per arch, and that already lives in
numbers_$cputype.h. Same reasoning as os/linux/open.c.

Two things that had to be got right in the raw wrappers, both instances
of traps this file already documents elsewhere:

- The decl's rettype is `uintptr`, and on the 64-bit arches it must go
  through `_syscall6v`, not the default `_syscall6`. _syscall6 is
  declared `long`-returning and `long` is 4 bytes on EVERY arch here, so
  a returned ADDRESS truncates. This is _syscall6v's second use and the
  first that is not about a 64-bit offset.
- uintptr itself was 4 bytes on amd64 and arm64 (`typedef unsigned long`
  in their u.h) until this work. Found precisely because sbrk is pointer
  arithmetic through uintptr. See tests/c/regressions/uintptr_width.c;
  riscv64 had already hit and fixed it, but its comment asserted the
  other two were fine, which is what kept anyone from checking.

Also found: include/os/mem.h (brk/sbrk/end) was included by NOTHING --
the header existed but was never reachable, so every caller of brk() or
sbrk() compiled with no prototype in scope. libc.h now includes it, the
same gap and fix as the earlier os/dir.h one.

On testing it, see notes_test_infra.txt's "qemu-user is not the kernel"
section: the failure path is deliberately NOT asserted, because qemu
implements brk itself and accepts what a real kernel refuses.

The "small tier": getpid, getwd, time/nsec, sleep
------------------------------------------------------------

Picked over the stat and process-control tiers precisely because these
four are NOT a uniform group: each is a plain syscall on some systems
and not a syscall at all on others, so between them they exercise every
shape of glue this directory has.

  getpid  syscall on linux/darwin (generated straight into its public
          name -- Plan9 and POSIX agree exactly). An ordinary FILE READ
          on plan9 ("#c/pid"), needing no syscall at all. A kernel32
          call on windows.
  getwd   a real getcwd(2) only on LINUX. darwin and plan9 both lack one
          entirely and independently arrive at the same alternative:
          open ".", then ask the kernel what path that DESCRIPTOR refers
          to -- fcntl(F_GETPATH) and fd2path respectively. Strictly
          better than a cached string, which can go stale. windows has
          GetCurrentDirectoryA, whose return value is overloaded three
          ways (0 = failure, < nbuf = length written, >= nbuf = required
          size and nothing written), so ">= nbuf" is failure, not
          success.
  time    clock_gettime on linux, gettimeofday on darwin, /dev/bintime
          on plan9 (8 bytes, BIG-endian regardless of machine, since it
          is 9P-served), a FILETIME epoch shift on windows.
  sleep   MILLISECONDS, per include/os/time.h -- not POSIX seconds.
          A real syscall on plan9 and a plain Sleep() on windows, both
          needing zero conversion; built from a timespec on linux, and
          from select() on darwin, which has no nanosleep syscall.

Two findings worth keeping:

- Darwin has NO getcwd syscall under any name, and NO nanosleep syscall.
  plan_syscalls.txt guessed __getcwd = 296 and flagged it unverified;
  296 is actually vm_pressure_monitor. Both were settled from XNU's own
  bsd/kern/syscalls.master, not from the 2010 Go snapshot the rest of
  syscall/os/darwin/ came from -- that snapshot simply does not have
  them. When a Darwin number is not in the Go snapshot, use the XNU
  tree; do not guess.
- Use clock_gettime/clock_nanosleep, NOT gettimeofday/nanosleep, on
  linux. The obvious pair takes a struct whose fields are the kernel's
  `long` -- 4 bytes on 32-bit, 8 on 64-bit -- so a single portable
  declaration is impossible and os/linux/time.c would need an #ifdef
  ladder. Taking the *_time64 forms on the 32-bit arches and the plain
  ones on the 64-bit arches makes the struct 8+8 EVERYWHERE, so that
  file is arch-independent. numbers_$cputype.h deliberately aliases both
  to the same SYS_clock_gettime name to keep it that way. It is also
  y2038-correct, and forced anyway on riscv32, which has neither
  gettimeofday nor nanosleep (arch/riscv/include/asm/unistd.h puts
  __ARCH_WANT_NEW_STAT and friends inside #if defined(__LP64__), and
  never defines __ARCH_WANT_TIME32_SYSCALLS at all).

Not runnable under the emulators: plan9's getpid and nsec read "#c/pid"
and "/dev/bintime", and 5i/vi forward open() straight to the host, which
on Linux has neither. The code is right for real Plan9 (it is
principia's); it just cannot be exercised here until the emulators
synthesize those two files. getwd and sleep DO run there, since FD2PATH
and SLEEP are both implemented in machines/{5i,vi}. See todo.org.

_mulv: vlong multiply had never worked in the self-hosted libc
------------------------------------------------------------

Found by nsec()'s "sec * 1000000000LL" -- the first vlong*vlong anything
had ever asked lib_core/libc for. 5l reported "undefined: _mulv"
followed by a cascade of bogus encoding errors on the unresolved BL
("illegal combination BL 0 0 16", "bad rrr 54"), which makes the real
cause easy to miss.

compilers/cc/com64.c and compilers/cck/com64.c both turn vlong*vlong on
a 32-bit arch into a call to _mulv, exactly as they turn + and - into
_addv/_subv. But _addv/_subv are portable C in port/vlrt.c, while a
64x64 multiply needs the machine's widening-multiply instruction, so
upstream Plan9 keeps it in per-arch assembly (libc/$arch/vlop.s) -- and
lib_core/libc had no vlop.s at all, for any arch. Now added for
arm/386/mips/riscv, adapted from principia (arm, 386), plan9front (mips)
and Richard Miller's riscv port, wired via each mkfiles/$cputype/mkfile's
ARCHEXTRAOFILES.

Take ONLY _mulv from those files: they also carry _addv/_subv (and, on
386, _mul64by32/_div64by32), which port/vlrt.c already defines in C
here -- copying wholesale is a duplicate-symbol link error.

Why it hid: tests/c/vlong/ has its own LOCAL copy of vlrt.c and links
against no libc, so it never consulted lib_core/libc's. Gated now by
tests/c/regressions/vlong_mul.c, which links vlrt.c + vlop.s directly
(not -lc) so it does not depend on a freshly-installed per-arch libc.a.

getenv: the environment reached four different ways
------------------------------------------------------------

23 call sites across the toolchain ($objtype, $GOROOT, $PATH lookups),
and no new syscall on any GOOS -- which is the interesting part.

  linux/darwin  NOT a syscall or a call of any kind. The SysV startup
                contract puts the environment on the initial stack
                immediately past argv's terminating nil, so "environ" is
                just argv walked past its own end. Both GOOSes agree
                exactly, so this is port/getenv.c, not os/$GOOS/ --
                the one call in recent tiers where they do.
  plan9         the environment is a DIRECTORY, /env, one file per
                variable. Needs nothing beyond open/seek/read/close.
                Also means it is shared and mutable through the file
                system rather than copied per-process at exec, which is
                why there is no array to walk.
  windows       GetEnvironmentVariableA. Windows does keep a block much
                like the SysV one, but the entry point is handed
                nothing, so it must be asked for rather than walked to.

Getting at the stack copy needed one store per rt0.s: _mainargv (see
port/mainargs.c). argv only, not argc -- getenv.c scans forward to
argv's nil, which needs one global instead of two. _mainargv is defined
in PORTOFILES, i.e. for every GOOS, because arch/$cputype/rt0.s is
SHARED between linux and plan9 (only darwin has its own rt0_darwin.s),
so the store is compiled for plan9 too and the symbol must resolve.

Do not name such a global _argc: include/flag/cli.h's ARGBEGIN already
uses that name for a local Rune.

Two testing notes:

- The sharp edge in any getenv is matching a NAME PREFIX: comparing
  strlen(name) bytes and forgetting to require '=' next makes "PATH"
  match "PATHEXT=...". tests/c/hello_libc/env.c gates both directions,
  and was confirmed to catch it by dropping the '=' test and watching
  it fail.
- env.c tests against $PATH rather than a variable the mkfile sets.
  That was originally because "VAR=val cmd" in an mk recipe did NOT
  reach the child: rc/unix.c's Updenv() was a no-op. THAT IS NOW FIXED
  (see tests/rc/env_export.sh), so a mkfile CAN set a child's
  environment again -- but env.c is deliberately left as it is, since
  testing getenv() against something the harness supplies would couple
  it to bin/rc being freshly promoted.

dirfstat/dirfwstat: the stat family (Tier 3)
------------------------------------------------------------------------

The design that shipped differs from plan_syscalls.txt's original plan
in one real way, worth recording because it wasn't obvious going in:
dirstat()/dirwstat() (BY PATH) are portable, not per-GOOS/arch. Grepping
every actual caller in this tree first (linkers/ar/ar.c, debuggers/
acid/{main,builtin}.c) showed none of them ever calls a raw byte-buffer
stat()/fstat() -- only the Dir*-returning dirstat()/dirfstat() pair.
That means the machine-independent wire format Plan9's own STAT/FSTAT
syscalls speak is not something this tree needs to expose as a portable
API at all: only dirfstat()/dirfwstat() (BY FD) are per-GOOS/arch now,
and dirstat()/dirwstat() are one portable open()+dirfstat()/dirfwstat()+
close() each (port/dirstat.c, port/dirwstat.c). Concretely this means:

  linux/darwin/windows  dirfstat() builds a Dir straight from that OS's
                         own native stat struct/BY_HANDLE_FILE_INFORMATION.
                         No marshal step, no convM2D/convD2M needed.
  plan9                 the ONE GOOS where the wire format is real:
                         FSTAT/FWSTAT genuinely return/expect it, so
                         os/plan9/stat.c needs convM2D/convD2M (ported
                         from principia's lib_core/libc/9sys/, adapted
                         to this tree's own type names -- see
                         os/plan9/stat9p.h, a deliberately tiny fcall.h
                         subset, not a general port).

Known, accepted tradeoff: dirstat()'s open(OREAD)-then-dirfstat() means
something statable-but-unreadable (0300 owned by someone else) would
fail here where a real stat(2) would succeed -- no caller in this tree
hits that. dirwstat()'s open(ORDWR)-then-dirfwstat() has the mirror-
image gap: chmod'ing a currently-read-only file to add write permission
back can't even open ORDWR to try. Both documented in port/dirstat.c
and port/dirwstat.c themselves, not just here.

Per-arch struct-stat layout, and why each source was trusted:

  linux 386/arm    glibc's struct stat64, from GO/pkg/syscall/
                    ztypes_linux_{386,arm}.go -- same 2010-era Go
                    snapshot numbers_386.h's own comment already treats
                    as ground truth for this tree. Note the double
                    inode field (truncated __st_ino vs the real
                    trailing 64-bit ino) -- qid.path uses the latter.
  linux amd64      ztypes_linux_amd64.go's Stat_t. The one field that
                    looks like it should be 4 bytes but is not: Nlink
                    and Blksize are BOTH uint64/int64 on amd64
                    specifically, unlike every other arch here -- easy
                    to get wrong by pattern-matching against arm64's
                    struct instead of checking amd64's own.
  linux arm64/riscv64
                    the Linux "generic" struct stat (asm-generic/
                    stat.h upstream), confirmed against this dev box's
                    own /usr/include/asm-generic/stat.h since it's
                    aarch64 -- resolves natively here, no cross header
                    needed. NOT shared with riscv32: that arch has no
                    fstat/newfstatat syscall at all (scripts/
                    syscall.tbl marks 79/80 64-bit-only), only statx,
                    not implemented -- see numbers_riscv.h.
  linux mips (o32) struct stat64 from arch/mips/include/uapi/asm/
                    stat.h, fetched directly rather than transcribed
                    from memory -- this tree carries no
                    ztypes_linux_mips.go to cross-check against (the Go
                    snapshot only has 386/amd64/arm), and o32 struct
                    layouts have enough padding-field history to make
                    memory risky. Verified correct via real qemu-mips
                    execution, not just compiled.
  darwin amd64/arm64
                    XNU's unified 64-bit stat64 struct, from
                    ztypes_darwin_amd64.go's Stat_t. Same struct on
                    BOTH arches despite different syscall NUMBERS
                    (numbers_arm64.h's own comment: arm64 macOS
                    postdates the stat64 unification, so its plain
                    fstat already returns this shape). Unverified by
                    execution -- no macOS host here, same as every
                    other os/darwin file added blind.
  windows          BY_HANDLE_FILE_INFORMATION via
                    GetFileInformationByHandle, a kernel32 call added
                    to winio_amd64.s -- needed a new linkers/lk/pe.c
                    importfuncs[] entry to even link (same "unlisted
                    import fails to resolve, no relocation pass" story
                    every prior windows call added there hit).

The recurring long-vs-vlong trap, reconfirmed here: every struct field
above that is genuinely 8 bytes on its arch's real kernel ABI (amd64's
Nlink/Blksize, arm64/riscv64's whole "unsigned long" family) has to be
declared vlong/uvlong in the Kstat struct, never this project's own
`long`/`ulong` -- SZ_LONG is 4 bytes in every compiler here regardless
of arch, exactly the same fact syscall_linux_amd64.h's own comment
already documents for syscall *arguments*. Using `long` for one of
these fields would not just truncate one value, it would misalign
every field declared after it.

dirfwstat()'s real, deliberately-scoped gaps (not oversights -- each
documented in the relevant file's own comment, not just here):

  mtime-setting     unimplemented on EVERY arch/GOOS. No caller in this
                     tree sets an mtime yet; would need utimensat (or
                     the *_time64 variant on 32-bit arches), whose
                     numbers were not sourced with the same rigor as
                     fstat's for this pass.
  mips length        mode (fchmod) works, length (ftruncate) does not.
                     o32's calling convention register-pads a 64-bit
                     syscall argument (sys_ftruncate64 takes fd, a
                     dummy word, then a high/low split) -- the same
                     class of arg-marshaling trap as the riscv32
                     llseek bug plan_syscalls.txt already documents,
                     and not worth guessing at blind.
  windows mode        length (SetEndOfFile, via seek-then-truncate)
                     works, mode does not. Win32 has no by-HANDLE
                     chmod equivalent -- SetFileAttributes takes a
                     PATH, which a bare fd/HANDLE here cannot reach
                     (same fd-as-truncated-HANDLE simplification
                     os/windows/open.c's own header comment already
                     flags). Would need SetFileInformationByHandle
                     with a FILE_BASIC_INFO struct, not written here.

Found along the way, and it very nearly made this whole tier untestable
under 5i: machines/5i's sysstat()/sysfstat() (syscall_posix.c) SEGFAULT
the emulator itself (not the guest program -- the host process) the
first time anything actually calls STAT/FSTAT under it. Root cause is
an ARM-specific register-aliasing bug, not a Plan9-libc one:
arm.h defines REGARG and REGRET as the same register (0), and
sysfstat()'s own "reg.r[REGRET] = -1" (an early "assume failure" store)
clobbers reg.r[REGARG] before a later debug line reads it back as
sysctab[reg.r[REGARG]] -- landing on sysctab[0xffffffff] and
dereferencing whatever garbage pointer was there. Confirmed with gdb
(`gdb -batch -ex "run ./x.exe < input" -ex "bt full" 5i`), not guessed:
the backtrace showed reg.r[REGARG] == 4294967295 at the crash site.
Fixed to fail cleanly (drop the %s/sysctab[] read from the debug
message) rather than actually implementing STAT/FSTAT emulation --
that is a real, separately-scoped gap (both are still TODO stubs that
exits(0) the whole emulator), tracked in todo.org next to the existing
getpid()/nsec() device-file gap this tier's own dirfstat() test ran
straight into. vi's mips equivalent never had this exact bug (its debug
message never indexed sysctab[] at all, unlike 5i's) -- confirmed by
plain execution under qemu-mips + vi, no crash, not by re-running the
gdb session (only 5i's crash needed that level of digging).

dirread/dirreadall: listing a directory (Tier 3.5)
------------------------------------------------------------------------

Landed right after Tier 3 above, once dirfstat() made it possible to
actually validate against real utilities (see "compiling real utilities
against the self-hosted libc" below) -- mtime.c and cat.c already ran,
but ls.c needed a way to enumerate a directory's contents, which
dirstat()/dirfstat() alone cannot do (they answer "what is this ONE
named thing", not "what is IN this thing").

  linux    getdents64 (a new raw syscall, one number per arch -- see
           numbers_$cputype.h) gives names (+ a cheap d_type hint this
           code ignores) in a batch per call; each name is turned into
           a full Dir by openat(dirfd, name, ...) (a NEW public raw
           wrapper on 386/amd64/arm/mips; arm64/riscv64/riscv already
           had it, generated for _sysopen's own AT_FDCWD bridge) + this
           file's own dirfstat(). Folded into the SAME per-arch
           stat_$cputype.c files as dirfstat/dirfwstat, not a separate
           OFILES entry -- it depends on the exact same fstat, so it
           inherits the exact same riscv32 exclusion for free by living
           in the same file.
           One real trap avoided, not hit: mips is this project's one
           BIG-ENDIAN target (include/arch/mips/u.h's own header
           comment). Reading linux_dirent64's d_reclen field via manual
           byte-shifting (`buf[16] | buf[17]<<8`) would have been
           silently wrong there. Reading it through a real typed C
           struct instead (`struct Dirent64 { uvlong ino; vlong off;
           ushort reclen; uchar type; char name[1]; }`) sidesteps the
           whole question -- the COMPILER decodes the multi-byte field
           in the target's native endianness, the same way it already
           does for every other struct field in this codebase. Verified
           correct on real qemu-mips execution, not just reasoned about.
  plan9    ported near-verbatim from principia's lib_core/libc/9sys/
           dirread.c (os/plan9/dirread.c) -- on Plan9 a directory is
           just a file whose read() returns back-to-back packed stat
           entries, the exact same wire format os/plan9/stat.c's
           dirfstat() already unpacks ONE of via convM2D. dirpackage()
           is the only real logic: walk the buffer finding each entry's
           boundary via statcheck() (ported alongside convM2D -- it was
           skipped when convM2D.c first landed since nothing called it
           yet) and convM2D() each one. Blocked on the SAME 5i/vi FSTAT
           gap Tier 3 already found (this needs a working read()-of-a-
           directory under the emulator too, itself untested) -- built,
           not run, same as stat_plan9_*.exe.
  darwin/windows
           NOT implemented -- deliberately deferred, not forgotten
           (todo.org has the gap entry). Unverifiable by execution here
           regardless (no host), and each needs real new work rather
           than a small extension: darwin wants getdirentries64 (BSD,
           different shape from Linux's getdents64), windows wants
           FindFirstFileA/FindNextFileA stubs plus new linkers/lk/pe.c
           importfuncs[] entries.

Design note distinct from dirfstat's own: dirread() returns whatever
fit in ONE getdents64 batch, not an artificial fixed count. BOOT/lib9's
own host-hosted dirreadmax() caps at 10 readdir() calls per dirread()
invocation purely because host readdir() hands back one entry at a
time and needed SOME cap; raw getdents64 has no such constraint, so
capping at all would have been copying a host-library limitation this
code doesn't share, not matching a real Plan9 semantic.

minimal repro before fixing:

  - `#ifdef Unix ... #include <fcall.h> ... #endif`: the file's own

    since the fix costs nothing (const was purely documentation here).

  - `include/base/ord.h` (EQ/INF/SUP enum, `ord` typedef) exists but

gmtime()/localtime()/asctime()/ctime()/tm2sec() -- the date/time stack
------------------------------------------------------------------------

Investigated by grepping/finding for gmtime/localtime/tm2sec/asctime/
ctime across lib_core/ before writing anything: ALL FIVE were entirely
unimplemented, despite gmtime()/localtime()/tm2sec() being declared as
if already available in include/os/time.h (only asctime()/ctime()
were commented out) -- a materially bigger gap than "just ctime()"
looked like from the header alone.

Found a ready reference before writing anything from scratch (the same
discipline dirread() followed): principia-softwarica's
lib_core/libc/9sys/ctime.c (gmtime/localtime/asctime/ctime) and
lib_core/libc/9sys/tm2sec.c (tm2sec) -- both textbook, decades-old
Plan9 libc code, ported near-verbatim into two new portable files,
port/ctime.c and port/tm2sec.c (lib_core/libc/mkfile's PORTOFILES),
matching the original's own split into two translation units (each
with its own private copy of a `timezone` struct + readtimezone()/
rd_name()/rd_long(), rather than a shared internal header neither
original file had).

Why port/, not os/$GOOS/: unlike dirfstat() (Tier 3), nothing here is a
raw syscall -- it's pure calendar arithmetic plus one best-effort
open()+read()+close() of a Plan9-shaped "/env/timezone" config file
(TZ name/offset/DST-pairs, plain text). On every GOOS other than
plan9 that file simply doesn't exist: open() fails, readtimezone()
falls through to its error label, and localtime() becomes a GMT-only
alias for gmtime() -- graceful degradation, not a "too Plan9-specific"
API-shape call the way dirfstat()'s design had to weigh (see
plan_syscalls.txt) -- just an optional config file no non-plan9 caller
ever needs to provide.

Two real findings while writing tests/c/hello_libc/ctime.c (fixed
expected strings, not the port itself -- the ported code matched
Plan9's real behavior in both cases):

  - ct_numb() (port/ctime.c) SPACE-pads a single-digit day of month
    ("Jan  1", two spaces) -- the classic ctime(3) format, not
    zero-padded ("Jan 01"). A first guess of "Jan 01" for ctime(0) was
    written into the test, then disproved by an actual qemu run
    ("ctime(0): wrong string: Thu Jan  1 00:00:00 GMT 1970") before
    being corrected -- caught by running the test, not by re-reading
    the ported code more carefully.
  - Pre-1970 (negative tim) is NOT correctly handled by this exact
    algorithm, and is NOT this port's own regression: gmtime()'s
    `hms = (ulong)tim % 86400L; day = (ulong)tim / 86400L;` mixes a
    ulong-cast dividend with a plain `long` (signed) divisor. The usual
    arithmetic conversions promote the whole expression to unsigned
    (confirmed directly against this project's own 6c, not assumed
    from the C standard: a 3-line repro of exactly this expression with
    tim=-86400 printed hms=23296, day=49709, not the small negative
    values the very next line's `if(hms<0){hms+=86400;day-=1;}`
    fix-up is written to expect) -- so that fix-up is dead code, and
    gmtime(-86400) lands in the year 2106 instead of 1969. This is
    upstream Plan9 libc's own long-standing behavior, faithfully
    reproduced from principia's ctime.c byte-for-byte in the algorithm
    that matters -- Plan9 systems don't see pre-1970 clock values in
    practice, so it likely was never exercised there either.
    tests/c/hello_libc/ctime.c documents this and deliberately does
    NOT test a negative epoch's exact ctime() string (round-tripping
    tm2sec(gmtime(t)) for t>=0 is tested instead).

Verified: tests/c/hello_libc/ctime.c (gmtime(0)'s exact fields incl.
wday=4/Thursday and yday=0; three ctime() strings incl. the 2000s
"20YY" asctime() branch; three tm2sec(gmtime(t))==t round-trips) passes
under a full `mk test` (all 7 Linux arches via qemu) AND `mk test_plan9`
(arm/5i, mips/vi) -- the latter actually RUNS end-to-end and passes
(unlike stat.exe/dirread.exe/proc.exe/env.exe, which are build-only
under 5i/vi due to real emulator gaps -- see those targets' own mkfile
comments), since ctime()'s only OS dependency (the /env/timezone
read attempt) degrades gracefully there the same way it does on every
non-plan9 GOOS.

utfrrune()/strrchr()/strncpy()/atexit()/dirmodefmt() -- finishing ls.c
------------------------------------------------------------------------

Retried utilities/files/ls.c right after the ctime() work above landed
(user explicitly asked to keep going on it). It now compiled cleanly
(0 errors) but did not link -- two, then a cascading few more, gaps,
each found by actually trying to link/run, not by re-reading ls.c:

  - utfrrune() (ls.c's xcleanname() calls it): the file EXISTED
    (lib_core/libc/utf/utfrrune.c, Go-era) but was never added to
    UTFOFILES, so simply missing from libc.a. While wiring it in, its
    signature turned out to use `const char*`/`Rune` (matching Go-code
    style, not this compiler's proven-shaky const support, see ls.c's
    own earlier `ord`-after-a-pointer 6c bug) and called strrchr(),
    which didn't exist anywhere -- so per this session's user
    instruction ("take principia code as is when possible, with a
    plain copy of the original file"), the Go-era body was replaced
    wholesale with a plain copy of principia's lib_core/libc/port/
    utfrrune.c (`char*`/`long`, no const) -- kept at its existing
    utf/ path (this tree's own Go-era directory split), not moved to
    port/ the way principia has it. include/utf/utf.h's own
    declaration had the same const/Rune mismatch and was fixed to
    match (principia's include/core/libc.h declares it the same plain
    way too, confirmed before assuming this was safe).
  - strrchr() itself: didn't exist at all (include/base/str.h had it
    commented out). Plain copy of principia's lib_core/libc/port/
    strrchr.c (built on strchr(), already present).
  - atexit(): declared (include/os/proc.h) but nowhere implemented --
    found via Binit() (ls.c's Biobuf setup) reaching lib_core/libbio/
    binit.c's install(), which calls it. principia's lib_core/libc/
    port/atexit.c defines BOTH atexit() (an onex[] table of (callback,
    pid) pairs) AND exits() itself (looping onex[] then calling
    _exits()) -- but this tree already has its own port/exits.c,
    per-GOOS-collapsed onto exit(int), predating this session and
    with its own header comment already flagging "if an atexit-driven
    cleanup layer is ever added...". Reconciled by taking atexit.c's
    atexit()/onex[] table as a plain copy but NOT its exits() (would
    have been a duplicate-symbol conflict) -- instead exposing a
    non-static atexitrun() helper that port/exits.c's own exits() now
    calls before exit(), matching the exact "exits() runs atexit
    handlers, _exits() doesn't" split include/os/proc.h's comment
    already promised. Verified the LIFO-order semantics (most-recently-
    registered callback runs first) directly with a throwaway 2/3-
    callback repro before trusting the real test.
    GAP: plan9's own exits(char*) is a raw EXITS syscall trampoline
    (os/plan9/_exits.$O), which never calls atexitrun() at all -- found
    by actually running tests/c/hello_libc/atexit.exe under 5i (it
    printed nothing before "exits(0)" where "atexit ok" was expected,
    not a crash), not assumed from reading the mkfile. atexit()-
    registered callbacks are therefore inert on plan9 specifically;
    todo.org tracks it, and the plan9 build targets are build-only
    (not run), matching stat.exe/proc.exe/env.exe's own precedent.
  - dirmodefmt(): the %M fmtinstall() verb ls.c's format() uses for
    `-l` (`"%M %C ..."`) didn't exist at all -- its installer call was
    commented out in ls.c (`//XXX: fmtinstall('M', dirmodefmt);`),
    presumably because the function never existed to install. Wiring
    it in (uncommenting that line) without first ADDING dirmodefmt()
    was tried and produced a real crash, not a link error: an
    unrecognized fmt verb doesn't consume its vararg, so every
    argument after %M (including %*q's char* pointers) read one slot
    stale, and `ls -l` segfaulted on the resulting garbage pointer --
    confirmed by an actual qemu run before diagnosing, not assumed
    from reading format(). Fixed with a plain copy of principia's
    lib_core/libc/9sys/dirmodefmt.c (dropping its #include <fcall.h>:
    this tree already defines DMDIR/DMAPPEND/DMAUTH/DMEXCL in
    include/os/dir.h, no separate fcall.h exists here), which itself
    needed strncpy() (also missing entirely -- plain copy of
    principia's lib_core/libc/port/strncpy.c) for its rwx() helper.
