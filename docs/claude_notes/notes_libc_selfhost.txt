Self-hosting a real libc.a: lib_core/libc/{fmt,port,syscall,arch}/, Linux
==========================================================================

Notes on building a genuinely reusable, self-hosted C library --
lib_core/libc/, producing libc.a -- compiled entirely by goken's own
Xc/Xa/Xl toolchain (not gcc/clang), as opposed to every prior test in
this tree, which either links no library at all (tests/c/mini/) or
links against a hand-rolled, per-test assembly stub duplicated in each
test directory (tests/c/mini2/linux_$arch.s, tests/c/vlong/vlrt.c+
print.c). Linux only so far; arm64, amd64, mips, riscv, riscv64, 386,
and arm are all done now -- every arch this project's toolchain
targets on Linux. The directory layout (lib_core/libc/{os,arch,
syscall}/ split by $OS and $cputype) was built to make adding archs
additive, and stayed that way through all seven; the same discipline
still applies to any future OS this gets extended to (darwin, windows,
plan9, xv6): verify every ABI claim empirically for the new target
(via `Xc -S` probes *and real execution*, not -S alone -- see below)
rather than assuming it matches an existing one. No two arches here
actually agree on every axis: arm64/mips/arm/riscv share register-
passing for the first arg, amd64/386 don't; arm64/amd64 share
uniform-8-byte slot width, mips/arm/386/riscv share natural-packing
instead; riscv alone additionally needs an 8-byte-alignment rule none
of the others have; 386/arm agree with mips on natural-packing but
(being little-endian, unlike mips) need little-endian sub-word
placement instead of mips's big-endian one.

Read docs/claude_notes/notes_arch_{amd64,mips,riscv,x86,arm}.txt's own
relevant sections for the full per-arch ABI write-ups (calling
convention, varargs slot layout); this file is the cross-cutting
design story and the bugs found along the way that weren't purely
arch-specific.

Why this exists: fmt/*.c wants a real libc, not a per-test stub
------------------------------------------------------------------------

lib_core/libc/fmt/*.c (Plan9's real, portable printf implementation)
is byte-identical to BOOT/lib9/fmt/*.c (symlinked, so gcc's BOOT build
and goken's own self-hosted build share one copy of the source) -- the
goal was to get goken's own Xc compilers to build *that*, plus enough
Linux syscalls (write, exit) to actually run a program, rather than
keep writing one-off minilibc stubs per test. tests/c/mini2/linux_$arch.s
and tests/c/vlong/vlrt.c+print.c stay exactly as they are; this is
purely additive infrastructure alongside them, not a replacement.

Hard constraint carried through every file added here: lib_core/ code
may only #include headers under include/, never a Unix/host header
directly (that's lib9/'s privilege, not lib_core/'s) -- see
include/arch/$cputype/u.h's own header comment on every arch.

Directory layout
------------------

    lib_core/libc/
      fmt/, utf/, math/     -- portable (symlinked from BOOT/lib9/{fmt,utf})
      port/                 -- portable, but goken-only (memmove.c,
                                strlen.c, ctype.c, vlrt.c, ... -- either
                                copied from ~/principia/lib_core/libc/port/
                                verbatim, preserving syncweb markers, or
                                new but OS/arch-independent)
      arch/$cputype/rt0.s   -- process startup (_main), one per arch
      syscall/arch/$cputype/svc.s        -- the *one* raw syscall
                                             trampoline per arch
      syscall/os/$OS/*.decl              -- declarative syscall specs
      syscall/os/$OS/numbers_$cputype.h  -- syscall number constants
      syscall/os/$OS/zsyscall_$OS_$cputype.c -- generated (see below);
                                             committed to the repo

include/arch/$cputype/u.h holds each arch's base scalar typedefs plus
va_list -- adapted from ~/principia/lib_core/libc/{arm,mips}/u.h and
include/arch/{arm,386}/u.h where an arch's own file already exists
there (mips's is copied close to verbatim; amd64 has no principia
equivalent, since principia never had an x86-64 arch, so it was built
fresh by empirical `6c -S` probing, following the same structure).
Trimmed relative to principia's fuller versions -- no Rune/jmp_buf/
mpdigit/FCR-FSR flags yet, since nothing under lib_core/libc uses them
so far; add them, matching principia's shape, when something does (the
user's stated intent is to eventually sync these files with principia
via syncweb the way mk/rc/the arm toolchain/utilities/ already are, so
staying close to principia's existing shape now, rather than
inventing a divergent one, is deliberate).

riscv/riscv64 have no principia or 9front equivalent to draw from at
all (see plan9front.txt's "riscv" section) -- their u.h files are
instead adapted from ~/xxx/miller-riscv/ROOT/{riscv,riscv64}/include/u.h
(Richard Miller's Plan9 riscv port), credited there. Same "adapt, don't
blindly trust" discipline applied: miller-riscv is a different,
independently-implemented compiler, so every va_start/va_arg claim
from it was re-verified against this project's own ic/jc -S output and
real qemu execution -- worth doing even when a seemingly-authoritative
reference exists, since it caught a genuine, riscv64-specific bug (see
below) that a straight copy would have carried over silently (miller's
own u.h actually gets it right; the bug was in an early draft of
*this* project's adaptation, not in the source being adapted from).

Declarative syscalls, Go-`mksyscall.sh`-style
------------------------------------------------

Per explicit design direction: a small `//sys name(args) (ret) =
SYS_NAME` comment spec (syscall_$OS_$cputype.decl), in the spirit of
GO/pkg/syscall/mksyscall.sh, parsed by scripts/mksyscall.sh (POSIX
sh+awk, matching this project's existing script-language convention --
no new language dependency) into a generated C file
(zsyscall_$OS_$cputype.c) with one thin wrapper per syscall, each just
calling a single generic `_syscall6(num, a1..a6)` trampoline (mirroring
Go's own Syscall6: always lower to the widest arity, pad unused
argument slots with 0, rather than one hand-written asm entry point
per syscall or per arity). Adding a syscall is then a one-line .decl
addition, no new assembly, *except* on mips, where a syscall needing a
5th/6th argument would need svc.s itself extended (see
notes_arch_mips.txt) -- not needed yet since only write/exit are
wired up.

One arch needs a variant of the generic wrapper shape: riscv64's
`long` is only 4 bytes (see below), so a pointer argument cast through
the default `(long)` would truncate before ever reaching _syscall6.
scripts/mksyscall.sh takes an optional 2nd positional argument (the
cast type, default "long") for exactly this -- lib_core/libc/mkfile
passes "vlong" only for riscv64's generation rule. Deliberately a
positional argument, not an environment variable: this project's rc
(rc/unix.c) has a no-op Updenv(), so a `VAR=val cmd`-shaped mkfile
recipe silently fails to actually set the variable in the environment
a forked subprocess (like this script, or its own awk) sees -- a
positional argument has no such dependency and was not worth
re-verifying whether the bug still applies.

zsyscall_*.c is deliberately committed to the repo, unlike most
generated files in this tree (.gitignore excludes y.tab.[ch], for
instance) -- see lib_core/libc/mkfile's own comment on the generation
rule for the full rationale (small reviewable glue code; and once
syscall numbers stop being hand-written and start getting scraped from
each target OS's own kernel headers, generating this file will require
a host of that OS, so committing the output is what lets goken
cross-compile for an OS you don't have).

Verifying an arch's calling convention before trusting it
--------------------------------------------------------------

The one recurring risk in this work: assuming a new arch's ABI matches
an arch already done, instead of checking. The concrete methodology
used for amd64 and mips (and arm64 before them, in the original pass):
write a tiny throwaway .c file with a fixed-arg function taking mixed
types (int, long, double, in different orders) and compile it with
`Xc -S`, reading the emitted FP-relative offsets directly off the
listing -- this reveals both the per-argument slot width/padding rule
(arm64/amd64: uniform 8 bytes regardless of type; mips: exact
sizeof(), no padding) and, separately, whether the *first* named
parameter arrives via a register (arm64, mips: yes, via R0/R1 --
readable directly in hand-written asm with no compiler prologue, but
only spilled to its FP+0 home slot by a *compiler-generated* function,
and only if that function's own code takes the argument's address) or
purely via the stack like every other argument (amd64: yes -- the
caller writes even the callee's first argument to the stack before the
CALL, confirmed by probing a variadic call *site*, not just a
function's own prologue). This second fact directly decides whether
that arch's svc.s needs a register-vs-FP special case for `num` (arm64,
mips, riscv/riscv64: yes; amd64: no, `num+0(FP)` just works). Do not
skip this step for a future arch on the assumption that "it's another
32-bit RISC arch, it'll be like mips" or "it's another 64-bit arch,
it'll be like arm64" -- amd64 shares arm64's slot-width rule but not
its register-passing rule; mips shares arm64's register-passing rule
but not its slot-width rule; riscv shares mips's natural-packing rule
*and* needs an 8-byte-alignment rule neither arm64 nor mips has (see
notes_arch_riscv.txt). No two arches done so far actually match on
every axis -- and for riscv specifically, -S inspection alone once
gave a wrong answer that only real qemu execution caught (see that
same notes file); trust execution over static reading when the two
disagree.

Bugs found along the way (not arch-specific ABI facts -- see the per-arch notes for those)
------------------------------------------------------------------------------------------------

- fmt/fltfmt.c's xsub1() fell off the end after abort() with no
  `return` statement -- harmless (abort() never returns) and silent on
  gcc/7c, but 6c treats it as a hard error ("no return at end of
  function"). Fixed with an explicit unreachable `return 0;`. Trivial,
  no dedicated regression test (a missing-return compile diagnostic,
  not a behavioral bug).

- compilers/cc/com64.c (the newer frontend) already handles a
  vlong-typed `?:` used as a call argument; src/cmd/cc/com64.c (the
  older, separate frontend that 7c/vc/ic actually build against) was
  missing the same OCOND/OLIST/OCOMMA cases and hit "unknown vlong
  %O". Only surfaced on mips (vc) and riscv (ic) because arm64/amd64
  are 64-bit-native and never enter this vlong-emulation code path at
  all (`machcap()` bails out immediately for them); ic/jc share the
  fix (both link against the same src/cmd/cc/cc.a) but needed a
  separate relink after the fix landed to actually pick it up -- an
  easy step to forget when a fix lands in a *library* multiple final
  binaries link against, not the binary you're testing directly. Full
  writeup, including exactly which nodes fail and why, in
  docs/claude_notes/notes_shared_frontend_bugs.txt.

- linkers/vl/obj.c's and linkers/il/obj.c's objfile() both resolved
  `-lXXX` straight to a hardcoded `/usr/{v,i}lib/libXXX.a`, never
  consulting the `-L` list at all (linkers/7l/pobj.c's equivalent
  already does this correctly via findlib()). Same fix ported to both
  (il needed one extra step: a forward declaration of findlib(), since
  unlike vl's file, il/obj.c defines objfile() textually before
  findlib()). This is now the *second* occurrence of this exact bug
  shape -- worth checking 5l/6l/8l before assuming they're fine. Full
  writeup in notes_arch_mips.txt (vl) and notes_arch_riscv.txt (il).

- riscv64-only: `long` stays 4 bytes there (like every Plan9 C
  compiler in this tree) despite riscv64 having 8-byte pointers, so
  anything typed `unsigned long`/`long` as a stand-in for "pointer-
  wide integer" (a va_arg alignment computation, a syscall trampoline
  argument) silently truncates. Not a compiler bug -- a real property
  of this arch that's easy to get wrong when adapting a `ulong`-based
  uintptr/intptr pattern that's correct on arm64/amd64 (where `long`
  really is 8 bytes). Full writeup in notes_arch_riscv.txt.

- arm-only: a genuinely new linkers/5l bug, and the one item on this
  list that checked out and confirmed 5l specifically (per the "worth
  checking 5l/6l/8l" note above -- 6l/8l turned out fine, having no
  equivalent divide-helper-lowering machinery at all). arm has no
  hardware integer divide, so 5c lowers it to calls to runtime helpers
  (_div/_divu/_mod/_modu); 5l's own logic for resolving those
  (initdiv(), noop.c) only ever looked at program text already loaded
  by the time it runs, which is *after* the point where pulling a new
  definition from a library is still safe -- so a program needing them
  from an actual library (as opposed to a directly-named object file,
  what every prior arm test in this tree did) failed to link. Checked
  against both ~/xxx/9front/5l/ and ~/principia/linkers/5l/: same bug,
  present and unfixed in both -- this is goken-original work, not a
  ported fix. Full writeup, including why principia's own arm kernel
  build never happened to trigger it, in notes_arch_arm.txt.

Verification
--------------

Each arch: `lib_core/libc && mk 'objtype='$cputype 'cputype='$cputype
all` (builds libc.a and installs it to ROOT/arch/$cputype/lib/), then
tests/c/hello_libc (`mk 'objtype='$cputype 'cputype='$cputype
test_one`) -- compiles hello.c against libc.a via `-lc`, links with
`-E _main`, and runs the result through scripts/qemu-runner explicitly
(not relying on binfmt_misc, per that script's own stated rationale --
this host has binfmt_misc registered for every arch already, which
silently masked the qemu-runner omission in tests/c/hello_libc/mkfile
until it was added; ./hello.exe "just working" is not proof
qemu-runner is actually being invoked, check the mkfile). All seven
arches (arm64, amd64, mips, riscv, riscv64, 386, arm) pass this. Full-
tree regression check after any change to shared code (com64.c,
vl/obj.c, il/obj.c, 5l/{main,noop,l}.c, fmt/fltfmt.c all being shared
with the gcc/BOOT build and/or other arches): `mk 'objtype=boot-gcc'
all` from the repo root -- and after touching anything under
src/cmd/cc/ specifically, remember every one of 7c/vc/ic (and jc, the
same binary as ic) needs relinking, not just recompiling, to pick up a
fix landed in that shared cc.a -- plus tests/c/vlong's own multi-arch
test (the most relevant existing regression coverage for the
com64.c/vlrt.c-adjacent changes), tests/c/mini2's, and
tests/c/regressions' (arm_div_from_lib.c specifically, for the 5l fix).
