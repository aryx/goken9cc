The alpha toolchain (za/zc/zl): reintroduction and first working binary
==========================================================================

Notes from bringing linkers/zl up to a working Linux ELF binary in
August 2026, as the first real milestone after "alpha: Reintroducing
alpha toolchain from Plan 9 4th ed" reintroduced za/zc/zl under the
'z' letter. This file is about alpha's own codegen/ABI/build-system
quirks; for how the '7' -> 'z' rename came about at all, see
git log on linkers/zl, assemblers/za, compilers/zc. See also
linkers/lk/elf.c (shared ELF writer, used by zl same as il/vl/6l/8l),
tests/s/exit/exit_linux_alpha.s.

Why the letter is 'z', not '7'
-------------------------------

Old Plan 9 4th edition / 9front used '7' for alpha. This project later
repurposed '7' for arm64 (assemblers/7a, linkers/7l, compilers/7c are
all arm64), so the reintroduced alpha toolchain uses 'z' instead
(assemblers/za, compilers/zc, linkers/zl, include/objexec/z.out.h).
The imported source still had 'thechar = \'7\'' and "7l"/"7.out"/".7
file" strings left over from before the rename -- za already had
thechar='z' from the start, zl did not until this pass. Grep for
literal '7' in a freshly-imported zl/zc/za file before trusting it;
the old value compiles fine (it's just a char), so nothing catches a
leftover '7' except reading the actual output/error strings.

l.h had no EXTERN: silent until modern gcc's -fno-common default
----------------------------------------------------------------------

zl/l.h's big global-variable block (HEADR, HEADTYPE, INITTEXT, hunk,
symsize, ... ~60 vars) was a straight copy from the original Plan 9
4th edition source: plain tentative definitions with no `EXTERN`
macro, one per line, included as-is by every .c file in the linker.
This relies on old-style "common symbol" linking (every TU's tentative
definition of the same name merges into one), which was the default
behavior of every C compiler for decades but is NOT gcc's default
since gcc 10 (-fno-common). The result: it *compiles* cleanly (no
error until link time), then fails at the final link step with a wall
of "multiple definition of `X`; Y.o: first defined here" for every one
of those ~60 globals, once every .c file's .o gets linked together --
completely silent until that point, unlike a normal missing-symbol
bug. vl/6l/8l/il already carry the fix (every one of those globals
prefixed with `EXTERN`, `#define EXTERN` added before `#include "l.h"`
in exactly one file -- obj.c, by convention); zl now matches. If a
future arch gets reintroduced from an old, pre-EXTERN-convention Plan
9 source tree the same way alpha was, expect the identical failure
mode and the identical fix.

See also tests/s/mini/hello_linux_alpha.s and its own section below
(the setSB/gp truncation bug) for the second real bug this bring-up
found, once a test finally touched .data.

elf.c needs wput/wputl/lputl/llput/llputl/cput/strnput to exist by name
---------------------------------------------------------------------------

linkers/lk/elf.c is shared verbatim across every linker that wants ELF
output. Critically, it does NOT take its byte-order put-functions as
parameters -- elf32()/elf64() do `putl = lput; putw = wput;` (or the
_l-suffixed pair for little-endian) by direct symbol name, so every
linker's own asm.c must define global functions under those exact
names (wput, wputl, lput, lputl, llput, llputl) plus cput/strnput as
real callable symbols (not just a local macro), even for an
architecture like alpha that only ever exercises the *l (little-
endian) half at runtime -- the compiler still needs the BE-slot names
to exist for the `putl = lput;`-style assignment to typecheck/link.
zl/asm.c pre-existed with only a `lput` (already little-endian, LPUT
macro) and a `lputbe`/`vlput` pair under non-matching names; the
native-format header cases (HEADTYPE 0-3, Plan9/Unix-alpha a.out
variants, all pre-dating ELF support here) already depend on `lput`
staying little-endian, so it was left alone rather than renamed to
match the BE-slot convention -- the new wput/llput genuinely implement
big-endian (dead code for alpha, but correctly labeled), while
wputl/lputl/llputl are the ones that actually run. cput was only a
local uppercase CPUT() macro in asm.c, invisible to elf.c's own
translation unit; promoted to a real `#define cput(c) ...` in l.h
(matching 6l/l.h's own convention) plus a genuine strnput() function.

compat.c (mysbrk) had been commented out of the mkfile
---------------------------------------------------------

zl/mkfile had `compat.$O` commented out, so obj.c's gethunk() (which
calls mysbrk()) failed to link. Other linkers (6l, 8l) have since
migrated off this hunk/bump-allocator entirely in favor of real libc
malloc() (see notes_libc_selfhost.txt-style comments in their own
compat.c, and the "simplify linker allocators" cleanup already
tracked elsewhere) -- zl has NOT been migrated yet, it's still on the
original fake malloc/free/calloc/realloc/mysbrk family via compat.c,
same starting point 6l/8l were once at. Re-enabling compat.$O in the
mkfile was enough to get zl linking; doing the same gethunk-removal
pass 6l/8l already went through is follow-up work, not a prerequisite.

The EM_ALPHA gotcha: 41 is registered but wrong; Linux wants 0x9026
------------------------------------------------------------------------

The ELF spec's officially registered e_machine value for Alpha is 41
(glibc's elf.h calls this EM_FAKE_ALPHA). Linux's actual Alpha port --
and so qemu-alpha, which emulates the Linux ABI -- never adopted that
value; it still expects the old pre-standardization value 0x9026
(glibc's elf.h calls *this* one EM_ALPHA, the confusing part). A
binary built with e_machine=41 looks entirely plausible (readelf even
labels it "Digital Alpha (old)", easy to misread as "not the modern
one, needs updating to 41"), but qemu-alpha flatly refuses it:
"Invalid ELF image for this architecture", no other diagnostic.
linkers/lk/elf.h's ALPHA constant is 0x9026 for exactly this reason --
do not "fix" it to 41 without re-testing under qemu-alpha.

HEADTYPE 7 (ELF Linux) layout, and alpha's 8192-byte page size
--------------------------------------------------------------------

zl's HEADTYPE 7 (added in zl/obj.c and zl/asm.c) mirrors il/vl's own
HEADTYPE 7 exactly: HEADR = rnd(Ehdr64sz+3*Phdr64sz, 16), a page-
aligned data-segment offset (`rnd(HEADR+textsize, INITRND)`, both for
the actual seek() before writing data and for the symbol-table seek
after it -- ELF requires vaddr mod page == file-offset mod page), and
`elf64(ALPHA, ELFDATA2LSB, 0, nil)` for the final header emission with
debug['S']=1 to also emit section headers. The one alpha-specific
number: INITRND (and so the data segment's page alignment) is 8192,
not the 4096 il/vl default to -- alpha Linux genuinely uses an 8KB
page size, matching what zl's own pre-existing native-format
HEADTYPE 2 ("plan9 format", INITRND=8192) already assumed. INITTEXT
defaults to 0x10000+HEADR (il/vl's own small ELF base), deliberately
NOT the real, conventional 0x120000000 Alpha/Linux non-PIE base that
zl's HEADTYPE 0 ("unix simple") already had hardcoded -- see the next
section for why that address doesn't actually work through this
linker.

The setSB/gp truncation bug: span()'s classification runs too early
-------------------------------------------------------------------------

Found via tests/s/mini/hello_linux_alpha.s (the exit(42) test has no
.data segment and so never exercises this at all). Symptom: the
program assembled and linked with no errors or warnings, ran, exited
0, but produced no output. Root-caused by tracing actual executed
instructions with `qemu-alpha -d in_asm,cpu` (objdump has no alpha
target on this host; `zdb`/`zobj` are only compiled into libmach.a,
not built as standalone tools -- see notes_libmach.txt) rather than
reading the assembler/linker source first.

The mechanism: `MOVQ $setSB(SB), R29` is the standard Plan 9 static-
base/gp setup (same idiom as riscv's `MOVW $setSB(SB), R3`, see
tests/s/mini/hello_linux_riscv64.s), resolving to the pseudo-symbol
"setSB" whose value is `BIG` (32760, l.h's ldgp-style constant).
span.c's aclass() has a special "botch" case (the original Plan 9
source's own comment) recognizing this symbol and resolving its real
value to `BIG+INITDAT`. This value drives which of two very different
code shapes optab.c picks: C_LCON -> case 15 in asm.c, a 2-instruction
lda+ldah pair that only ever encodes the low 32 bits of the target
(compare case 16's C_QCON, a real 5-instruction 64-bit load using
v>>32 and v>>48 too). The original "botch" branch always returned
C_LCON, unconditionally -- with HEADTYPE 0's INITTEXT=0x120000000,
BIG+INITDAT doesn't fit in 32 bits, so the encoded gp silently lost
its high bit and became ~0x20000000 instead, and every SB-relative
access (e.g. `$msg(SB)`, encoded as gp-relative) was corrupted downstream.
That INITTEXT value already carried a "/* BUG */" comment in the
original imported source -- almost certainly the same bug, just never
caught because nothing ever ran HEADTYPE 0 (no test, no Alpha hardware
or native-a.out emulator available; see the closing section below).

Widening the bound check alone (`return C_QCON` when BIG+INITDAT
doesn't fit in 32 bits, span.c's aclass()) turned out to be necessary
but NOT sufficient: oplook() (also span.c) caches the chosen optab
entry -- and therefore the instruction's byte size and shape -- in
`p->optab` the first time it classifies a given Prog. For the setSB
instruction that first classification happens during span()'s own
sizing loop, which runs BEFORE span() computes the real INITDAT (its
`INITDAT = rnd(c, INITRND)` assignment is the very last thing span()
does, after the loop that sizes every instruction including this one).
So aclass() always observes INITDAT==0 at the point that matters, sees
BIG+0 (fits comfortably in C_LCON), and that 2-instruction shape gets
locked into `p->optab` for good. asmb()'s later re-evaluation of the
same instruction (now with the correct, final INITDAT) can still
change the *value* it computes (regoff() has no cache, unlike
oplook()) but can no longer change the already-cached *shape* --
so it re-derives the correct large offset and then silently truncates
it through the same 2-instruction encoding. Confirmed by instrumenting
oplook()/aclass() directly (temporary fprint(2, ...) calls, since
p->optab's caching wasn't obvious from reading the code alone -- do
this again before assuming a span.c/asm.c fix "should" work; verify
with qemu-alpha -d, not by re-reading the source more carefully).

Real fix applied here: keep INITTEXT small enough (0x10000+HEADR, see
above) that BIG+INITDAT never leaves the 32-bit range the existing
2-instruction form can actually encode, sidestepping the bug rather
than fixing span()'s classify-before-INITDAT-is-known ordering. A
proper fix (computing text size and INITDAT in a first pass before
classifying/sizing any instruction that depends on it, or just always
picking C_QCON conservatively for anything BIG-relative regardless of
apparent size) would let HEADTYPE 7 use the conventional 0x120000000
base too, and is the more principled fix for HEADTYPE 0 as well --
not done here, out of scope for getting one working ELF binary.

Alpha Linux syscall ABI, as used by tests/s/exit/exit_linux_alpha.s
-------------------------------------------------------------------------

Inherited from OSF/1, quite different in *mechanism* from every other
arch here even though the register roles are familiar: v0/R0 holds the
syscall number going in and the return value coming out; a0-a5 are
R16-R21. The trap instruction is `CALL_PAL $0x83` (za's grammar:
LTYPEE takes a single `$`-prefixed immediate -- see assemblers/za/a.y,
lex.c's "CALL_PAL" entry), i.e. what OSF1/Linux call "callsys" as a
PAL-code call rather than a dedicated syscall/trap opcode the way
SVC/ECALL are on arm/riscv. exit is syscall number 1 -- same numeric
value as x86 (both trace back to the same old Unix numbering), not 93
like arm64/riscv.

zc build fixes: the same int32/const-qualifier gap vc already closed
-------------------------------------------------------------------------

zc shares its frontend with vc/5ck/8ck/etc. via compilers/cck/ (pgen.c,
pswt.c, cc.h), the same shape of relationship zl has with linkers/lk/.
The compile errors here were the exact same class already fixed once
for vc when it was brought up, just not yet ported to zc's own gc.h/
swt.c/txt.c:
- swt.c's align()/maxround() were declared `long` locally but cc.h's
  shared prototype is `int32` -- harmless on this 64-bit host where
  long and int32 differ in width but not in practice, until the
  mismatched prototype/definition pair becomes a hard "conflicting
  types" error under a stricter compiler.
- gc.h's swcmp() prototype was `(void*, void*)`, but pswt.c's actual
  definition (shared, used by every cck-based compiler) is
  `(const void*, const void*)` -- every other compiler's gc.h already
  has the const-qualified version; zc's was just never updated.
- gc.h declared `hintabsize` via the EXTERN macro (real definition in
  whichever .c file #define's EXTERN away, here list.c), but mul.c
  ALSO carries its own real, initialized definition (`int hintabsize =
  nelem(hintab);`) -- two real definitions of the same symbol, a
  multiple-definition link error once mul.o and list.o are both
  linked. vc/gc.h already has the fix: a plain (non-EXTERN) `extern`
  declaration with a "// defined in mul.c" comment, so mul.c stays the
  sole owner. Unlike the l.h-wide EXTERN gap zl needed (notes above),
  this is NOT a systemic issue across zc/gc.h's whole global block --
  it's specific to hintabsize, because mul.c is the one file in this
  frontend that defines a global outside the usual list.c-owns-
  everything convention.

Also had the same pre-rename '7' thechar leftover as zl (txt.c's
ginit()), harmless to compile but printed "usage: 7c" until fixed.

Verified: zc builds, links, and compiles a trivial `void main(void){}`
without crashing, producing a .z object file. NOT yet verified: that
the .z object it produces actually assembles/links/runs correctly
through za/zl, or that any real (non-trivial) C construct codegens
correctly -- zc's own cgen.c/reg.c/peep.c/mul.c are untouched beyond
the two signature fixes above, unlike vc's, which went through actual
bring-up debugging to get real programs running.

tests/c/mini: zc actually compiling and running real C, plus two more gaps
---------------------------------------------------------------------------------

Getting tests/c/mini/helloc.c (a real two-call, two-arg C program,
compiled by zc rather than hand-written assembly) working end to end
found two more gaps, neither in zc/za/zl's own C sources this time:

- zl had no `-L` flag at all (no addlibpath()/findlib(), unlike
  vl/il): a bare `#pragma lib "libmini.a"` (no leading '/' or '.')
  always fell through addlib()'s hardcoded /usr/%clib or /%s/lib
  guess, silently ignoring -L. Ported vl/il's addlibpath()/findlib()
  and the corresponding search-vs-guess branch in addlib() (zl/obj.c).
- lib_toolchain/libmach/obj.c's per-arch object-dispatch table had a
  '7'-vs-'z' leftover pointing alpha at arm64's object reader instead
  of zobj.c's own _isz/_readz -- see notes_libmach.txt's own section
  on this, it's a bug in a shared library, not in zc/za/zl themselves,
  and cost `iar` its ability to build a real archive symbol table for
  alpha objects ("first entry not symbol header" from zl, several
  layers downstream of the actual cause).
- mkfiles/alpha/mkfile's LD was plain "zl", but zl's own no-flag
  default (no -U/-B/-9 given) is Plan 9 native format, not ELF (see
  the HEADTYPE 7 section above) -- tests/c/mini's generic recipe never
  passes -H itself, unlike tests/s/exit's/tests/s/mini's own recipes.
  Fixed the same way arm's own mkfiles/arm/mkfile does it: bake "-H7"
  into $LD itself ("LD=zl -H7"), rather than changing zl's own
  argument-less default (il/vl instead default unconditionally to
  HEADTYPE 7, a different, equally valid convention -- picked the
  arm-style fix here as the smaller, more localized change).

xwrite_alpha.s's second (stack) parameter offset (count+4(FP)) was
read directly off `zc -S`'s own generated assembly for an equivalent
two-arg function, not derived from the autosize+offset+ptrsize formula
the riscv/arm64 xwrite_*.s comments use -- zc has no ptrsize concept at
all (unlike the dual-width ic/il), and blindly reusing that formula
would have guessed 8 (matching arm64's own pointer width) when the
real answer is 4.

tests/c/mini2: SZ_IND=4, a genuine 64-bit-pointer bug inherited from the original source
--------------------------------------------------------------------------------------------

tests/c/mini2/helloprintf.c is the first real test with actual pointer
arithmetic and multi-level function calls (printf's classic K&R
varargs trick: `arg = (byte*)(&s+1);` in print_nofloat_no64.c, reading
subsequent varargs by walking a raw byte pointer across the stack).
Building it surfaced a chain of real 64-bit-pointer bugs in zc,
starting with the same shape as the setSB/gp bug (notes above) but
worse: this time in the *compiler*, not the linker, and load-bearing
for any C code that does pointer arithmetic or passes pointers as
non-first (stack) arguments -- not a narrow one-symbol special case.

Root cause, found by re-tracing the exact same "truncated pointer,
missing high bits vs. the real ~0x2000_00800xxx stack address"
symptom with `qemu-alpha -d in_asm,cpu` again: compilers/zc/gc.h had
`#define SZ_IND 4` -- pointers declared 4 bytes wide, on a machine
where they're 8. Compare compilers/7c/gc.h (arm64, also 64-bit
pointers): `SZ_IND 8`. compilers/vc/gc.h (mips32) and compilers/ic/
gc.h (riscv32, `ic`'s SZ_IND is compile-time 4 for its rv32 default,
with ginit() patching pointer-specific codegen at runtime for -j/rv64
-- see below) are correctly 4, because THEIR pointers really are 4
bytes; alpha's genuinely aren't.

`git show f47294078:compilers/zc/gc.h` (the very first "Reintroducing
alpha toolchain from Plan 9 4th ed" commit, before any work this
project did) already has SZ_IND=4 -- this is not something introduced
by za/zc/zl's bring-up here, it's inherited as-is from the original
Plan 9 4th edition source. Best-evidence theory for why a real,
hardware-testable bug like this could survive: Plan 9's own native
formats (HEADTYPE 0-3 above) use small, fixed load addresses chosen by
Plan 9's own kernel (HEADTYPE 2's INITTEXT=8224, for instance) --
comfortably under 2^32 on any real process. This bug is only load-
bearing once a pointer value needs its high 32 bits, which a classic
Plan 9 process on real Alpha hardware plausibly never did. HEADTYPE 7
(added in this bring-up, for Linux ELF) is the first thing that ever
handed this compiler a modern-Linux-kernel-chosen stack address, which
is why it surfaces only now, not because this bring-up broke something
that used to work.

Two more instances of the identical bug class, both in the same
family as the setSB/gp fix (notes above): missing TIND from an
`et == TVLONG || et == TUVLONG`-shaped check, so pointers fell through
to the 32-bit path. compilers/zc/txt.c's gopcode() (OADD/OSUB and 8
other arithmetic/shift/mul/div/mod cases -- fixed all 10 uniformly,
following compilers/7c/txt.c's own isv() macro precedent, which
explicitly folds TIND in alongside TVLONG/TUVLONG for this exact
purpose) and gmove()'s memory load/store switches (fixed by adding
`case TIND:` alongside `case TVLONG: case TUVLONG:` in both). Also
directly precedented in compilers/ic/txt.c's own load/store switches
-- `case TIND: a = thechar == 'j' ? AMOV : AMOVW;` -- ic needs the
*same* fix conditionally, because rv64 (thechar=='j') has 64-bit
pointers too; zc's version is unconditional since alpha is never
anything but 64-bit. None of this is Alpha-specific special-casing:
it's the same fix every 64-bit-pointer arch in this codebase already
carries, just not yet ported to zc when it was reintroduced.

Fixing SZ_IND and the gopcode()/gmove() TIND gaps did NOT fully
resolve tests/c/mini2 by themselves -- two more sites needed the same
class of fix before it passed:

- compilers/zc/reg.c's own addmove() (the register allocator's spill/
  fill instruction generator -- a THIRD codegen path, separate from
  both gopcode() and gmove(), confirmed by finding `MOVL arg+8(FP),R4`
  in `zc -S` output for a minimal repro even after the gopcode()/
  gmove() fixes) had the identical missing-TIND bug at its own
  `v->etype == TVLONG || v->etype == TUVLONG` check. Directly
  precedented too: compilers/7c/reg.c's own addmove() already includes
  TIND in the identical check.
- tests/c/mini2/minilibc.h's `uintptr`/`intptr` typedefs were behind an
  `#ifdef arm64 / amd64 / riscv64 / else-32-bit` chain with no `alpha`
  branch at all, so alpha fell into the 32-bit `else` and got
  `uintptr = uint32`. This is why %t/%d/%x (fixed-4-byte varargs, sized
  by a literal `4` in print_nofloat_no64.c's vprintf()) worked once the
  compiler-side bugs above were fixed, while %s/%p (pointer-sized
  varargs, sized by `sizeof(uintptr)`) still crashed until this was
  added -- a test-harness-side gap, not a zc bug, but the same root
  cause (alpha's 64-bit pointers not being told apart from the 32-bit
  archs) showing up a third, unrelated way.

Also had to re-derive tests/c/mini/xwrite_alpha.s's and tests/c/mini2/
linux_alpha.s's own hand-written FP offsets and widths (re-running
`zc -S` on minimal repros) once SZ_IND was fixed: fixing the
compiler's pointer width changed its own frame layout (a pointer
argument now reserves/consumes a real 8-byte slot instead of 4), so
offsets read off `zc -S` *before* the SZ_IND fix (int count+4(FP) in
xwrite_alpha.s, char*buf+4(FP)/int count+8(FP) in linux_alpha.s) were
stale afterward -- became +8(FP) and +8(FP)/+16(FP) respectively, the
second one now also needing MOVQ instead of MOVL for the pointer.
Concrete lesson: a hand-written asm stub's FP offsets are pinned to
one specific compiler build's frame layout, not a property of the C
signature alone -- re-verify with `zc -S` after any change to the
compiler's own type-width tables, don't assume "it was confirmed
correct" survives across a fix on the compiler side.

All fixed: tests/c/mini2/helloprintf.exe now produces byte-for-byte
correct output (matching helloprintf.expected.txt) under qemu-alpha,
`mk test` in tests/c/mini2 passes for alpha alongside every other arch
in ARCHS.

tests/c/vlong and tests/c/float: no new bugs, confirming the fixes above were the real thing
-----------------------------------------------------------------------------------------------

Both passed on the first try, no further zc/za/zl changes needed --
the SZ_IND and gopcode()/gmove()/reg.c TIND fixes from the tests/c/
mini2 bring-up already covered what these needed too (vlong's own
helloprintf.c doesn't happen to exercise real 64-bit arithmetic in its
printf calls, matching every other arch's own copy of the same file;
this tier is really about vlrt.c/print.c linking and running cleanly,
not exclusively about int64 correctness).

tests/c/float additionally needed initializing the hardwired FPU
constant registers compilers/zc/txt.c's gmove() assumes for common
float literals -- z.out.h: FREGHALF=28/FREGONE=29/FREGTWO=30/
FREGZERO=31, the same convention mips/riscv already have their own
linux_*.s stubs handle (see those files' own comments). za has no
float-immediate MOVT (unlike mips's assembler sugar for "MOVD
$0.5,F26"; confirmed by grep: no C_FCON row for AMOVT in linkers/lk/
optab.c), so tests/c/float/linux_alpha.s loads 0.5 from a DATA-
declared memory constant and derives 1.0/2.0 via ADDT, the same
indirection riscv's own stub already needs for the same reason.
FREGZERO (F31) needed no initialization at all -- confirmed by
omission, not by looking it up: skipped it initially assuming Alpha's
real ISA hardwires $f31 to +0.0 in hardware (same as $31 for
integers), and the "+0.000000e+000" line matched expected output
without any explicit zeroing, confirming the assumption held under
qemu-alpha too.

-------------------------------------------

Two compiler/linker bugs found here are worth remembering beyond this
one bring-up, since both are "a table that assumed int and pointer are
the same width" mistakes -- the same root cause as the SZ_IND=4 bug
higher up in this file, just recurring in two places that fix hadn't
reached:

1. compilers/zc/txt.c's ncast[] table (nocast()'s no-op-cast lookup)
   still had TINT/TUINT/TLONG/TULONG carrying |BIND, and TIND's own row
   was BLONG|BULONG|BIND -- i.e. it claimed int<->pointer needs no real
   code, true back when SZ_IND was 4 (int and pointer both 32 bits) but
   wrong once SZ_IND became 8. Symptom: `a[na]` (na a plain int index)
   compiled to a bare 64-bit `MOVQ na-N(SP),R` instead of a 32-bit
   MOVL+widen -- cgen.c's OCAST case (inserted by arith()'s own
   int->pointer promotion for pointer arithmetic, sub.c) took nocast()'s
   "no code needed" fast path straight into gmove() with the SOURCE
   int's real memory operand but the DESTINATION pointer's width, so
   the top 32 bits of the loaded register were whatever garbage
   happened to be there. This one took a long debugging session (see
   notes_debug_techniques.txt for the method: print()-based node
   tracing rather than gdb, since it was chasing a Node's ->type field
   through 3 layers of shared cc/ typecheck code before finding the
   backend-local table). Fixed by matching compilers/7c/txt.c's own
   ncast[]: TIND joins TVLONG/TUVLONG's class (all genuinely 64-bit
   here), not TINT/TLONG's. Two earlier fix attempts in this same
   session turned out to be real but insufficient on their own: txt.c's
   gmove() load-branch temp-register mistyping (regalloc(&nod,t,t) vs
   f) and reg.c's paint3() AMOVL->AMOVQ upgrade being gated on
   typechlp[] (chars/shorts/ints/longs/pointers) instead of just TIND
   -- both were real bugs (now fixed, matching 7c), just not the one
   actually firing for this specific construct.

2. linkers/zl/obj.c's `main()`: real Alpha hardware has no integer
   divide, so zc emits ADIVQ/AMODQ/etc pseudo-ops that zl's noop.c
   initdiv()/divsubr() expand into calls to div.s's _divq and 7
   siblings -- but loadlib()'s archive-scanning loop (objfile() on
   each -lXXX/`#pragma lib` library) only pulls in a .a member that
   resolves an ALREADY-SXREF symbol, and it runs before noops() (which
   is the only thing that ever lookup()s these 8 names for real). Fix
   needs two halves, not one: (a) pre-mark all 8 SXREF before the
   first loadlib() call, mirroring INITENTRY's own marking just above
   it, so a real divide's div.z gets pulled from libc.a in time for
   initdiv() to find it -- initdiv() itself doesn't lazily resolve;
   it walks the already-linked firstp list for a matching ATEXT and
   diag()s "undefined: _divq" immediately if the code isn't already
   there. (b) right after noops() returns, if prog_divq (l.h's own
   EXTERN, set by initdiv() the first time ANY of the 8 pseudo-ops is
   seen) is still P, reset all 8 symbols' ->type back to 0 -- a
   program that never divides never calls initdiv() at all, and
   without this the pre-marking from (a) sits there as an unresolved
   SXREF forever, which undef() (the final pass) then rejects even on
   links with no division and no libc.a to resolve it from at all
   (broke tests/c/mini2's helloprintf.exe, a libprint.a-only test,
   as a regression while chasing (a) in isolation -- fixed by adding
   (b), not by reverting (a)). Also fixed, same file: the `-lXXX`
   command-line-flag path in objfile() was still guessing
   /usr/%clib/lib%s.a or /%s/lib/lib%s.a instead of using findlib()
   (the -L search list) the way addlib()'s own #pragma-lib path
   already had been fixed to -- needed for `zl ... -lc` to find
   ROOT/arch/alpha/lib/libc.a at all.
