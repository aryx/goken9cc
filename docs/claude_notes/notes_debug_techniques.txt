Debugging techniques for goken miscompilation bugs
=====================================================

claude: General-purpose debugging *methodology* for tracking down
goken compiler/assembler/linker bugs -- as opposed to
notes_test_infra.txt (how the test suite itself is organized and run)
or notes_shared_frontend_bugs.txt (a status table of specific bugs).
This is "how I found bug X", written so the next session doesn't have
to rediscover these from scratch. Grown out of the arm64 uvlong
constant-truncation and sha3.c lexer-truncation investigations (see
notes_arch_arm64.txt and git history); update this file when a new
technique earns its place, not with narrative of any specific bug hunt.

Differential tracing against a reference compiler (the single most useful technique)
------------------------------------------------------------------------------------------

When a program builds and links cleanly but computes the wrong answer
(the hardest class of bug -- no diagnostic points at anything), the
fastest way to localize it is NOT to stare at codegen. Instead:

1. Take the exact same source file goken is miscompiling.
2. Add plain `printf()` trace statements at natural checkpoints (loop
   iterations, after each major computation step) -- printing enough
   intermediate state to reconstruct where things went right vs wrong.
   Many benchmark files already have a `#ifdef DEBUG` block ready-made
   for this (see benchs/compcert/siphash24.c) -- check before adding
   your own.
3. Compile the *instrumented* copy with a real, trusted compiler
   (clang or gcc, whichever is on the host) AND with goken's own
   toolchain, using the exact same source.
4. Run both, diff the trace output line by line. The first line that
   differs tells you exactly which step/iteration/variable is wrong --
   turning "the whole program is wrong" into "this one expression, in
   this one iteration, computes 0x...wrong instead of 0x...right".

This is dramatically faster than reading -S assembly cold, because you
don't need to already suspect what's broken -- the diff finds it for
you. Once you have a suspect line, THEN read the assembly for just
that line/expression.

Concretely (see git history around the sha3.c/siphash24.c
investigation for the full worked example): a Keccak permutation
function was instrumented to print the full 25-word state after every
round; clang's and goken's traces matched for rounds 0-1 and diverged
at round 2 in exactly one word, by exactly one bit -- immediately
pointing at that round's specific round-constant (a value with bit 63
set) rather than requiring any theory about *why* first.

Progressive source minimization once you have a live repro
------------------------------------------------------------------

Once differential tracing (or any other method) gives you a *reliably
reproducing* buggy program (even a whole real-world file), shrink it
mechanically rather than guessing:

1. Delete unrelated code paths a chunk at a time (unused functions,
   unused struct fields, whole macro-expanded steps) and rebuild+rerun
   after each deletion.
2. Keep deleting as long as the bug still reproduces; back out the last
   deletion the moment it stops.
3. Prefer deleting *whole semantic units* (a macro invocation, a case
   arm, a function) over line-by-line edits -- faster convergence, and
   each intermediate state is still meaningful C.

This reliably turns a multi-hundred-line real program into a
20-50-line minimal repro suitable for tests/c/regressions/, without
needing to understand the bug's mechanism first. It's how a full
Keccak permutation (~100 lines including three macro-heavy transform
steps) reduced to a ~15-line loop doing nothing but
`st0 ^= const_array[round]` for the sha3.c literal-truncation bug --
Theta, RhoPi, and Chi were all provably irrelevant once each was
deleted in turn and the bug persisted.

When deleting-away stalls, try reconstructing-forward instead: if a
"minimized" repro (built the normal way, by copying the real function
bodies verbatim and stripping everything else) mysteriously stops
reproducing the bug, don't assume you deleted the wrong thing -- it's
possible the *thing you stripped away* is the actual trigger, even if
it looks like unrelated, never-executed code. Add pieces of the
original file back one at a time (a whole loop, a whole later
statement) rather than continuing to guess what a truly-minimal repro
should contain. This is how benchs/compcert/binarytrees.c's bug was
actually found: a hand-written minimal repro (BottomUpTree/ItemCheck/
DeleteTree, copied verbatim, called from a small main()) did not
reproduce the crash at all, even at the real program's exact tree
depth -- only restoring the *entire* original main() body, including a
`pow()` call inside a loop that never executes before the crash point,
brought the bug back. The trigger turned out to be the mere presence
of that pow() call in the compiled function, not anything reachable at
runtime -- something no amount of deleting-away from the full program
would have surfaced as cleanly, since removing pow() looks like "just
removing dead code relative to the crash" until you test it.

7c/7l-specific debug flags for bisecting *which pass* is at fault
-------------------------------------------------------------------------

Once you know a program's output is wrong (not just "it looks
different in assembly"), these flags narrow down which compiler PASS
introduced the corruption, before you read any code:

- `7c -N file.c -S`: disables regopt() entirely (no register
  allocation/optimization pass at all). If the bug disappears, it's
  somewhere in regopt()/reg.c or peep.c, not in the initial
  expression-to-Prog codegen (cgen.c/txt.c).
- `7c -R file.c -S`: runs regopt() but skips peep() specifically (see
  compilers/7c/reg.c's `if(!debug['R'] || debug['P']) peep();`). If `-R`
  still shows the bug but `-N` doesn't, the bug is in regopt() itself
  (register allocation/coloring/spill-reload synthesis), not the
  peephole optimizer -- a real example: the mkvar() constant-width bug
  in notes_arch_arm64.txt was isolated exactly this way.
- `7c -g file.c -c`: prints every Prog as it's generated (gins()'s own
  `if(debug['g']) print("%P\n", p);`), i.e. the RAW codegen before any
  optimization pass touches it. Compare this against the same `-g`
  trace from a different backend (e.g. 6c) building the identical
  source, to see whether both backends reach the same intermediate
  representation or diverge immediately -- if they diverge at the
  `-g` level already, the bug is in codegen (cgen.c/txt.c), not
  optimization; if `-g` traces match but final output doesn't, the bug
  is downstream (reg.c/peep.c or the linker).
- Read the compiler's warnings. Don't skip this when a program
  "compiles clean but computes wrong" -- it can point straight at the
  bug. The sha3.c literal-truncation bug (see notes_shared_frontend_
  bugs.txt's "unsuffixed hex constant" entry) produced a "truncated
  constant" warning on the exact lines at fault, but at the time this
  was found it was invisible unless `-w` was passed -- warnings are
  visible by default now (as of the same session; `-q` silences them
  instead), specifically *because* this bug was found this way and
  demonstrated how much a default-off warning can hide. If you're
  reading this on an older checkout where warnings still default off,
  pass `-w` explicitly rather than trusting a "clean" build.
- `7l -a`: prints the linker's disassembly listing (address, raw
  encoded bytes, and the Plan 9 assembly mnemonic) for everything it
  processed, interleaved with any diagnostics -- read the raw
  bytes column, not just the mnemonic: an instruction that failed to
  encode (oplook() found no matching optab entry) shows as all-zero
  bytes with a normal-looking mnemonic printed alongside, which is easy
  to misread as "this instruction looks fine" if you don't check the
  hex.

Instrumenting a recursive function with a counter + guard + exit(), when lldb won't cooperate
----------------------------------------------------------------------------------------------------

When a deep recursive traversal (hundreds of thousands of calls) hits
undefined behavior somewhere inside itself, and lldb's breakpoints
aren't reliably stopping execution on this project's own binaries (see
this file's own "macOS/Darwin-specific execution debugging" section,
and the underlying issue is broader than just quarantine -- address-
based breakpoints have been observed to silently not fire at all, even
for addresses causally before a later crash), don't fight the
debugger: add the check *in the C source itself* and call exit() with
a distinct, greppable code the moment it fires. Concretely, for "a
recursive function sometimes gets called with a bad argument
somewhere in a quarter-million-call traversal": add a global counter,
increment it once per successful call, and guard the function's own
first dereference with something like
`if((unsigned long)ptr < 0x1000){ printf("BAD: ptr=%p at call #%d\n",
ptr, counter); exit(77); }`. This turns "a nondescript SIGSEGV
somewhere deep in a huge recursion, with lldb's own backtrace showing
only one broken frame" (this project's minimal -H6 Mach-O output does
not appear to carry whatever unwind info lldb needs for `bt` to walk
more than one frame -- observed repeatedly, not yet root-caused
separately) into an exact, reproducible, greppable data point: which
call number failed, and what bad value it saw. This is what actually
cracked benchs/compcert/binarytrees.c's bug (see todo.org's "7c
(compiler)" section) after lldb's own breakpoints/watchpoints
repeatedly failed to stop where expected -- the counter+guard
approach revealed the failure was happening at *exactly* the total
node count of a perfect binary tree (2^(depth+1)-1), every single
time, regardless of the tree's actual memory address -- a level of
precision no amount of "set a breakpoint and see what happens" got to
in the same amount of time, because it doesn't depend on the debugger
actually stopping where asked.

Renaming a suspect identifier to correlate corruption with its name
----------------------------------------------------------------------------

When garbled output *looks* like it could be a stray identifier leaking
into the wrong place (e.g. a string that should read "%c" instead reads
something else entirely), and you have a specific suspect name in mind,
rename that one identifier in a minimal repro and rebuild. If the
garbled output changes to track the new name, that confirms the bug is
substituting the identifier itself (a symbol-table/macro-expansion
bug), not corrupting memory at some fixed offset unrelated to the name.
This is how benchs/compcert/mandelbrot.c's `print("%c", (c))` bug was
distinguished from a generic buffer-overrun theory early: renaming the
macro parameter from `c` to some other letter changed *what* the
corrupted string contained, immediately pointing at macro-parameter
substitution rather than, say, a fixed-size scratch buffer being
overwritten by unrelated data. See notes_shared_frontend_bugs.txt's
"Macro parameter substituted inside a string/char literal" entry for
the bug this caught.

Reading `-S` assembly output to verify a fix without executing anything
----------------------------------------------------------------------------

Not every environment has qemu-user available to actually *run* a
cross-arch regression test's binary (this project's own dev host
often doesn't -- see notes_test_infra.txt). When the bug under test
manifests as wrong compile-time output (a corrupted string literal, a
wrong constant, a missing instruction) rather than needing runtime
execution to observe, `Xc -S file.c` and grepping the resulting
assembly for the specific `DATA`/instruction in question is a fast,
completely execution-free way to confirm a fix landed -- e.g. `7c -S
cpp_macro_param_in_string.c | grep 'DATA.*string'` showing
`$"%c\z..."` (fixed) vs `$"%42\z..."` (bug) directly, no linking or
qemu-runner needed at all. Combine with git stash on just the fixed
source file (see notes_test_infra.txt's stash-based verification
pattern) to see both the before and after in the same repro without
ever running the binary.

Using snprint() instead of intercepting write() to test format-string bugs
----------------------------------------------------------------------------

To test a bug in the fmt/ library's formatting logic itself (dofmt(),
__charfmt(), etc.) without needing to capture what actually got written
to a real file descriptor, use snprint()/vsnprint() -- they format into
a caller-provided memory buffer through the *exact same* dofmt() code
path print()/fprint() use, just without the syscall at the end. Much
simpler than trying to intercept the write() syscall (a locally-defined
function of the same name will NOT override a call to the real,
already-linked write() in this codebase's simple static-linking model
-- there's no symbol interposition support to lean on). See tests/c/
regressions/fmt_charfmt_high_bit.c for a worked example: it detects the
%c-drops-high-bit-bytes bug purely by checking snprint()'s return value
and buffer contents, no file descriptor or qemu-runner involved.

Verifying a fix actually reached the *installed* binary, not just the source
------------------------------------------------------------------------------------

A fix compiling cleanly in isolation (e.g. via a quick `-S` check, per
the technique above) is not proof the *installed* compiler/linker
binary a regression test will actually invoke has picked it up. Two
distinct footguns found together while wiring up
cpp_macro_param_in_string.check (see notes_shared_frontend_bugs.txt's
entry on the underlying bug for the fuller story):

- A dependency line in the relevant mkfile may be commented out (e.g.
  `#mac.$O: macbody` in compilers/cck/mkfile and compilers/cc/mkfile),
  so a plain `mk install` after editing a #include'd body file like
  macbody silently rebuilds nothing. `mk -a install` (force) is
  required whenever you can't trust the dependency graph is complete.
- Some per-arch compiler directories don't compile their own frontend
  source at all -- they link a *prebuilt* library archive built by a
  sibling directory (compilers/6c/ links compilers/cck/cc.a rather than
  compiling mac.c itself). `mk -a install` inside the leaf directory
  only relinks against whatever that archive already contains; if the
  archive itself is stale, the leaf binary stays stale too, silently.
  Rebuild the library's own directory first (compilers/cck/, in this
  example), then the leaf.

The reliable way to actually confirm a fix landed in the binary you're
about to trust: don't just check that the build reported success --
re-run the same `-S`/behavioral check *after* the full rebuild chain,
on the freshly-installed binary. That's what caught this: 8c picked up
the fix on the first `mk -a install` (its own directory rebuilds its
library inline), but 6c silently didn't until compilers/cck/ was
rebuilt explicitly first -- a difference invisible from either build's
"success" output alone, only visible by re-checking the actual
resulting assembly.

A third variant, found wiring up benchs/compcert's goken-O0/goken-O3
(docs/claude_notes/notes_frontend_optlevels.txt): running `mk
objtype=boot-gcc` inside a compiler's own directory only produces a
local o.out there -- it does NOT copy anything to $PATH's
ROOT/arch/$objtype/bin/, which is what any script invoking the tool by
bare name (`7c`, not `./o.out` or an explicit path) actually runs. `mk
install` (not just `mk`) is required for that. This one is sneakier
than the other two because it doesn't even fail quietly -- it produces
a complete, plausible-looking result (bench.sh's full table, no error)
that just happens to be wrong, since the stale pre-patch binary's
ARGBEGIN loop silently absorbed the new `-O0`/`-O3` flag as two
meaningless single-char debug flags instead of erroring on it. Same
fix as always: re-verify the actual behavior (here, `7c -O0 -S` vs `7c
-O3 -S` on a real .c file) using the exact invocation path (bare name
via $PATH, not a directory-relative o.out) the thing you're trusting
will actually use.

Unbuffered write() markers vs print() when a crash might prevent a flush -- and when it doesn't matter
------------------------------------------------------------------------------------------------------------

When instrumenting a program that might SIGSEGV partway through, and
using print()/printf() trace statements to bisect where, first check
whether this libc's own print() path buffers across separate calls at
all -- don't assume a stdio-style FILE* buffer that a crash could
prevent from ever flushing. It doesn't, here: vfprint() (fmt/vfprint.c)
allocates a *fresh, local* 256-byte Fmt buffer on every single
print()/printf() call and explicitly calls __fmtFdFlush() before
returning, so each call's output reaches the fd before the *next*
statement even runs -- there is no cross-call buffering to lose on a
later crash. First-hand confusion this session: an early debug pass
assumed print() output could be silently lost and switched to raw
write(1, "marker\n", n) calls instead "to be safe" -- genuinely
harmless, but based on a wrong premise (verified afterward by reading
vfprint.c directly), and the real reason that first pass showed zero
output turned out to be an unrelated string-replace typo (whitespace
mismatch silently leaving the intended edit unapplied). Worth knowing
the flush behavior for real before reaching for write() out of
caution: raw write() IS still preferable in one case though --
formatting a *suspect* value through print()'s own machinery (the
thing you're trying to test) to report on that same machinery is
circular if the format call itself is a suspect. Manually converting a
long to decimal digits and write()-ing the raw bytes (see below)
sidesteps that.

Manually formatting a value with write() to get a trusted read on it, independent of a suspect formatting call
-------------------------------------------------------------------------------------------------------------------

When the very thing under suspicion is a print()/printf() call itself
(as opposed to the value being printed), inserting *another*
print()-based trace statement to inspect that value doesn't actually
rule anything out -- if print()'s handling of a particular vararg type
or combination is what's broken, a second print() call might exercise
the exact same broken path and give a misleading (or also-crashing)
answer. Write a tiny throwaway helper that converts an integer to
decimal digits by hand (repeated `%10`/`/10`, no library call) and
write()s the raw bytes directly -- this is untestable-wrong in a much
smaller amount of code than the real formatter, so a value it reports
can be trusted while bisecting whether the *real* formatting call is
the actual point of failure. Concretely, this is what separated
"write_frequencies()'s hash-table size/total values are wrong" (would
have pointed at the hash-table code) from "the values are exactly
right (size=4, total=50000, matching the expected A/T/C/G split) and
the crash is specifically in the subsequent printf(\"%.3f\", ...) call"
(points at formatting/varargs instead) while investigating
benchs/compcert/knucleotide.c's SIGSEGV -- both a %s+%.3f combined call
and, further narrowed, a *bare* printf(\"%f\", floatexpr) with no other
verbs at all, crash at that exact point in the real program, even
though hand-verified via this technique to be receiving perfectly
sane arguments.

strace as a coarse but fast way to see how far a program actually got before a silent-looking crash
-------------------------------------------------------------------------------------------------------

Before reaching for gdb (which may not even load this project's own
linker output at all -- see below) or adding print()-based
instrumentation, run the failing binary under `strace -f` once. It
costs nothing extra to try and immediately answers "did the crash
happen in this syscall-heavy phase, or after it": for
benchs/compcert/knucleotide.c's crash, a full strace showed thousands
of successful one-byte read() calls (this project's own fgets() reads
one byte at a time, no internal buffering -- see lib_core/libc/APE/
stdio.c) ending in a clean `read() = 0` (real EOF) followed immediately
by the SIGSEGV -- ruling out "crashed mid-file-read" in one command,
before writing a single line of debug instrumentation, and correctly
redirecting suspicion toward the *processing* that happens after the
whole file is read rather than the file-reading path itself.

qemu-user's -strace to split "wrong syscall" from "right syscall, mis-read result"
-------------------------------------------------------------------------------------

A sharper variant of the plain-strace technique above, for the
cross-compiled targets: every arch this tree tests under qemu-user can
be run as `qemu-<arch> -strace ./foo.exe` directly (scripts/qemu-runner
picks the binary name; call qemu yourself when you want the flag).
Unlike host strace, this works for all seven Linux arches from one x86
box.

What makes it worth reaching for early is that it draws a line the
program's own output cannot: it shows what the *kernel* was asked and
what the kernel answered, independently of what libc then did with
that answer. When tests/c/hello_libc/dir.c failed on mips only, the
trace showed:

  unlink("dir_tmp.txt") = 0
  open("dir_tmp.txt",O_RDONLY) = -1 errno=2 (No such file or directory)

i.e. both syscalls behaved perfectly -- while the program printed
"remove left the file behind", which it only does when that open()
returns >= 0. That single contradiction localizes the bug to the
syscall *return-value* path (svc_mips.s's trampoline, which was
ignoring o32's $a3 error flag -- see notes_arch_mips.txt) with no
instrumentation, no bisection, and no reading of generated assembly.

Generalizing: whenever a libc-level call misbehaves on one arch only,
check the trace before suspecting the syscall number, the arguments,
or the compiler. "Kernel did the right thing, caller disagreed" and
"kernel did the wrong thing" look identical from inside the program
and completely different in one line of -strace output.

A corollary worth designing tests around, since it is what let three
successive bugs hide in this one file: a trampoline's *error* path is
invisible to any test whose syscalls all succeed. hello.c and io.c
only ever make calls that work. dir.c deliberately requires a call to
FAIL (open() after remove()), which is what finally exposed it.

A throwaway probe that prints one suspect value across several inputs
-------------------------------------------------------------------------

When a value is wrong but you cannot tell WHERE it went wrong, a
ten-line program that prints just that value for a handful of chosen
inputs often identifies the exact defect from the PATTERN of wrongness,
with no debugger and no disassembly.

Concretely, while chasing a Plan9 seek() that returned the wrong
offset: rather than instrument libc, a scratch main() did

  off = seek(fd, 6, 0);   print("seek(6,0) -> %lld\n", off);
  off = seek(fd, 0, 0);   print("seek(0,0) -> %lld\n", off);
  off = seek(fd, 3, 1);   print("seek(3,CUR) -> %lld\n", off);

and printed 0, 0, and 4294967296. That last value is exactly 1<<32 --
the whence argument (1) appearing in the HIGH word of the returned
64-bit offset. A single number named the bug: something was reading the
vlong one 4-byte stack slot too high, picking up
(whence<<32)|offset_high. Confirmed in one grep of the emulator's
sysseek() (+16 where the kernel uses +12).

The technique generalizes: choose inputs that are DISTINCT SMALL
POWERS or otherwise mutually distinguishable, never all-zero or
all-equal. Zero is the worst possible probe value for an offset, index,
or flag word, because it survives being truncated, mis-slotted, or
dropped entirely -- which is precisely why the bug had hidden behind
seek(fd, 0, 0) for so long. Picking 6 and 3/SEEK_CUR made the
misplacement arithmetic legible at a glance.

gdb refusing to load this project's own linker output at all
-------------------------------------------------------------------

`gdb --args ./some.goken` can fail immediately with "not in executable
format: file format not recognized" -- even though `file` correctly
identifies the same binary as a normal ELF executable for the target
arch, and even with an absolute path (ruling out a cwd-relative-path
theory). Not yet root-caused (plausibly some section BFD expects and
this project's own Xl doesn't emit, given goken's linkers have
repeatedly needed exactly-conformant-enough-for-the-kernel-loader
output rather than fully standard output elsewhere in this tree's
history) -- but the practical consequence is: don't spend time trying
flags/paths to coax gdb into loading a goken-linked binary on this
host. Fall back to strace (syscall-level visibility) and manual
print()/write() instrumentation instead; both worked fine on the exact
binaries gdb refused here.

Bottom-up reconstruction with the *real* growth history/scale, not just the real code shape, when a "faithful-looking" minimal repro doesn't reproduce
--------------------------------------------------------------------------------------------------------------------------------------------------------------

Extends this file's existing "reconstructing-forward" section
(binarytrees.c's pow() story) with a sharper version of the same
lesson, from the knucleotide.c investigation. A hand-written repro that
faithfully reproduces the real code *shape* (same struct layout, same
malloc/calloc/strdup calls, same sort-then-printf loop, even called
from a separate function to match real stack depth) can still fail to
reproduce a bug if it doesn't also reproduce the real *quantities* --
how many bytes were allocated, how many times, in what order, before
the crashing call. A structurally-faithful repro using 4 hand-built
hash-table nodes and no file I/O did NOT crash; only re-introducing the
real ~100KB input file (driving the real ~50000-byte buffer growth via
realloc(), and the real, much-larger intermediate hash table churn from
generate_frequencies() actually processing that much data) brought the
crash back, even though the *values* reaching the final printf() were
verified identical either way (via the manual-write() technique above).

This scale theory turned out to be a red herring, caught by the next
technique below: the real trigger had nothing to do with volume at all.
Worth keeping this section anyway as a caution -- a same-shape-smaller-
scale repro failing to reproduce a bug is genuinely ambiguous evidence
("scale matters" and "some unrelated thing I stripped out in the
process matters" look identical from here), so don't stop at the first
theory that fits; keep testing until you've actually isolated the
single changed variable, not just the first one that correlates.

Narrowing down which of several candidate symbols an unexplained crash needs by testing each in isolation, then re-testing the same repro on a different backend
--------------------------------------------------------------------------------------------------------------------------------------------------------------------

What actually resolved the "scale" red herring above: the real, growth-
matching repro (buffer sizes and final content identical to the real
run, but built via simulated realloc() growth, no real file I/O) still
did NOT crash on its own -- until a single, provably-dead call
(`if(neverrun){ fopen("x","r"); }`, `neverrun` a global int initialized
to 0, so the branch is never taken at runtime) was added anywhere in
the same function. That immediately reproduced the crash. This is the
same "mere presence, not execution" shape as binarytrees.c's pow() bug
(see this file's "reconstructing-forward" section and todo.org) --
recognizing the shape from a previously-documented bug is what turned
"scale must matter" into "test presence-without-execution instead,
exactly like last time".

Once presence-without-execution was confirmed as the trigger, two
further isolation steps are what actually made this a reportable
finding rather than a vague "something about stdio.c":

1. Test each candidate symbol individually, not just the group. The
   real code linked in three new functions together (fopen/fgets/
   fclose, lib_core/libc/APE/stdio.c). Rather than assume all three (or
   "something about that file") are responsible, build one repro per
   function, each with only that one dead call added to the same known-
   safe baseline. All three reproduced independently here, which is
   itself useful information (rules out "it's specifically fgets's own
   internal loop", say) -- but the general point is: when N things
   changed together, don't report "one of these N is the trigger",
   spend the N extra small builds to say which one(s) actually are.
2. Test whether a *different function's own callees* also trigger it.
   fopen()/fgets()/fclose() each internally call a lower-level function
   (open()/read()/close() respectively) that was already known-safe
   elsewhere in the codebase (hello_libc, io.c). Testing those directly
   -- same dead-code-presence pattern, calling open()/read()/close()/
   seek() individually instead of the fopen/fgets/fclose wrappers --
   did NOT reproduce the crash. This is what separated "any I/O-
   adjacent symbol's presence triggers this" (would implicate something
   shared, like the syscall trampoline machinery) from "specifically
   these three wrapper functions do" (implicates something about their
   own compiled bodies or their specific position in the link) --
   a real, load-bearing distinction that a single all-three-together
   test could never have surfaced.
3. Re-run the *identical* repro (same .c file, unchanged) through a
   different backend before concluding anything about the bug's scope.
   The exact same dead-fopen()-call repro was built with both 7c/7l
   (arm64) and 6c/6l (amd64); only the arm64 build crashed, amd64 ran
   clean -- and the real, complete, unmodified knucleotide.c
   subsequently confirmed the same split (crashes on arm64, matches
   Results/knucleotide byte-for-byte on amd64). Without this step the
   finding would have been mis-filed as "a bug in APE/stdio.c" (an
   ordinary C source file, portable by construction) instead of what it
   actually is: a second, independent instance of a 7c/7l-specific
   link-time/layout bug -- the same family as binarytrees.c's pow()
   bug, and worth cross-referencing there (todo.org) rather than
   writing up as a new unrelated bug, once the shape matched.

Correction to the above, and isolating a crash trigger to a *structural* fact about the build (object-file boundaries) rather than to specific symbols
---------------------------------------------------------------------------------------------------------------------------------------------------------------------

The three-part isolation above was real progress but its conclusion
("specifically fopen/fgets/fclose, not their callees") was still
wrong -- a good reminder that ruling out several specific theories
doesn't mean the *next* theory you land on is correct, only that it's
survived more tests than the others so far. Two results that didn't
fit finally forced a rethink: (1) the crash reproduced identically at
`-O0` (regopt() entirely disabled) through `-O3`, with byte-identical
machine code at the crash-adjacent call site across all four --
ruling out the optimizer despite register allocation *looking*
different between crashing and non-crashing builds (that register
shift, chased at length via reg.c's `regalloc()`/`lasti` round-robin
counter, turned out to be a correlated symptom of unrelated code being
compiled earlier in the same function, not the cause -- see git
history for that dead end if picking this up again); (2) the crash
reproduced with a plain `print("%d\n", i)` (an int, no float
computation anywhere in the call), which the original "specifically
fopen/fgets/fclose" framing had no room for.

What actually found the real trigger: instead of continuing to vary
*which function* was dead-called, vary the *build structure* while
holding the dead-called function's own logic fixed. Concretely: take a
function that calls a real external symbol (open() or strdup(), both
already known individually safe when dead-called *from the same file
as main*), and test all three placements of it: (a) inlined directly
into main(), (b) a separate function within the same .c/.7 file as
main(), (c) a separate function in its *own* .c file, compiled to its
own .7, linked alongside main's .7. (a) and (b) never crashed, for
either open() or strdup(). (c) crashed for *both* open() and strdup()
-- immediately reframing the bug from "these specific symbols" to
"calling any external function from a non-entry object file, even
dead code, corrupts something elsewhere when >=2 object files are
linked together" (confirmed further: a trivial no-external-call
function placed the same way, option (c), does NOT crash -- the
external call inside the separate object file is the load-bearing
part, not merely "a second .o exists"). This is why fopen/fgets/fclose
(lib_core/libc/APE/stdio.c, a separately-compiled object file whose
functions each call another external symbol) tripped it while calling
open()/read()/close() *directly from main's own file* never did --
they're not different in what they call, they're different in *how
many object-file boundaries* separate the call site from main().

The general lesson: when a crash's trigger looks like it depends on
*which* function/symbol is involved, and the individual-symbol tests
keep producing a confusing pattern (some wrappers trigger it, their
own callees don't, an unrelated function called the "same way"
doesn't), consider that the real independent variable might not be
symbol identity at all -- it might be a structural property of the
build (object-file count, which file a call originates from, link
order) that happens to correlate with which symbols you tried. Test
that directly by holding the *content* of a dead call fixed and only
varying *where it's compiled* (same file vs. separate file vs. inlined)
before spending more effort on a growing, still-unexplained list of
"this symbol does, this symbol doesn't."

macOS/Darwin-specific execution debugging

Cross-arch rt0.s bring-up: verifying a calling convention when there is no disassembler
------------------------------------------------------------------------------------------

claude: grown out of wiring real argc/argv into every arch's
lib_core/libc/arch/$cputype/rt0.s (previously all 7 arches just did
`CALL main` / `BL main` with no argument setup at all -- every existing
test used `void main(void)` specifically to dodge this, and todo.org
already had a related, unexplained crash-on-argv[1] report). Two
techniques worth keeping, and one specific gotcha they both exist to
catch.

First-order technique: empirically confirm each compiler's own
argument-passing convention with a throwaway 2-arg probe compiled with
-S, rather than assume it matches another arch or a textbook ABI doc:

    echo 'void probe(int a, char **b) { *b = (char*)a; }' > probe.c
    7c -S probe.c   # or 6c/8c/5c/vc/ic/jc for the other arches

Reading the output tells you, per arch, whether the FIRST argument
arrives in a register (arm/arm64/mips/riscv/riscv64 all do -- R0, R0,
R1, R8, R8 respectively) or is caller-stack-passed like every other
argument (amd64/386, no registers at all), and at what FP-relative
offset the second argument lives (a full pointer-width slot per
argument on every arch here, confirmed via the *first* register-passed
argument still "reserving" its own phantom FP+0 slot in the numbering).

Second-order gotcha this alone does NOT catch: -S output shows the
compiler's own *logical* FP-relative addressing, resolved assuming
whatever prologue the compiler+assembler decide to emit -- it does NOT
tell you what raw, hand-written code operating on the bare hardware SP
register (as rt0.s must, since there is no frame yet at the process
entry point) needs to add or subtract to land on the same memory. Two
compounding effects, found only by live inspection (see below), not by
reasoning about the ABI on paper:

  - Calling BL/JAL/CALL from within a TEXT block makes it "non-leaf",
    and the assembler auto-inserts a prologue that saves the return
    address BEFORE any of your own hand-written instructions run --
    even with an explicit `TEXT foo(SB), $0` (zero declared frame
    size!). This silently shifts the raw SP by a fixed, arch-specific
    amount that raw register-relative code must compensate for: one
    word on arm/mips/riscv/riscv64 (4 bytes on the 32-bit ones, still
    only 8 -- not 16 -- on riscv64 despite its wider registers), a
    full 16-byte-aligned block on arm64 (its ABI's mandatory stack
    alignment), and none at all on amd64/386 (CALL's own push IS the
    only stack effect, and there is no separate LR/RA register to
    save).
  - Separately, and NOT fully explained by the auto-push alone: the
    exact stack slot where an *outgoing* argument must be written for
    the callee to read it back correctly was consistently one pointer-
    width slot further out than the naive "argv is the callee's FP+N,
    so write it at (my adjusted SP)+N" arithmetic predicts, on every
    arch tested (arm, arm64, mips, riscv, riscv64). Confirmed
    empirically each time, never fully re-derived from first
    principles -- treat any first attempt at these offsets as a
    hypothesis to verify live, not a formula to trust.

How to verify live when the toolchain's own binaries aren't
disassembler-readable: this project's linkers produce ELF/Mach-O files
that `file` recognizes but `objdump -d` and `gdb`'s own symbol loader
both reject outright ("file format not recognized") -- there is no
"just disassemble it" option here. Two techniques stood in:

  1. qemu-user's built-in GDB stub, for any arch other than the host's
     own: `qemu-$arch -g 1234 ./binary args... &`, then
     `gdb-multiarch -ex "target remote localhost:1234" -ex "set
     architecture $arch" -ex "x/Ni $pc" -ex "info registers"`. gdb
     still can't load symbols from the file (same "not recognized"
     complaint), but it can single-step, dump registers, and dump raw
     memory at any address on the *live* remote target regardless --
     `x/Ni $pc` conveniently disassembles instructions AT the target
     even though it could not load the file as an object. On the
     host's own arch (here, arm64), the exact same recipe works
     natively without qemu at all.
  2. When even that address-finding is awkward (e.g. main's own
     compiled entry point isn't a fixed, known address to break at
     ahead of time), skip disassembly entirely: write a tiny, separate
     C "debug helper" function with known, simple parameters (e.g.
     `void dbg1(uintptr a) { print("a=%p\n", (void*)a); exits(nil); }`),
     hand-write a throwaway entry stub that computes a candidate value
     and calls the helper with it (`-E _dbgmain` to override the
     linker's default entry symbol so this coexists with the real
     rt0.s untouched), and read the printed result. This turns "what
     is actually at this memory location" into an ordinary print-
     debugging loop -- sweep a handful of candidate offsets (0, 4, 8,
     12, 16, ...) this way rather than trying to compute the right one
     by hand, since the auto-push amount above is exactly the kind of
     fact this technique exists to pin down instead of assume.

One tooling trap met while doing this: `ia` (the riscv/riscv64
assembler, riscv64 via its `ja`/`jc`/`jl` aliases) reliably crashes
with "stack smashing detected" on a *very short* standalone .s file
assembled directly (as few as 2-3 instructions), but assembles the
same real, larger rt0.s file (built through its normal mkfile, with
several instructions and a trailing infinite loop) without any issue.
Root cause not investigated -- unrelated to whatever fix is in
progress when it's hit -- but worth recognizing immediately: pad
throwaway probe files out to roughly the same shape as a real,
already-working TEXT block (ending in the same `loop: JMP loop` idiom,
rather than a bare `RET`) instead of spending time on the crash itself.

Two non-lldb, non-otool gotchas on this host that both produce the
*identical* symptom -- a build reports success (`exit=0`) but the
output file "doesn't exist" moments later -- and are worth telling
apart before suspecting the toolchain:

- The agent shell's cwd can silently reset to a *different* configured
  working directory (not just back to the primary repo root) after a
  `cd` into a scratch/temp directory several tool-calls earlier. Check
  with a plain `pwd` first; this is the more common self-inflicted
  cause.
- Separately, this host runs endpoint security software (observed:
  CrowdStrike Falcon) that can quarantine/remove a freshly-built,
  ad-hoc-signed executable within a very short window after creation
  -- sometimes right after `codesign`, sometimes even before it. Not a
  code bug: confirmed by watching a file exist under `ls -la` and then
  fail to `open()` (via `file <binary>`) moments later in the *same*
  shell invocation, with no error from the linker or codesign. No
  reliable workaround found beyond retrying (usually works within a
  few attempts) or building under a name/path not previously
  quarantined this session; do not attempt to disable or bypass the
  security tool itself.

Bisecting a "mere presence of an unrelated call corrupts something else" bug
------------------------------------------------------------------------------

claude: grown out of the arm64_large_bss_sb_offset regression (see
notes_arch_arm64.txt's own section) -- a shape of bug where adding one
semantically-unrelated function call to main() (here: atoi(), inside a
ternary whose branch never actually ran) made a *different*, unrelated
part of the program crash later. This shape recurs in this codebase
(todo.org's still-open knucleotide.c multi-object-file note is another
instance) and is worth a dedicated approach rather than reasoning about
the failing program directly.

1. Reduce to the smallest C file that still reproduces, by literally
   copying the failing source and deleting/simplifying one thing at a
   time, rebuilding and rerunning after each cut -- not by reading the
   code and guessing which part matters. Each step is one Write + one
   7c/7l/run cycle; keep every intermediate file (a.c, b.c, c.c, ...)
   rather than overwriting, so a later step can go back and re-check an
   earlier hypothesis cheaply. This found, in order: the loop wasn't
   needed (single call reproduced), the malloc size wasn't needed (100
   bytes reproduced same as 5MB), argc/argv alone weren't sufficient
   (needed the extra call too), and finally that the *unreached* atoi()
   branch alone -- with no malloc/memset/print at all -- did nothing,
   but adding back just one more real call (memset after malloc) turned
   it into a crash. That last step is what pointed at "combination of
   call *count*", not any single suspicious-looking line.
2. Once the minimal repro exists, use it to test cross-arch: build and
   run the *same* source for another arch via qemu-user (here: amd64
   through qemu-x86_64, since the host is arm64) before touching any
   compiler/linker source. A clean pass on another arch changes the
   search space entirely -- from "logic bug in this C code" to
   "codegen/linker bug specific to one backend" -- and costs one build
   +run, far cheaper than any source-level investigation.
3. To find *where* corruption actually happens (as opposed to where it
   crashes, which can be arbitrarily far downstream -- here, a printf()
   call that had nothing to do with the actual bug), run under
   qemu-$arch's GDB stub even on the host's own native arch (`qemu-
   aarch64 -g 1234 ./a.out &` then `gdb -ex "target remote :1234" -ex
   c`); native execution alone gives you a core dump you may not have
   permission to read (see below) and no way to inspect registers at
   the exact faulting instruction. `x/Ni $pc`, `info registers`, and
   `x/Nxg <addr>` at the crash point identify which register holds a
   clearly-wrong value (garbage, or a value that decodes suspiciously
   as a memset() fill byte repeated four times, etc.) and which
   instruction produced it -- gdb still can't load this project's own
   binaries as an "executable" (same "file format not recognized" as
   noted elsewhere in this file), but remote register/memory inspection
   doesn't need that.
4. `ulimit -c unlimited` plus a native segfault does NOT reliably give
   you a readable core file on a locked-down host -- here, apport
   redirected it to a root-owned, `-r--------` file under
   /var/lib/apport/coredump, unreadable without sudo. Don't spend time
   fighting the OS's own crash-dump policy; go straight to the qemu-gdb
   approach in (3), which sidesteps the host's core-dump handling
   entirely by running the target under emulation regardless of host
   arch.
5. Once a specific instruction's encoded immediate looks wrong, decode
   it by hand (a short Python snippet extracting the relevant bitfields
   is faster and less error-prone than eyeballing hex) and compare the
   decoded value against the *expected* value computed independently
   (e.g. from the linker's own symbol-placement pass, see below) --
   don't stop at "this looks wrong", compute what it should have been
   and confirm the delta matches a specific, nameable failure mode
   (here: the delta between the wrong and right address was exactly
   0x10101010, i.e. a 4x-repeated 0x01 byte -- immediately recognizable
   as memset(p,1,n)'s own fill pattern once you know to look for it,
   which is what turned "some register has a weird value" into "this
   register is reading stale memset'd memory instead of the intended
   struct field").
6. When the suspect is a linker internal pass (here: 7l's dodata(),
   which assigns each global symbol's final offset by walking a hash
   table -- not a resolvable-by-inspection order), add temporary
   fprint(2, ...) instrumentation directly to that pass (gated behind
   `getenv("SOMEDEBUG")` so it's opt-in), rebuild just that one tool
   (`mk 'objtype=boot-gcc' install` in the tool's own directory -- see
   the gotcha below), and diff its output between the working and
   crashing link. This is far faster and more reliable than
   reconstructing the same information by hand-decoding every relevant
   instruction's encoded immediate -- use hand-decoding (step 5) to
   find *which* symbols are suspect, then instrumentation to get their
   *actual* assigned offsets directly from the source of truth, and use
   the two together rather than either alone.
7. Gotcha hit repeatedly this session: rebuilding one of this project's
   own host tools (7l here) requires passing `objtype=boot-gcc`
   explicitly on the `mk` command line when invoking `mk` directly
   inside that tool's own directory (`cd linkers/7l && mk
   'objtype=boot-gcc' install`) -- plain `mk install` there silently
   resolves `$objtype` to empty (mkconfig's values are sourced as
   *shell* variables by env.sh, not exported, so a bare `mk` invoked
   directly doesn't see them the way it does when reached through the
   top-level mkfile's own `<$TOP/mkconfig` include), producing
   confusing, unrelated-looking compile failures ("-o: No such file or
   directory") for a handful of source files instead of a clear "unset
   variable" error. Same root cause as the already-documented goken9cc/
   goken PATH-shadowing note; this is the mk-variable-scoping variant of
   it. Same fix applies to running any of this project's own test
   suites (e.g. `tests/mkfile`) directly instead of through the
   top-level `mk test` -- those also assume the top-level mkfile's
   objtype binding is already in scope and don't `<$TOP/mkconfig`
   themselves.
8. A regression test for this class of bug needs care in what it
   actually asserts: writing and reading the *same* buggy L(R)-style
   memory reference (`x = V; if(x != V)`) can pass even with the bug
   present, if the write and the read both consistently compute the
   same *wrong* address (confirmed empirically while writing this
   session's own regression test -- the naive version didn't catch the
   bug at all). Write through an independently-computed-correct address
   (e.g. `p = &x; *p = V;`, which typically goes through different
   compiler/linker codegen than a direct `x = V`) and read through the
   specific path under test, so a wrong address shows up as a real
   value mismatch instead of two wrongs silently agreeing.

Driving an interactive REPL-style host tool (5i/vi) non-interactively under gdb
----------------------------------------------------------------------------------

machines/5i and machines/vi are themselves interactive debuggers (read
a `:c`/`$q`-style command language from stdin, print to a Bio stream) --
which makes a HOST-side crash inside one of them (as opposed to the
guest program it's running) awkward to catch with a plain `gdb 5i` plus
manual typing, since the crash only happens after the emulator has
already accepted commands and started executing guest code.

The fix is to give gdb the same stdin script scripts/qemu-runner-style
callers already pipe in (`printf ':c\n$q\n' | 5i ./x.exe`), but via
file redirection instead of a pipe, and set the guest binary as gdb's
own `args` rather than folding it into `--args` alongside redirection
(the two do not compose the way you'd expect -- `--args 5i ./x.exe`
combined with `run < file` on the same line drops the program's own
argv, and 5i falls back to its default guest name, `5.out`):

    printf ':c\n$q\n' > /tmp/in.txt
    gdb -q -batch \
      -ex "set args ./x.exe" \
      -ex "run < /tmp/in.txt" \
      -ex "bt full" \
      /path/to/5i

`bt full` is what actually pays off here: it prints every frame's
locals, not just the call chain, which is what turned a plain
"SIGSEGV in sysfstat()" into "reg.r[REGARG] == 4294967295" -- the exact
value that explained the bug (see notes_libc_selfhost.txt's stat-family
section). Reading the crashing line's source alone would not have shown
that REGARG and REGRET happened to be the same register at that point
in the register file; the concrete runtime value did.

Also worth noting: a plain (non-gdb) run of the same repro under bash
segfaults with "core dumped" printed, but this box's apport handler
intercepts the actual core file (`/proc/sys/kernel/core_pattern` pipes
to `apport`), so there is nothing under `./core*` to load into gdb
after the fact -- running the crash live under gdb from the start (as
above) sidesteps that entirely, rather than fighting with core-dump
configuration.
