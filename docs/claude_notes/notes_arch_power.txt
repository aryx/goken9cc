The powerpc toolchain (qa/qc/ql/qi): first Linux ELF exit/hello/C bring-up
===========================================================================

Notes from bringing up qa/ql/qc (emulator qi untouched so far) far
enough to run tests/s/exit/exit_linux_power.s, tests/s/mini/
hello_linux_power.s, tests/c/mini/helloc.exe, tests/c/vlong/
helloprintf.exe, tests/c/float/helloprintf.exe, and tests/c/mini2/
helloprintf.exe (all byte-matching their expected.txt) under qemu-ppc.
Source is Plan 9 4th edition's powerpc port (see
cf54e8364/359281e56/53b0b0882 for the import and initial "make it
compile" commits); this session is the first real runtime exercise of
any of these tools. See assemblers/qa/, linkers/ql/, compilers/qc/,
include/objexec/q.out.h, tests/s/exit/, tests/s/mini/, tests/c/mini/,
tests/c/vlong/, tests/c/float/, tests/c/mini2/.

lput/wput/cput: long -> int32 parity fix
-----------------------------------------

Same class of fix already applied to 5l/8l (37e0fe696) and to zl during
its own bring-up: linkers/ql/asm.c's cput/wput/wputl/lput/lputl took
`long` (64 bits on this LP64 host) where every sibling linker (6l, vl,
zl) already uses `int32`. Not yet load-bearing for exit(42) -- these
functions mask/shift down to the byte or word they emit regardless of
the parameter's real width -- but matching sibling linkers' signatures
avoids the prototype drift that class of fix exists to prevent, and
keeps ql from being the one exception if a future caller ever relies on
the parameter overflowing/wrapping at exactly 32 bits. Changed
linkers/ql/l.h's prototypes and linkers/ql/asm.c's definitions;
compilers/qc's gc.h SZ_IND is already 4 (power is a 32-bit target, not
64-bit like alpha), so the pointer-width bug class that also hit zc
does not apply here.

HEADTYPE 7 (Linux ELF): case 5 existed but wasn't page-aligned
-----------------------------------------------------------------

ql already had two ELF-emitting HEADTYPEs before this session -- case 5
("intended for blue/gene") and case 6 (virtex 4 boot), both calling the
shared elf32() (linkers/lk/elf.c) with mach=POWER. Neither is what the
rest of the project's exit tests expect: every other arch's
tests/s/exit/mkfile passes -H7 uniformly. Added a genuine case 7 to
linkers/ql/obj.c (HEADR/INITTEXT/INITDAT/INITRND, matching il/vl/zl's
own HEADTYPE 7 sizing) and to the three HEADTYPE switches in
linkers/ql/asm.c (data-segment seek, symtab seek, header write --
calling elf32(POWER, ELFDATA2MSB, 0, nil) with debug['S']=1, same as
vl/zl's own case 7).

The reason case 5 could get away without this: its INITRND defaults to
0, and rnd(x, 0) is a no-op, so case 5's unrounded
`seek(cout, HEADR+textsize, 0)` already matched what elf32()'s own
phdr computation used (also unrounded when INITRND==0) -- consistent by
accident, not by design, and fine for whatever custom loader Blue
Gene's HEADTYPE 5 actually targets. A real Linux kernel ELF loader
requires each PT_LOAD segment's vaddr and file offset to agree modulo
the page size, which needs a real INITRND (4096) and the matching
`rnd(HEADR+textsize, INITRND)` seek in case 7 -- copied from zl's own
HEADTYPE 7 (see linkers/zl/asm.c), which hit this exact requirement
during its own Linux ELF bring-up.

exit(42) alone never exercised this rnd() alignment path (no .data
segment); tests/s/mini/hello_linux_power.s (added later this session,
see below) does, and produces correct output under qemu-ppc, so the
page-alignment computation is now verified against a real .data
segment too -- the same way zl's own mini.s test was what actually
caught its setSB/gp bug (see notes_arch_alpha.txt) that exit(42) alone
never could.

r0iszero: PowerPC's RA=0-means-literal-0 quirk, and why -0 is needed
-----------------------------------------------------------------------

Hand-written assembly that loads a literal into R0 (`MOVW $1, R0`, used
here for the syscall number since PowerPC Linux's ABI is r0=syscall#,
r3-r8=args, `sc` traps) fails by default:

    _start: literal operation on R0
    (10)    MOVW    $1,R0

linkers/ql/asmout.c's asmout() (cases 1/3/4, ~lines 131-174) checks a
global `r0iszero` (set in obj.c: `r0iszero = debug['0'] == 0;`, so true
unless -0 is passed) and diag()s whenever an instruction would write a
nonzero literal into R0. This exists because of a real PowerPC ISA
quirk, not an arbitrary Plan 9 convention: in the RA field of
addi/addis-family instructions, RA==0 means "use the literal value 0"
instead of "read register 0" -- so `addi r0, r0, 1` cannot mean "r0 +=
1"; the hardware always reads 0 for the RA operand regardless of r0's
actual contents. The qc compiler relies on R0 conventionally staying
zero (like MIPS's $zero) and this check is qc's own safety net against
accidentally violating that invariant. Hand-written asm that
legitimately needs R0's real hardware value (as the Linux syscall ABI
does) must pass `ql -0` to disable the check. tests/s/exit/mkfile's
power recipe does this: `ql -0 -H7 -o $target -E _start ...`.

span.c's hardcoded `#define r0iszero 1` silently defeated `-0`
--------------------------------------------------------------------

`ql -0` (above) is necessary but was NOT sufficient: with only that
flag, tests/s/mini/hello_linux_power.s ran, printed "Hello, world"
correctly, but called exit(4) instead of exit(0) --
`qemu-ppc -strace` showed the actual syscall trace:

    write(1,0x401000,13)Hello, world
     = 13
    exit(4)

`4` is exactly the write() syscall number, i.e. R0's value from three
instructions earlier -- meaning `MOVW $0, R3` (meant to zero the exit
status) assembled to `or r3,r0,r0` (0x7c030378, a register-to-register
move copying R0's current value into R3) instead of `addi r3,0,0`
(0x38600000, the correct "li r3,0"). This is the exact same
RA==0-means-literal-0 hardware trick described above, but applied in
the *other* direction: ql's own instruction selection was using
`$0`-as-a-constant interchangeably with "read R0" -- valid only on a
machine where R0 is truly hardware-zero (MIPS), which PowerPC is not,
and definitely not valid once hand-written code has repurposed R0 to
hold a real value (here, still 4 from the write() syscall two
instructions earlier).

Root cause: linkers/ql/span.c had its own file-scope
`#define r0iszero 1` (line 2, present unmodified since the original
Plan 9 4th edition import -- `git show cf54e8364:linkers/ql/span.c`
already has it), which shadows the real `EXTERN int r0iszero` from
l.h that obj.c's `-0` flag actually sets. So `-0` correctly disabled
the asmout.c diagnostic (r0iszero read from the real global there) but
had *no effect at all* on span.c's own aclass()/cmp() (both in the same
file, both silently seeing the macro's constant `1` instead of the
real variable), which is what decides that `$0` may be encoded as "mv
from R0" in the first place. Safe for qc-generated code (qc never
reassigns R0, so treating it as a permanent hardware zero is harmless
there) but wrong for any hand-written code that uses R0 as a real
register, which the Linux syscall ABI requires. Fixed by deleting the
`#define` so span.c falls through to the real global. Verified:
hello_linux_power.exe now traces as `exit(0)`, and the full tests/s
suite (all archs, not just power) still passes -- this is shared
classification logic (aclass()/cmp()), so worth re-checking sanity
after any future edit near it.

;;` alongside the other arches. qemu-ppc (from qemu-user, already

qc: align()/maxround() long -> int32, swcmp/hintabsize (matches zc)
---------------------------------------------------------------------

Getting compilers/qc/mkfile to build hit the *exact* same two errors
zc hit during its own bring-up (523eadaad), fixed the same way:

- swt.c's align()/maxround() took `long` where the shared
  compilers/cck/cc.h prototypes declare `int32` -- "conflicting types"
  from gcc, since the two are different widths on this LP64 host.
  Changed both functions' parameter/return/local types to int32,
  matching zc/vc's own swt.c.
- gc.h's `swcmp` prototype was unqualified (`void*, void*`) but the
  actual definition lives in the shared compilers/cck/pswt.c as
  `swcmp(const void *a1, const void *a2)` (a real qsort comparator).
  Const-qualified the prototype. Same file's `hintabsize` was declared
  `EXTERN int` (gc.h's own EXTERN macro, which list.c #define's away to
  claim ownership of every other global) but mul.c already provides a
  real, initialized definition (`int hintabsize = nelem(hintab);`) --
  changed to a plain `extern int` matching zc/vc's own gc.h, avoiding a
  conflicting tentative definition in list.c.

Unlike zc, qc's SZ_IND is already 4 (power is 32-bit, not 64-bit like
alpha), so the pointer-width bug class that also hit zc's txt.c/reg.c
does not apply here -- confirmed by qc successfully compiling and
correctly framing a real two-argument function (see next section).

qc's calling convention, confirmed with `qc -S`
--------------------------------------------------

Rather than guess from q.out.h's REGARG/REGRET=3 comment, compiled a
throwaway two-arg function and read the actual codegen: qc passes the
first argument in R3 (confirmed) and any further arguments on the
stack, readable in the callee as `argname+4(FP)` for a 4-byte-wide
arg (int, pointer) -- same offset convention as arm/mips's own
xwrite_*.s, since power's pointers/ints are 4 bytes here. Used this to
write tests/c/mini/{start,xwrite,xexit}_power.s: start_power.s sets up
R2 (setSB, same role as setR30 in start_mips.s) before `BL main(SB)`;
xwrite_power.s must move the incoming buf pointer out of R3 into R4
before overwriting R3 with the syscall's fd argument (same reason
xwrite_arm.s/xwrite_alpha.s move their own incoming arg register
first) -- same -0/r0-as-real-register story as tests/s/exit and
tests/s/mini above.

lib_toolchain/libmach and iar had no power/'q' support at all
------------------------------------------------------------------

`ql -L` (linking against the iar-built libmini.a) failed with
"first entry not symbol header" -- the exact same message and root
cause zl hit during its own tests/c/mini bring-up (fc257505a):
lib_toolchain/libmach's object-dispatch machinery had no entry at all
for power's '.q' objects (unlike zl's case, this wasn't a wrong
leftover entry pointing at another arch -- power's ObjPower case was
simply never added), so iar could read the archive members but never
built a real symbol table for them.

lib_toolchain/libmach/q.c, qobj.c, and qdb.c already existed (imported
alongside qa/ql/qc in cf54e8364) but were never wired up or built:

- include/arch/mach.h needed six new enum constants: MPOWER (machine
  type), FPOWER (executable type -- no bootable variant, like arm's
  FNONE), APOWER/APOWER64 (disassembler types -- qdb.c's decode()
  already referenced APOWER64 to pick 32- vs. 64-bit instruction
  decoding, matching this Plan 9 4th edition power port's dual-width
  heritage), and ObjPower (object-file type).
- lib_toolchain/libmach/obj.c's dispatch table (the same "explicit
  [Maxobjtype] size" array whose comment already warns about
  under-sized-array OOB reads) needed a `[ObjPower] "power .q", _isq,
  _readq` row.
- lib_toolchain/libmach/setmach.c's `machines[]` table (selects Mach/
  Machdata by name or by executable type) needed a "power" row, plus
  the `extern Mach mpower;` / `extern Machdata powermach;` declarations
  those structs (already defined in q.c/qdb.c) need to be visible.
- lib_toolchain/libmach/mkfile's OFILES was missing q.$O, qdb.$O, and
  qobj.$O entirely -- they were never compiled into libmach.a at all.
- Two leftover absolute/relative paths, present unmodified since the
  original import, needed the same treatment as z.c's/zobj.c's own
  once-leftover paths: q.c's `#include "/power/include/ureg.h"`
  (Plan-9-native absolute path) -> `<arch/power/ureg.h>`; qobj.c's
  `#include "qc/q.out.h"` (assumed-adjacent-source-tree relative path)
  -> `<obj/q.out.h>`.

Verified: rebuilt libmach.a, iar, qa, ql, qc from clean; tests/c/mini's
helloc.exe (real qc-compiled C, not hand assembly) now links and runs
under qemu-ppc, `-strace` shows two correctly-sized write() calls and
a clean exit(0), and its output byte-matches the shared
helloc.expected.txt like every other arch in tests/c/mini's ARCHS.
Re-verified debuggers/acid, machines/5i, machines/vi (all link
libmach.a) still build and pass their own smoke tests after these
mach.h/libmach changes -- shared code, worth re-checking. Also added
compilers/qc to the top-level mkfile's DIRS (assemblers/qa and
linkers/ql were already there; qc was not) and mkfiles/power/mkfile
(CC=qc, AS=qa, LD="ql -0 -H7", AR=iar -- no ARCHEXTRAOFILES yet, see

tests/c/vlong: big-endian Vlong struct order (matches mips's own bug)
------------------------------------------------------------------------

tests/c/vlong/helloprintf.exe's "%d" line printed "002" instead of
"42". Root cause: vlrt.c's `struct Vlong {ulong lo; ulong hi;}` field
order assumes a little-endian target (the file's own comment already
documents this, added during mips's bring-up: "big-endian mips stores
the high word first... this file was copied from the little-endian
arm vlrt.c"). Power is also big-endian and hit the identical bug
class -- _modvu/_divvu's `n.lo`/`n.hi` read the wrong halves of the
64-bit value qc actually passed, so `v % 10` operated on the wrong
32 bits. Fixed by adding `#ifdef power` alongside the existing
`#ifdef mips` branch (nested, not `mips || power`, since this
project's own preprocessors have no #if expression support). Cross-
checked against the real Plan 9 4th edition source at
~/xxx/plan9/SRC/libc/power/vlrt.c (a genuine reference the user
pointed at mid-session): its own `struct Vlong` is unconditionally
`{ulong hi; ulong lo;}` (no ifdef needed there since that file is
power-only), confirming hi-first is the correct big-endian order.
tests/c/vlong now passes for power with no other zc/za/zl-class fixes
needed, matching alpha's own "both pass first try" experience for
this specific test once its one endianness bug was found.

tests/c/float: three more real bugs, each found by peeling the last one
----------------------------------------------------------------------------

Getting tests/c/float working took four real, distinct bugs -- vlong's
above, plus three more this test uniquely exercises (real .data
symbol-table interaction, arbitrary float literals, and int<->float
conversion -- none of which vlong or mini touch). Found in this order,
each fix exposing the next failure underneath it:

1. compilers/qc/txt.c's gins3() had no fallback when !R0ISZERO for an
   operand that's a bare `$0` needing a real register (used by 64-bit
   negate/shift codegen, not just the store-immediate case already
   fixed in ql/asmout.c): it just `diag()`'d out ("REGZERO in gins3
   SUBC") building tests/c/vlong/print.c's `v = -v;` (int64 negate).
   Fixed by materializing 0 into a real scratch register when
   R0ISZERO is off, computed *before* nextpc() starts the real
   instruction (the MOVW loading zero must precede it in program
   order) -- see the fix's own comment in gins3() for why gins4()
   right below it (unconditional `p->reg = REGZERO`) wasn't touched:
   nothing in this session's test content reached it, so it's
   flagged as a matching latent bug rather than guessed at blind.

2. include/objexec/q.out.h's `struct ieee {long l, h;}` was still
   `long` -- the exact same bug class already fixed via the shared
   include/objexec/common.out.h (whose own comment literally says
   "must be int32, not long: the linkers copy the raw bytes of this
   struct into the data segment... 64-bit longs corrupt the emitted
   doubles") and already applied independently to i.out.h, just never
   ported to q.out.h. On this LP64 host, `long` is 8 bytes, so the
   struct was 16 bytes instead of 8 -- every byte-offset computation
   in linkers/ql/asm.c's D_FCONST case (hardcoded assuming a tightly
   packed 2×4-byte struct) silently read/wrote 4 bytes to one side of
   where the real data actually was. Symptom: any DATA-declared 8-byte
   float constant read back as zero (tests/c/float/linux_power.s's
   own `const_half`, and every non-special-cased C float literal qc
   emits via its own literal-pool mechanism, ql/obj.c's AFMOVD case).
   Found by direct field-by-field instrumentation (temporary print()
   calls at each pipeline stage: qa's ieeedtof() encoding -> ql's
   decode into Adr.ieee -> the datblk() byte-copy loop) after ruling
   out the DATA-writing byte-order table (fnuxi8[]) as a red herring --
   its "big-endian" formula matches vl's (mips) own identically-shaped
   formula, so if it were wrong for the {ieee.l; ieee.h;} field order,
   mips would show it too; mips's own float test avoids ever exercising
   this path (va has a MOVD-immediate pseudo-op, so it never needs a
   DATA-based float constant), which is presumably why the shared
   fnuxi8 formula was never actually verified against a real 8-byte
   float write before now. Fixed q.out.h to `int32 l, h;`, matching
   the already-fixed sibling headers.

3. FREGCVI (F27, q.out.h) was never initialized in tests/c/float/
   linux_power.s -- only F28-31 (the ZERO/HALF/ONE/TWO literal
   constants) were. F27 plays a different role: it's the magic bias
   (2^52 + 2^31 = 4503601774854144.0) compilers/qc/txt.c's gmove()
   "fxtofl" path subtracts to convert a 32-bit int/uint to double
   without a native int->float instruction (build a double with bit
   pattern 0x43300000_(f^0x80000000) in memory, load it, subtract
   FREGCVI to cancel the bias). Left uninitialized, every such
   conversion subtracted ~0 instead, off by the full magnitude --
   e.g. tests/c/float/print.c's digit-extraction loop (`s = v; ...;
   v -= s;`, an implicit int->double widening of the truncated digit)
   turned 2.2 into roughly -4e15 after one iteration, printing
   "2.000000" instead of "2.200000" (only the FIRST digit, computed
   before this path ever ran, came out right). Every other constant
   in the test (0.0, 2.0, 3.0, NaN) happened to avoid this path
   entirely (handled by the FREGZERO/HALF/ONE/TWO special-casing or
   isNaN's own bit manipulation), which is why the bug hid behind bug
   #2 until 2.2 -- the one literal with no register short-cut -- was
   the last thing left failing. Fixed by adding the same
   MOVW-then-FMOVD init sequence as const_half, with its own
   DATA-declared 4503601774854144.0 constant.

Verified: tests/c/vlong and tests/c/float's full `mk test` (all
ARCHS, power now included in both) pass with byte-identical output to
their respective helloprintf.expected.txt; re-ran tests/c/mini,
tests/s/exit, tests/s/mini's own `mk test` afterward to confirm the
q.out.h/gins3 changes (both touch code every power program goes
through) didn't regress the earlier, simpler bring-up work.
