lput/wput/cput: long -> int32 parity fix
-----------------------------------------

Same class of fix already applied to 5l/8l (37e0fe696) and to zl during
its own bring-up: linkers/ql/asm.c's cput/wput/wputl/lput/lputl took
`long` (64 bits on this LP64 host) where every sibling linker (6l, vl,
zl) already uses `int32`. Not yet load-bearing for exit(42) -- these
functions mask/shift down to the byte or word they emit regardless of
the parameter's real width -- but matching sibling linkers' signatures
avoids the prototype drift that class of fix exists to prevent, and
keeps ql from being the one exception if a future caller ever relies on
the parameter overflowing/wrapping at exactly 32 bits. Changed
linkers/ql/l.h's prototypes and linkers/ql/asm.c's definitions;
compilers/qc's gc.h SZ_IND is already 4 (power is a 32-bit target, not
64-bit like alpha), so the pointer-width bug class that also hit zc
does not apply here.

HEADTYPE 7 (Linux ELF): case 5 existed but wasn't page-aligned
-----------------------------------------------------------------

ql already had two ELF-emitting HEADTYPEs before this session -- case 5
("intended for blue/gene") and case 6 (virtex 4 boot), both calling the
shared elf32() (linkers/lk/elf.c) with mach=POWER. Neither is what the
rest of the project's exit tests expect: every other arch's
tests/s/exit/mkfile passes -H7 uniformly. Added a genuine case 7 to
linkers/ql/obj.c (HEADR/INITTEXT/INITDAT/INITRND, matching il/vl/zl's
own HEADTYPE 7 sizing) and to the three HEADTYPE switches in
linkers/ql/asm.c (data-segment seek, symtab seek, header write --
calling elf32(POWER, ELFDATA2MSB, 0, nil) with debug['S']=1, same as
vl/zl's own case 7).

The reason case 5 could get away without this: its INITRND defaults to
0, and rnd(x, 0) is a no-op, so case 5's unrounded
`seek(cout, HEADR+textsize, 0)` already matched what elf32()'s own
phdr computation used (also unrounded when INITRND==0) -- consistent by
accident, not by design, and fine for whatever custom loader Blue
Gene's HEADTYPE 5 actually targets. A real Linux kernel ELF loader
requires each PT_LOAD segment's vaddr and file offset to agree modulo
the page size, which needs a real INITRND (4096) and the matching
`rnd(HEADR+textsize, INITRND)` seek in case 7 -- copied from zl's own
HEADTYPE 7 (see linkers/zl/asm.c), which hit this exact requirement
during its own Linux ELF bring-up.

exit(42) alone never exercised this rnd() alignment path (no .data
segment); tests/s/mini/hello_linux_power.s (added later this session,
see below) does, and produces correct output under qemu-ppc, so the
page-alignment computation is now verified against a real .data
segment too -- the same way zl's own mini.s test was what actually
caught its setSB/gp bug (see notes_arch_alpha.txt) that exit(42) alone
never could.

r0iszero: PowerPC's RA=0-means-literal-0 quirk, and why -0 is needed
-----------------------------------------------------------------------

Hand-written assembly that loads a literal into R0 (`MOVW $1, R0`, used
here for the syscall number since PowerPC Linux's ABI is r0=syscall#,
r3-r8=args, `sc` traps) fails by default:

    _start: literal operation on R0
    (10)    MOVW    $1,R0

linkers/ql/asmout.c's asmout() (cases 1/3/4, ~lines 131-174) checks a
global `r0iszero` (set in obj.c: `r0iszero = debug['0'] == 0;`, so true
unless -0 is passed) and diag()s whenever an instruction would write a
nonzero literal into R0. This exists because of a real PowerPC ISA
quirk, not an arbitrary Plan 9 convention: in the RA field of
addi/addis-family instructions, RA==0 means "use the literal value 0"
instead of "read register 0" -- so `addi r0, r0, 1` cannot mean "r0 +=
1"; the hardware always reads 0 for the RA operand regardless of r0's
actual contents. The qc compiler relies on R0 conventionally staying
zero (like MIPS's $zero) and this check is qc's own safety net against
accidentally violating that invariant. Hand-written asm that
legitimately needs R0's real hardware value (as the Linux syscall ABI
does) must pass `ql -0` to disable the check. tests/s/exit/mkfile's
power recipe does this: `ql -0 -H7 -o $target -E _start ...`.

span.c's hardcoded `#define r0iszero 1` silently defeated `-0`
--------------------------------------------------------------------

`ql -0` (above) is necessary but was NOT sufficient: with only that
flag, tests/s/mini/hello_linux_power.s ran, printed "Hello, world"
correctly, but called exit(4) instead of exit(0) --
`qemu-ppc -strace` showed the actual syscall trace:

    write(1,0x401000,13)Hello, world
     = 13
    exit(4)

`4` is exactly the write() syscall number, i.e. R0's value from three
instructions earlier -- meaning `MOVW $0, R3` (meant to zero the exit
status) assembled to `or r3,r0,r0` (0x7c030378, a register-to-register
move copying R0's current value into R3) instead of `addi r3,0,0`
(0x38600000, the correct "li r3,0"). This is the exact same
RA==0-means-literal-0 hardware trick described above, but applied in
the *other* direction: ql's own instruction selection was using
`$0`-as-a-constant interchangeably with "read R0" -- valid only on a
machine where R0 is truly hardware-zero (MIPS), which PowerPC is not,
and definitely not valid once hand-written code has repurposed R0 to
hold a real value (here, still 4 from the write() syscall two
instructions earlier).

Root cause: linkers/ql/span.c had its own file-scope
`#define r0iszero 1` (line 2, present unmodified since the original
Plan 9 4th edition import -- `git show cf54e8364:linkers/ql/span.c`
already has it), which shadows the real `EXTERN int r0iszero` from
l.h that obj.c's `-0` flag actually sets. So `-0` correctly disabled
the asmout.c diagnostic (r0iszero read from the real global there) but
had *no effect at all* on span.c's own aclass()/cmp() (both in the same
file, both silently seeing the macro's constant `1` instead of the
real variable), which is what decides that `$0` may be encoded as "mv
from R0" in the first place. Safe for qc-generated code (qc never
reassigns R0, so treating it as a permanent hardware zero is harmless
there) but wrong for any hand-written code that uses R0 as a real
register, which the Linux syscall ABI requires. Fixed by deleting the
`#define` so span.c falls through to the real global. Verified:
hello_linux_power.exe now traces as `exit(0)`, and the full tests/s
suite (all archs, not just power) still passes -- this is shared
classification logic (aclass()/cmp()), so worth re-checking sanity
after any future edit near it.

qc: align()/maxround() long -> int32, swcmp/hintabsize (matches zc)
---------------------------------------------------------------------

Getting compilers/qc/mkfile to build hit the *exact* same two errors
zc hit during its own bring-up (523eadaad), fixed the same way:

- swt.c's align()/maxround() took `long` where the shared
  compilers/cck/cc.h prototypes declare `int32` -- "conflicting types"
  from gcc, since the two are different widths on this LP64 host.
  Changed both functions' parameter/return/local types to int32,
  matching zc/vc's own swt.c.
- gc.h's `swcmp` prototype was unqualified (`void*, void*`) but the
  actual definition lives in the shared compilers/cck/pswt.c as
  `swcmp(const void *a1, const void *a2)` (a real qsort comparator).
  Const-qualified the prototype. Same file's `hintabsize` was declared
  `EXTERN int` (gc.h's own EXTERN macro, which list.c #define's away to
  claim ownership of every other global) but mul.c already provides a
  real, initialized definition (`int hintabsize = nelem(hintab);`) --
  changed to a plain `extern int` matching zc/vc's own gc.h, avoiding a
  conflicting tentative definition in list.c.

Unlike zc, qc's SZ_IND is already 4 (power is 32-bit, not 64-bit like
alpha), so the pointer-width bug class that also hit zc's txt.c/reg.c
does not apply here -- confirmed by qc successfully compiling and
correctly framing a real two-argument function (see next section).

qc's calling convention, confirmed with `qc -S`
--------------------------------------------------

Rather than guess from q.out.h's REGARG/REGRET=3 comment, compiled a
throwaway two-arg function and read the actual codegen: qc passes the
first argument in R3 (confirmed) and any further arguments on the
stack, readable in the callee as `argname+4(FP)` for a 4-byte-wide
arg (int, pointer) -- same offset convention as arm/mips's own
xwrite_*.s, since power's pointers/ints are 4 bytes here. Used this to
write tests/c/mini/{start,xwrite,xexit}_power.s: start_power.s sets up
R2 (setSB, same role as setR30 in start_mips.s) before `BL main(SB)`;
xwrite_power.s must move the incoming buf pointer out of R3 into R4
before overwriting R3 with the syscall's fd argument (same reason
xwrite_arm.s/xwrite_alpha.s move their own incoming arg register
first) -- same -0/r0-as-real-register story as tests/s/exit and
tests/s/mini above.

tests/c/vlong: big-endian Vlong struct order (matches mips's own bug)
------------------------------------------------------------------------

tests/c/vlong/helloprintf.exe's "%d" line printed "002" instead of
"42". Root cause: vlrt.c's `struct Vlong {ulong lo; ulong hi;}` field
order assumes a little-endian target (the file's own comment already
documents this, added during mips's bring-up: "big-endian mips stores
the high word first... this file was copied from the little-endian
arm vlrt.c"). Power is also big-endian and hit the identical bug
class -- _modvu/_divvu's `n.lo`/`n.hi` read the wrong halves of the
64-bit value qc actually passed, so `v % 10` operated on the wrong
32 bits. Fixed by adding `#ifdef power` alongside the existing
`#ifdef mips` branch (nested, not `mips || power`, since this
project's own preprocessors have no #if expression support). Cross-
checked against the real Plan 9 4th edition source at
~/xxx/plan9/SRC/libc/power/vlrt.c (a genuine reference the user
pointed at mid-session): its own `struct Vlong` is unconditionally
`{ulong hi; ulong lo;}` (no ifdef needed there since that file is
power-only), confirming hi-first is the correct big-endian order.
tests/c/vlong now passes for power with no other zc/za/zl-class fixes
needed, matching alpha's own "both pass first try" experience for
this specific test once its one endianness bug was found.

tests/c/float: three more real bugs, each found by peeling the last one
----------------------------------------------------------------------------

Getting tests/c/float working took four real, distinct bugs -- vlong's
above, plus three more this test uniquely exercises (real .data
symbol-table interaction, arbitrary float literals, and int<->float
conversion -- none of which vlong or mini touch). Found in this order,
each fix exposing the next failure underneath it:

1. compilers/qc/txt.c's gins3() had no fallback when !R0ISZERO for an
   operand that's a bare `$0` needing a real register (used by 64-bit
   negate/shift codegen, not just the store-immediate case already
   fixed in ql/asmout.c): it just `diag()`'d out ("REGZERO in gins3
   SUBC") building tests/c/vlong/print.c's `v = -v;` (int64 negate).
   Fixed by materializing 0 into a real scratch register when
   R0ISZERO is off, computed *before* nextpc() starts the real
   instruction (the MOVW loading zero must precede it in program
   order) -- see the fix's own comment in gins3() for why gins4()
   right below it (unconditional `p->reg = REGZERO`) wasn't touched:
   nothing in this session's test content reached it, so it's
   flagged as a matching latent bug rather than guessed at blind.

2. include/objexec/q.out.h's `struct ieee {long l, h;}` was still
   `long` -- the exact same bug class already fixed via the shared
   include/objexec/common.out.h (whose own comment literally says
   "must be int32, not long: the linkers copy the raw bytes of this
   struct into the data segment... 64-bit longs corrupt the emitted
   doubles") and already applied independently to i.out.h, just never
   ported to q.out.h. On this LP64 host, `long` is 8 bytes, so the
   struct was 16 bytes instead of 8 -- every byte-offset computation
   in linkers/ql/asm.c's D_FCONST case (hardcoded assuming a tightly
   packed 2×4-byte struct) silently read/wrote 4 bytes to one side of
   where the real data actually was. Symptom: any DATA-declared 8-byte
   float constant read back as zero (tests/c/float/linux_power.s's
   own `const_half`, and every non-special-cased C float literal qc
   emits via its own literal-pool mechanism, ql/obj.c's AFMOVD case).
   Found by direct field-by-field instrumentation (temporary print()
   calls at each pipeline stage: qa's ieeedtof() encoding -> ql's
   decode into Adr.ieee -> the datblk() byte-copy loop) after ruling
   out the DATA-writing byte-order table (fnuxi8[]) as a red herring --
   its "big-endian" formula matches vl's (mips) own identically-shaped
   formula, so if it were wrong for the {ieee.l; ieee.h;} field order,
   mips would show it too; mips's own float test avoids ever exercising
   this path (va has a MOVD-immediate pseudo-op, so it never needs a
   DATA-based float constant), which is presumably why the shared
   fnuxi8 formula was never actually verified against a real 8-byte
   float write before now. Fixed q.out.h to `int32 l, h;`, matching
   the already-fixed sibling headers.

3. FREGCVI (F27, q.out.h) was never initialized in tests/c/float/
   linux_power.s -- only F28-31 (the ZERO/HALF/ONE/TWO literal
   constants) were. F27 plays a different role: it's the magic bias
   (2^52 + 2^31 = 4503601774854144.0) compilers/qc/txt.c's gmove()
   "fxtofl" path subtracts to convert a 32-bit int/uint to double
   without a native int->float instruction (build a double with bit
   pattern 0x43300000_(f^0x80000000) in memory, load it, subtract
   FREGCVI to cancel the bias). Left uninitialized, every such
   conversion subtracted ~0 instead, off by the full magnitude --
   e.g. tests/c/float/print.c's digit-extraction loop (`s = v; ...;
   v -= s;`, an implicit int->double widening of the truncated digit)
   turned 2.2 into roughly -4e15 after one iteration, printing
   "2.000000" instead of "2.200000" (only the FIRST digit, computed
   before this path ever ran, came out right). Every other constant
   in the test (0.0, 2.0, 3.0, NaN) happened to avoid this path
   entirely (handled by the FREGZERO/HALF/ONE/TWO special-casing or
   isNaN's own bit manipulation), which is why the bug hid behind bug
   #2 until 2.2 -- the one literal with no register short-cut -- was
   the last thing left failing. Fixed by adding the same
   MOVW-then-FMOVD init sequence as const_half, with its own
   DATA-declared 4503601774854144.0 constant.

Verified: tests/c/vlong and tests/c/float's full `mk test` (all
ARCHS, power now included in both) pass with byte-identical output to
their respective helloprintf.expected.txt; re-ran tests/c/mini,
tests/s/exit, tests/s/mini's own `mk test` afterward to confirm the
q.out.h/gins3 changes (both touch code every power program goes
through) didn't regress the earlier, simpler bring-up work.

tests/c/hello_libc/hello.exe: a real lib_core/libc/arch/power port
------------------------------------------------------------------------

Scoped deliberately to hello.c (print()+exit() only -- see
tests/c/hello_libc/mkfile's own header comment for what the rest of
that test directory needs), not the whole hello_libc suite, on
explicit instruction. Ported the arch/OS glue lib_core/libc needs:

- include/arch/power/u.h: was missing s8/u8/s16/u16/s32/u32/s64/u64
  (required by include/core/types.h -- every other arch's u.h already
  has these; this file only had the older u8int/u32int/... aliases)
  and `intptr` (missing entirely -- only `uintptr` existed), had a
  duplicate `#define nil` (already in include/core/macros.h; a second
  definition is a hard compiler error here, not a warning) and a
  duplicate/conflicting `jmp_buf[2]`/JMPBUFSP/PC/DPC (include/core/
  exn.h already provides the real Jmpbuf{sp,pc} every arch shares).
  All four gaps are the exact same class alpha's own u.h bring-up hit
  (see that commit) -- this header was imported alongside qa/ql/qc but
  never brought up to the same baseline the newer arches (arm64/
  riscv64/alpha) already share.
- lib_core/libc/arch/power/rt0.s: process entry, argc/argv bridge.
  Confirmed via a real 'ql -a' + qemu-ppc -d in_asm trace (not assumed
  by analogy with alpha/riscv64's own different-offset findings) that
  ql's noop.c auto-prologue shifts the kernel's raw argc/argv from
  0(R1)/4(R1) to 8(R1)/12(R1), the same class of shift those two
  arches' own rt0.s already document.
- lib_core/libc/arch/power/setjmp.s: the usual two-field
  {sp,pc}-only jmp_buf (see include/core/exn.h's own comment on why
  this compiler needs no real callee-saved-register preservation).
  Genuine leaf functions, R1=sp, LR read/written via the special-
  register MOVW forms already established in tests/s/exit's own _main
  prologues.
- lib_core/libc/arch/power/sigrestore.s: a trivial tail-branch
  (`BR signotify(SB)`), like arm's own -- REGARG=R3 already matches
  the kernel's own sig-in-r3 signal-handler convention, so no real ABI
  bridging is needed (see os/linux/notify.c's own header comment for
  the general design and why amd64/386/mips/riscv/riscv64 needed real
  bridging while arm/arm64 didn't). NOT independently verified with a
  real kill(2)+notify() probe the way arm's own comment describes --
  reasoned by analogy only.
- lib_core/libc/arch/power/vlop.s: the 64-bit multiply helper (_mulv)
  qc's frontend calls for `vlong * vlong` -- classic 32-bit PowerPC has
  no 64x64 multiply, only MULLW/MULHWU (32x32->64, low/high halves),
  so this builds the truncated 64-bit product the standard way (see
  arm's own vlop.s for the general algorithm). No div.s needed (real
  divw/divwu hardware instructions exist, unlike arm/riscv's software
  divide helpers) and no getcallerpc.s (power isn't special-cased in
  port/getcallerpc.c, so it falls into that file's portable `return 0;`
  fallback like arm64/mips/riscv/riscv64).
- lib_core/libc/syscall/os/linux/{numbers,syscall_linux,svc}_power.*:
  the raw syscall layer. Numbers are the classic/legacy table (same as
  386/arm, confirmed against this host's installed powerpc-linux-gnu
  cross headers) -- NOT mips's o32 +4000-offset scheme. svc_power.s's
  error convention needed real derivation, not copying: PowerPC's `sc`
  signals failure via CR0's SO (Summary Overflow) bit, not a GPR flag
  like mips's/alpha's a3/a4 -- confirmed by decoding linkers/ql/
  asmout.c's own ABVS/ABVC encoding (BI=3 selects CR0 bit 3 = SO,
  matching real PowerPC ABI) rather than assumed from the mnemonic
  name alone. NEG (a real PowerPC instruction) negates the syscall's
  positive errno into the return register on error -- no hardwired-
  zero-register trick needed here, unlike alpha's/mips's SUBQ/SUBU
  (PowerPC has no such register). Deliberately narrower than every
  other arch's own decl: no _syspipe yet (PowerPC's raw sys_pipe
  return convention -- register pair like mips, or pointer-write like
  arm/386? -- not confirmed against real kernel source), left as a
  documented gap (port/pipe.c declares _syspipe's extern itself, so
  omitting it here only defers pipe.c, not this file's own build).
- lib_core/libc/os/linux/stat_power.c: Kstat struct confirmed against
  real kernel source on this host (arch/powerpc/include/uapi/asm/
  stat.h's own "struct stat64", explicitly commented "matches struct
  stat64 in glibc2.1") -- a simpler, single-`ino`-field shape than
  arm's own EABI struct_stat64 (no leading pad/dual-ino). The two
  padding gaps (before st_size, before st_blocks) are inferred from
  natural 8-byte alignment, same as stat_alpha.c's own __pad0, written
  as explicit uchar[] so the byte offsets don't depend on qc's own
  struct-layout rules matching the real ABI.
- lib_core/libc/os/linux/isatty.c: TCGETS is not the generic 0x5401 on
  PowerPC (arch/powerpc/include/uapi/asm/ioctl.h overrides
  _IOC_SIZEBITS=13/_IOC_DIRBITS=3, a BSD/SunOS-style encoding like
  mips's own divergence) -- confirmed empirically by compiling and
  running a real probe with the installed powerpc-linux-gnu-gcc cross
  compiler under qemu-ppc (`printf("%x",TCGETS)`), not computed by
  hand from the encoding macros (judged too error-prone to trust
  blind, unlike the numbers above which came straight from a header).
- lib_core/libc/os/linux/notify.c and port/vlrt.c: needed only an
  `#ifdef power` branch each (numbers_power.h's own include, and the
  big-endian Vlong field order respectively) -- the identical fix
  already applied to tests/c/vlong/vlrt.c's own copy this session, now
  ported to the shared port/vlrt.c too. os/linux/open.c's O_CREAT/
  O_EXCL split needed no new branch: confirmed against real kernel
  source that PowerPC uses the generic (non-mips) fcntl.h values
  already in that file's `#else` branch.

tests/c/hello_libc bring-up for power (full suite, follow-up session)
----------------------------------------------------------------------

power was added to tests/c/hello_libc/mkfile's $ARCHS and to
test_one's stat/dirread/fork block. 12 of 15 binaries pass
(hello/io/dir/fd/mem/proc/args/atexit/notify/alarm/stat/dirread/fork
-- that's 13, env/ctime/utfmisc are the 3 that don't). Three real bugs
found and fixed; two more found and NOT fixed (documented below for a
future session, since both turned into much deeper rabbit holes than
their symptoms suggested).

Fixed: _syspipe wired up (syscall_linux_power.decl) -- confirmed
against this host's own arch/powerpc/kernel/syscalls/syscall.tbl that
PowerPC's pipe(2) is the generic (non-mips) fs/pipe.c sys_pipe(int
__user*), the same arm/386-shaped single-pointer-arg convention
syscall_linux_arm.decl already uses, not mips's register-pair
sysm_pipe. Needed because fork.c calls pipe() directly (not just the
separate, plan9-only pipe.exe test).

Fixed: arch/power/sigrestore.s's sigentry rewritten from a plain
tail-branch ("BR signotify(SB)") to "BL signotify(SB)" + manual
MOVW LR,R4/MOVW R4,LR save-restore. The tail-branch failed to
assemble ("illegal combination BR NONE NONE NONE LEXT") because
linkers/ql/optab.c's ABR has no C_LEXT (long-external-symbol) optab
row, even though ABL shares the SAME oprange table
(oprange[ABL]=oprange[ABR] in span.c) and cross-file BL calls (to
exit(SB), main(SB)) already work fine elsewhere in this tree. Root
cause not chased (looks like an archive-symbol-resolution-order quirk
specific to BR, since BL already proves cross-file linking works in
general) -- worked around instead, since LR must survive unclobbered
across signotify() for the noted(NCONT) case anyway (no SA_RESTORER
here), so BL+restore achieves the same net effect from primitives
already proven to work. See that file's own header comment for the
full reasoning.

Fixed (the important one): arch/power/rt0.s's argc/argv bridge had an
off-by-one-word bug in the OUTGOING argv slot for main(argc, argv),
identical in shape to the bug arch/arm/rt0.s's own header comment
already documents and fixes for arm. Every 0-argument main() in this
suite (hello.c, env.c, etc.) worked fine regardless, which is exactly
why this went unnoticed during the hello.c-only bring-up: nothing
exercised main(argc, char*argv[]) until args.c and fork.c (which
re-execs itself with argv) were added. Symptom: args.exe printed
"argc=4" correctly (argc arrives in R3, no bridging needed) but
segfaulted the instant it read argv[1] -- even a bare `argv[1]` access
with no further dereference crashed, confirmed with a minimal repro.

Root cause, traced via `ql -a` disassembly + hand-decoding the actual
PowerPC branch/load-immediate encodings (see notes_debug_techniques.txt's
new section on this): ql's own D_PARAM (FP-relative argument) offset
formula in linkers/ql/span.c is
    instoffset = autosize + a->offset + 4L
The "+4L" is deliberate and correct in general -- it's the same
"phantom pushed-return-address slot" convention every register-call
arch here needs (arm, mips, alpha, riscv64), compensating for the fact
that PowerPC's BL doesn't push a return address to the stack the way
x86's CALL does, so the FP-relative addressing scheme (designed
assuming one architecture-wide convention across all backends) needs
the CALLER to manufacture that missing word itself. arch/power/rt0.s's
original version only accounted for ONE such adjustment (subtracting 8
before storing argv at 4(R1)), but the real bridge chain has TWO
prologues between the raw kernel stack and main()'s own argv+4(FP)
read: _main's own auto-prologue (-8) and main()'s own auto-prologue
(-16) BOTH have to be summed against the +4 formula, working out to an
outgoing slot at 8(R1), not the naively-expected 4(R1) -- exactly the
same "+4 beyond the naive expectation" arm's own header comment
already found and confirmed via qemu-arm's gdbstub. Confirmed via a
qemu-ppc + gdb (gdbstub) session stepping through the actual value
written and the actual offset main()'s own prologue-adjusted
`argv+4(FP)` read resolved to (R1+24 needed to reach where argv was
stored, not R1+20) -- not re-derived from the formula alone, per this
project's own "verify via a live debugger" rule.

Fix: arch/power/rt0.s's outgoing-argv sequence changed from
"ADD $-8,R1,R1" / "MOVW R4,4(R1)" to "ADD $-12,R1,R1" /
"MOVW R4,8(R1)". This alone additionally fixed args.exe, fork.exe (its
own child re-exec passes argv through the exact same path),
stat.exe and dirread.exe (both of which happened to be silently
relying on some now-corrected stack layout too, though neither reads
argv directly -- worth re-confirming if either regresses later,
since their earlier "passing" status before this fix was never
independently explained).

FIXED (follow-up session) -- env.exe/ctime.exe/utfmisc.exe, all one root cause
----------------------------------------------------------------------

All three of the failures below turned out to be the SAME bug,
root-caused and fixed in a later session after the writeup below was
already on disk (kept verbatim, since the investigation trail -- and
the two theories it disproves -- is worth keeping): linkers/ql/asm.c's
HEADTYPE-7 case unconditionally set `debug['S'] = 1` (i.e. "always
emit an ELF section-header table"), which makes the shared
linkers/lk/elf.c's elf32()/elf32sectab() seek to
`HEADR+textsize+datsize+symsize` to write that table -- an UNROUNDED
offset. But the data (and, when present, symbol-table) content right
before it was actually written starting at the PAGE-ROUNDED
`rnd(HEADR+textsize,INITRND)+datsize+symsize` (ELF requires
vaddr-mod-page == file-offset-mod-page, so ql/asm.c's own asmb() -- the
one write path that's already correct -- has to round there). Whenever
that rounding gap exceeds symsize (ALWAYS true once `-s` makes symsize
0, which mkfiles/power/mkfile's LD flags always do for every power
binary), the mis-seeked section-header-table + .shstrtab write lands
INSIDE the tail of the already-written .data content instead of past
it, silently overwriting real program data with section-header/string
bytes.

This is the exact same bug class commit d5cfb36f0 already root-caused
and fixed for 8l/8lk's own (separate, non-shared) ELF writer --
found only because the user pointed at that commit as "a fix we did
in another toolchain during goken integration" worth checking for an
analogous fix here, not re-derived independently. The fix landed in
linkers/ql/asm.c itself (only set debug['S'] when NOT stripping), not
in the shared linkers/lk/elf.c: since power's own mkfile always links
with -s, and a stripped ELF has no legitimate use for section headers
anyway (the kernel loader reads only PROGRAM headers to run it),
skipping elf32sectab() entirely whenever debug['s'] is set removes the
whole corruption path with no loss. The shared elf.c was deliberately
left untouched even though it has the identical unrounded-offset
code (confirmed by hand-computing the exact byte offset the bug would
land at for a real utfmisc.exe build, before finding the real fix,
matching a `.strtab` fragment printed where a string literal should
have been) -- vl/il/zl, the other HEADTYPE-7 arches sharing it, build
their own tests/c/vlong and tests/c/float WITHOUT stripping, so their
symsize is normally big enough to absorb the same rounding gap and
never trips it. Power is the one arch whose mkfile always strips,
making symsize unconditionally 0, which is why this was ever
observable here at all.

All 15 tests/c/hello_libc binaries pass with this one-line fix (plus
the earlier rt0.s argv/argc fix): env.exe and ctime.exe's
getenv("PATH") failures (below) and utfmisc.exe's segfault (further
below) were ALL this same corruption hitting different, unlucky
offsets within each binary's own .data -- not three separate bugs.
The malloc(1)-fixes-env.c clue below now also makes sense in
retrospect: pulling in port/minimal_malloc.c's own heap[] array grew
symsize's effective replacement (well, grew datsize/bsssize, which
isn't quite the same lever, but shifted the corrupted-byte-range far
enough past env.c's own small, early string pool to stop mattering)
by accident, without addressing the real cause -- exactly the kind of
fragile, binary-size-dependent "sometimes it's fine" behavior a real
unrounded-offset bug produces.

Original (pre-fix) investigation, kept for the record
----------------------------------------------------------------------

env.c and ctime.c both fail with a bare `exit(1)`/no output, the
observable shape being "getenv did not find PATH" even though PATH is
demonstrably present and correctly reachable by the exact same
environ()/getenv() code in other, smaller test programs (a minimal
getenv("PATH")+print() repro succeeds every time). This is NOT the
"successive print() calls in one function get corrupted" bug the
previous bring-up session's notes speculated (a `long nstring`/
`outstring()` host-arithmetic-width bug in compilers/qc/{gc.h,swt.c},
analogous to the already-fixed `struct ieee` bug) -- that theory was
directly disproved this session: `qc -S` and a byte-for-byte hexdump
of the linked .data segment's `.string<>` pool (computed by hand by
decoding the actual `lis`/`ori`/gp-relative-load instruction encodings
qc/ql emitted, not assumed) showed EVERY string constant's bytes and
computed address were exactly correct, in both a working 2-string
repro and a 3+-getenv-call repro that failed the same way env.c does.
compilers/qc/gc.h's `EXTERN long nstring;` (vs vc's already-correct
`int32`) is still real and still worth fixing for hygiene/cross-arch
consistency (compilers/zc/gc.h has the identical latent bug), but it
is NOT what breaks env.c on power.

What was actually confirmed, via a qemu-ppc gdbstub + gdb session
(the ONLY reliable way found this session to inspect live PowerPC
register/CR state -- a hand-parsed `qemu-ppc -d in_asm,cpu -singlestep`
text trace was tried first and produced internally-inconsistent
register readings, later traced to a line-counting bug in the ad hoc
Python parser, not a real CPU/emulation anomaly; see
notes_debug_techniques.txt):
  - rt0.s's argc/argv/_mainargv/_mainargc capture is correct (already
    fixed above) and getenv()'s own `environ()` computation
    (_mainargv + _mainargc + 1) is correct -- confirmed by
    single-stepping to the exact loop-head instruction and printing
    the real envp base address and its first few dereferenced
    pointers.
  - The getenv() loop genuinely walks EVERY entry in what it believes
    is the environment array, from a correctly-computed envp base,
    all the way to a `*e == nil` it (also genuinely) finds -- without
    that comparison ever matching "PATH=". This was confirmed by
    breakpointing the loop head and printing every $r11 (entry slot
    address) and its dereferenced value for the entire walk.
  - The env-string CONTENT values qemu-ppc-user hands this process sit
    at addresses in the low 0x408xxx range -- i.e. inside the SAME
    small virtual-address neighborhood as this binary's own ELF-loaded
    .data segment (which starts at 0x408000 for this H7/-0400000-based
    linker layout). This is suspicious on its face (real env/argv
    string content should live on the process's stack, not inside the
    executable's own static data range) but turned out NOT to be
    simply "our .data overlaps qemu's stack" in the way first
    hypothesized:
      - Adding an unrelated `malloc(1)` call to env.c (pulling in
        port/minimal_malloc.c's own ~64KB `heap[]` BSS array) reliably
        and reproducibly fixes it -- confirmed on both a hand-reduced
        repro AND on an instrumented copy of the real env.c.
      - But adding an equivalent (or much larger -- tried 256KB and
        4MB) block of BSS padding via a hand-written GLOBL pseudo-op
        in arch/power/rt0.s (to sidestep a SEPARATE bug found along
        the way, below) did NOT fix it, despite growing the binary's
        total declared .data+.bss (ELF p_memsz) by far more than
        minimal_malloc.c's own heap ever does relative to env.c's tiny
        baseline. So the fix is not simply "more BSS headroom" --
        something more specific to minimal_malloc.o being linked in
        (its exact position in archive link order? some other symbol
        it drags in transitively? not yet identified) is what matters,
        and this was not chased further given the time already spent.
  - Editing env.c/ctime.c themselves to call malloc() is NOT an
    acceptable fix even though it "works" -- both files are shared,
    unmodified verbatim across every arch in $ARCHS, and a
    power-only malloc() call would be exactly the kind of arch-special-
    cased test content this project's tests are supposed to avoid.
  - A separate, smaller bug was found (not the main one) while testing
    the "add padding" theory: declaring a large `static char pad[N]`
    directly inside env.c (i.e. in the SAME compilation unit as its
    own `.string<>` literal pool) does not just fail to help -- it
    corrupts CODEGEN entirely, causing a totally unrelated string (a
    fragment of the ELF's own .strtab section content) to be printed
    in place of an actual string literal. This did NOT happen when
    the equivalent padding lived in its own separate, code-only .s
    file (arch/power/rt0.s) linked alongside an otherwise-unmodified
    env.c. So there is a genuine, separate ql/qc power bug in how a
    single compilation unit's data-segment symbol addresses get
    computed once there is more than one top-level data/bss symbol in
    it -- distinct from (but likely related in spirit to) the
    already-documented "-s is load-bearing" asmsym()/asmlc() bug
    mkfiles/power/mkfile's own comment describes. Neither root-caused.

Next steps for whoever picks this back up: (1) try reordering/
isolating exactly which symbol from minimal_malloc.o (heap[] itself,
heapnext<>, or the mallocz() call site's own codegen) is load-bearing,
by linking in ONLY that piece; (2) get a byte-level dump of what
qemu-ppc-user's own linux-user/elfload.c ACTUALLY computes for its
initial stack top address for this exact binary shape, rather than
inferring it from qemu-ppc-supplied virtual addresses observed from
inside the guest -- that would settle definitively whether this is a
qemu placement quirk or a real bug in how ql (or rt0.s) computes
_mainargv/envp; (3) the multi-data-symbol corruption bug above is
probably the more tractable, more clearly-in-scope one to root-cause
first, since it doesn't depend on qemu's own internal placement logic
at all.

(Also fixed by the same root cause above.) utfmisc.exe: segfaults, but ONLY when linked with -s
----------------------------------------------------------------------

utfmisc.exe segfaults (SIGSEGV) under qemu-ppc when linked the normal
way (mkfiles/power/mkfile's `ql -0 -s -H7`). Bisected the source
(strrchr/strncpy/utfrrune/two dirmodefmt-via-%M calls) down to needing
the FULL original file, with its real if/exit(1)-with-message-string
branches intact -- every smaller reduction that dropped some of that
structure (even ones keeping all four functions exercised, just
without the surrounding if-checks) passed. This is very likely the
same class of "compiled-code-size/layout-dependent" fragility as the
env.exe bug above, though not confirmed to be the identical root
cause.

The one clean, reproducible, surprising fact found: rebuilding the
EXACT SAME utfmisc.q WITHOUT `-s` (`ql -0 -H7`, no strip) makes it
pass consistently (confirmed 3/3 runs each way). This is the OPPOSITE
of what mkfiles/power/mkfile's own header comment documents for
tests/c/float's helloprintf.exe, where `-s` is what FIXES an
ELF-symbol-table-corrupts-.data bug. Both are almost certainly the
same underlying ql HEADTYPE-7 asmsym()/asmlc() bug for power (still
not root-caused there either), manifesting on opposite sides of
some exact-symbol-count or exact-offset threshold depending on the
binary -- not two different bugs. Since flipping the mkfile's global
`-s` would trade this failure for reintroducing float's, the correct
fix is rooting out the real asmsym()/asmlc() bug, not toggling the
flag. Left as-is (still `-s`, still failing) rather than adding a
per-target flag override, since a real fix is worth more than papering
over one side of a two-sided bug.
