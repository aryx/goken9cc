*** 7c (compiler)

**** binarytrees.c: ItemCheck() makes exactly one extra call with tree==NULL, iff main() also uses pow()
claude:
Found while trying to unblock benchs/compcert/binarytrees.c. Second
pass at this bug (see git history for the first pass's now-superseded
theory, which blamed print()'s own formatting path directly -- still
true that a print() call is *involved*, but the actual trigger and
symptom are both much more specific than that pass had pinned down).
Real, 100%-deterministic SIGSEGV on darwin/arm64 -- not a probabilistic
memory-corruption symptom the way the "small leftover pointer value"
framing from the first pass suggested.

Precise, reproducible finding (minimal repro: BottomUpTree/NewTreeNode/
ItemCheck/DeleteTree copied verbatim from binarytrees.c into a
standalone main(), see scratchpad -- not yet promoted to a committed
tests/c/regressions file, that's the natural next step): instrument
ItemCheck() with a global call counter and a guard
(`if((unsigned long)tree < 0x1000) { report and exit; }`) before
dereferencing. For a perfect binary tree of depth D (built by
BottomUpTree(0,D), exactly 2^(D+1)-1 nodes), a call to
`ItemCheck(root)` should make exactly 2^(D+1)-1 total recursive calls,
one per node, and never see tree==NULL (every real node's `left` is
either a valid pointer or NULL, and NULL is only ever *checked*, never
recursed into -- see ItemCheck's own `if(tree->left==NULL) return
tree->item;` base case). Observed instead: **exactly** 2^(D+1)-1
*successful* calls happen (a fully correct traversal of the entire
real tree), immediately followed by **exactly one** extra, spurious
call with tree==NULL -- verified identically at D=8,10,12,14,16,17,18
(counts 511/2047/8191/32767/131071/262143/524287, i.e. 2^(D+1)-1 in
every case, no exceptions). This is not "a pointer got corrupted
somewhere in a quarter-million-node tree" -- it's "the recursion
that should stop after the last leaf takes one more step it
shouldn't."

The trigger, isolated by minimization, is unrelated to the print()
call's own arguments or format verbs (the first pass's theory) and
instead is: **main() calls pow() *anywhere*, even in code never
reached before the crash**. Concretely: take the real binarytrees.c
structure verbatim (all four functions, main()'s full body including
the depth-loop that calls pow() to compute `iterations`), and the bug
reproduces on the very first `ItemCheck(stretchTree)` call, which
happens before that loop ever executes. Delete just the
`iterations = pow(2, maxDepth-depth+minDepth);` line (replace with a
constant) and the *identical* program, *identical* tree, *identical*
ItemCheck()/DeleteTree() traversal, runs to completion with zero extra
calls, exit 0. Re-add the pow() call (even wrapped in a
provably-never-taken `if` branch elsewhere in main(), confirmed via
7l -a to actually still emit real FMOVD/BL-pow/FCVTZSDW instructions,
not dead-code-eliminated) and it's back to instrument-and-crash. So
the causal factor is "does main()'s compiled body contain
floating-point codegen", not "is pow() actually called at runtime" or
"is print() given a particular argument."

Ruled out via direct verification, not assumption:
- NOT address-magnitude-dependent: a separate minimal repro
  (BottomUpTree/ItemCheck/DeleteTree with *no* pow() anywhere, heap[]
  offset controlled directly by pre-`malloc()`ing and discarding N MB
  before building the tree) never reproduces the bug for any tested
  offset 0-128MB, at tree depths up to 17 -- despite this covering,
  and exceeding, the actual address range (~16-84MB) where the pow()
  variant's stretchTree lands across several runs. The pow()-present
  variant's own stretchTree address is *not* stable run-to-run (real
  ASLR is evidently applied to this BSS heap[] array despite the
  binary's own code segment loading at a fixed, non-PIE address) --
  but the bug fires at the exact same call-count boundary on every
  run regardless of the specific address, which is itself evidence
  this is a logic bug, not a data/memory-corruption one.
- NOT a bug in ItemCheck()'s, DeleteTree()'s, NewTreeNode()'s, or
  BottomUpTree()'s own compiled code: `7l -a` disassembly of all four
  functions is byte-identical (down to the opcode, modulo relocation-
  driven immediate/branch-target differences that shift with overall
  binary size) between the pow()-free (survives) and pow()-present
  (crashes) builds. Same for main()'s own instructions up through and
  including the `BL ItemCheck` call site itself. Whatever differs is
  either something at that exact call site not visible in a plain
  diff (e.g. a register/stack-slot decision that happens to encode
  identically here but behaves differently, unlikely but not yet
  disproven) or, more likely given the FP-codegen correlation, a
  callee-saved-register save/restore bug specific to when main()'s own
  prologue/epilogue needs to preserve floating-point (D8-D15,
  AAPCS64 callee-saved) registers alongside integer ones -- not yet
  confirmed by reading main()'s actual prologue/epilogue for a missing
  or miscomputed FP register spill, which is the natural next step.
- NOT reproducible via a global-counter artifact: the same "exactly
  one extra call, argument exactly 0" result held when spot-checked
  independently (see the instrumentation itself, which reports the
  *argument value* the guard rejected, not just an internal count).
- lldb address-based breakpoints (`breakpoint set -a <addr>`) remain
  unreliable on this project's own -H6 Mach-O output -- confirmed
  "set" with a real resolved address but did not actually stop
  execution there, even for addresses causally before the crash;
  print()-based instrumentation (add a guard + report + exit, per
  above) was what actually cracked this, not lldb. Worth checking
  whether this is a property of this project's minimal Mach-O load
  commands or an lldb-specific issue before relying on lldb here
  again.
- The host's endpoint security software quarantining freshly-built
  ad-hoc-signed binaries (see notes_debug_techniques.txt) resurfaced
  mid-session, this time correlated with *specific directories*
  accumulating many rebuilds rather than a global block -- switching
  to a directory with an established history of successful builds
  this session (rather than a brand new one) reliably unblocked it.
  Worth trying before concluding the host is fully wedged.

Checked, and ruled out, one specific next step already: main()'s own
prologue (`MOV R30,-112(R31)!`, nothing else) and epilogue (`MOV
$0,R0; MOV (R31)112!,R30; RET`, nothing else) are identical in shape
to the pow()-free build and never save/restore any register beyond
LR/R30 -- so this is NOT main() itself failing to preserve a
callee-saved FP register (D8-D15) around its own body; the FP values
main() computes for `iterations` use F0-F4, which are caller-saved
under AAPCS64 and need no such preservation by main() itself. If a
callee-saved-register-accounting bug is still the right family (this
file's other REGMIN/REGMAX and register-mask entries are the closest
precedent for "register bookkeeping goes wrong under specific
register-class-mixing conditions"), it would have to be inside pow()
itself (a large function, easily worth checking whether *it*
correctly restores every callee-saved register, D8-D15 and R19-R28
alike, given how much internal scratch state its polynomial
computation needs) -- but pow() is never actually *called* before the
crash point (it lives in a loop body that hasn't executed yet), so any
bug in pow() itself can only matter here via some link-time/layout
side effect of pow()'s mere presence (code size, symbol/constant-pool
placement) rather than its execution. That side-effect is the
remaining open question: two functions' worth of machine code
(main()'s shared prefix, and all of NewTreeNode/ItemCheck/
BottomUpTree/DeleteTree) were confirmed byte-identical between the
crashing and non-crashing builds, which makes it hard to see how
runtime *behavior* can differ at all -- unless it's a data dependency
on an address that shifts between builds (heap[]'s own BSS address is
confirmed to shift substantially, though direct testing of that one
address via artificial padding did not reproduce the bug on its own;
some other address -- a constant pool, a string literal, `itcheck_n`
itself -- shifts too and hasn't been individually tested the same
way). Whoever picks this up next should either: (a) systematically
test each shifting address in isolation the way heap[] was tested, or
(b) get a working interactive debugger on this project's own -H6
Mach-O output (lldb's unreliability here was the main blocker to going
faster) and single-step through the actual `BL ItemCheck` call site
and its return path with real hardware watchpoints on the relevant
stack slots.

Real trigger, fully isolated via a 3-file minimal repro (not yet
promoted to tests/s/regressions/, see todo below): compile two
separate .c files with 7c, link both together with 7l. File A (main)
has a dead, provably-never-taken call (`if(neverrun){ helper(); }`,
`neverrun` a global int initialized to 0) to a function `helper()`
defined in File B. If `helper()`'s own body makes an external call to
*any* function living in a third place (libc.a -- confirmed with both
open() and strdup(), unrelated functions in unrelated libc.a members),
something elsewhere in the final binary gets corrupted -- concretely,
main()'s own later `print("%d\n", i)` call (integer, not float --
floats are NOT required to trigger this, that was the misleading part
of the first pass) segfaults. If `helper()` is a trivial function with
no external call (`return x+1;`), no crash. If the exact same
dead-code-calls-helper() structure is kept but `helper()` lives in the
*same* object file as main() instead of a separate one (whether as a
separate function or inlined), no crash, even though it still makes
the same external call to open()/strdup()/whatever. So the trigger is
specifically: >=2 separate 7c-compiled object files linked together,
where a non-entry object file itself contains a call to an external
symbol -- not which symbols are involved, not floats, not registers,
not fopen/fgets/fclose specifically (those were just the first,
misleading way this was noticed, because lib_core/libc/APE/stdio.c
happens to be exactly this shape: a separately-compiled object file
whose fopen()/fgets()/fclose() each call another external function,
open()/read()/close(), that lives in yet another libc.a member).
Confirmed independent of regopt()/peephole/-O level entirely: crashes
identically at -O0 through -O3 (byte-identical machine code for the
crash-adjacent block was verified across all four) -- ruling out the
optimizer as the culprit and pointing squarely at either cgen.c's base
codegen or (more likely, given the trigger is about *linking multiple
object files*, not anything in one function's own compiled shape)
something in 7l's handling of BL-relocations/symbol layout when
resolving an external call that originates from a non-entry object
file. NOT yet root-caused at the instruction level: manually decoding
the raw machine code around the actual crash site (main()'s own
print() call) shows byte-correct, self-consistent instructions with no
visible corruption -- so whatever's wrong is either in exactly which
address something resolves to (a wrong but validly-encoded relocation
target) or in something not visible in that local disassembly at all.
Confirmed 7c/7l-specific (arm64), not a general goken-toolchain issue:
the byte-identical 3-file repro does NOT crash when built with 6c/6l

*** ic (compiler)

**** boolgen()/comrel() NaN-comparison bug -- deeper than expected
claude:
compilers/ic/cgen.c:763, compilers/vc/cgen.c:636,730 -- boolgen()
applies comrel[] (the integer logical-complement table, OLT<->OGE,
OLE<->OGT, OEQ<->ONE, etc) to the source-level relational operator
unconditionally, before checking whether the comparison is floating-
point. That complement is sound for integers (total order) but not for
IEEE-754 comparisons under NaN: e.g. "!(x < y)" is not equivalent to
"x >= y" when x or y is NaN (both are false for NaN operands). This is
shared kencc lineage code -- present in every backend's boolgen() (5c/
6c/7c/8c/vc/ic and the 5ck/7ck/8ck variants), but 7c/5c already carry a
compensating fix in gmove()/boolgen() ("ensure NaN comparison is
always false", substituting ABMI/ABPL/ABHI/ABLS for the naive signed
branches when typefd[et]). Confirmed real on both riscv and mips with
a live qemu run: "x = 0.0/0.0; y = 1.0;" wrongly evaluates x>y and
x>=y as true on riscv, x<y and x<=y as true on mips.

Tried the obvious fix (mirroring kencc-riscv's restructuring: move the
comrel[] application out from before the typefd check to only the
integer-specific branches) -- it does NOT work. Confirmed empirically:
it just changes *which* operators come out wrong (riscv: x<y, x<=y,
x==y wrong instead of x>y, x>=y -- a lateral move, not a fix).
Root cause is deeper: compilers/ic/txt.c's gopcode() (case OGE:1217,
OGT:1225, `cmpfloat:` 1246) has its own synthesis for OGE/OGT, because
RISC-V's FPU only has native FEQ/FLT/FLE, no FGT/FGE -- it computes
FLE/FLT then branches on the *inverted* sense (`ab`), and that
synthesis is independently NaN-unsound (assumes "!(x<y) implies x>=y",
the same unsound total-order assumption, just relocated). boolgen()'s
comrel[] turns out to be partly *compensating* for gopcode()'s
synthesis rather than purely redundant with it, which is why removing
it breaks cases it was accidentally getting right. A real fix needs to
untangle both pieces together (likely: fix gopcode()'s OGE/OGT
synthesis to be NaN-safe first, matching 7c/5c's ABMI/ABPL/ABHI/ABLS
approach as closely as this ISA allows, *then* revisit whether
boolgen()'s comrel[] still needs adjusting on top) -- not the
"easily testable" one-line reorder it first looked like

**** gap: 5i/vi cannot serve plan9's synthetic device files
claude:
plan9's getpid() and nsec() are FILE READS on that GOOS, not syscalls --
"#c/pid" and "/dev/bintime" (see lib_core/libc/os/plan9/{getpid,time}.c,
ported from principia). That is correct for real Plan9, and is exactly
why plan_syscalls.txt predicted Plan9 needs far fewer syscalls than the
Unix column suggests.

But machines/5i and machines/vi forward open() straight to the host
(machines/5i/syscall_posix.c's sysopen calls the host open()), and a
Linux host has neither file. So under the emulators getpid() returns 0
and nsec() returns 0, and tests/c/hello_libc/proc.c's first check fails.
proc.c is therefore built for plan9 but not RUN in that mkfile's
test_plan9 target -- getwd() and sleep() there do work, since FD2PATH
and SLEEP are already implemented in both emulators.

The fix is a small synthetic-device layer in each emulator: intercept
open() of a known device path, hand back a synthetic fd, and serve its
contents from the host on read (getpid() -> the host's own pid,
/dev/bintime -> the host clock as 8 big-endian nanosecond bytes). Maybe
60 lines per emulator, and it would make the plan9 target genuinely
testable rather than merely compiled. Worth doing before the stat or
process-control tiers, both of which will want more of /dev.

landed lib_core/libc's dirfstat()/dirfwstat() for plan9/arm+mips
(os/plan9/stat.c, convM2D.c, convD2M.c) -- correct on the guest side,

**** gap: no dup() on windows (needs an fd -> HANDLE table first)
claude:
access/dup finished Tier 2 of docs/claude_notes/plan_syscalls.txt on
every GOOS except this one, where dup() is deliberately absent rather
than approximated. The blocker is the simplification
lib_core/libc/os/windows/open.c's own header comment already documents:
fdt is `int` but a real Win32 HANDLE is an 8-byte pointer, so open()
truncates it and the other calls widen it back. That works only because
CreateFileA happens to return small handle values.

dup() is the first call that cannot live with it. Plan9's
dup(oldfd, newfd) must place a descriptor at a number the CALLER
chooses -- that is the whole point of the newfd argument, and what
every shell redirection needs. A HANDLE-as-fd model has no way to
express "make this copy be number 9": DuplicateHandle returns whatever
handle the kernel picks, and nothing maps that back to 9.

So the fix is the fd table that open.c already names as the real
solution: a small array mapping int fds to HANDLEs, with open/create
allocating the lowest free slot, close freeing it, and read/write/seek
indirecting through it. dup then becomes trivial (copy the slot, or
DuplicateHandle into a chosen slot). Until then
tests/c/hello_libc/fd.c is not built for windows -- see that file's
comment and this mkfile's test_windows target, which lists its
binaries explicitly rather than using `all`.

access() IS implemented for windows (GetFileAttributesA), but only
approximately: it can answer existence and the read-only bit, not AREAD
or AEXEC, since Win32 permissions are ACLs rather than mode bits.

**** gap: bare `%u`/`%llud`-style unsigned decimal prints a stray trailing 'd'
claude:
Found while verifying utilities/files/wc.c: `%7llud` (Plan9's own
"length modifiers then verb" idiom, used throughout ls.c/wc.c/mv.c
etc, all ported from real Plan9 sources) printed the number correctly
but then a literal trailing 'd', e.g. "42d" instead of "42" -- also
present (previously unnoticed) in ls -l's dev/length columns. Root
cause isolated to lib_core/libc/fmt/fmt.c's own verb table
(`knownfmt[]`): it has a genuine upstream `#ifdef PLAN9PORT ... #else
'u', __ifmt ... #endif` switch for the character 'u' -- PLAN9PORT mode
treats 'u' as a FLAG (like 'l'/'h') meaning "the verb that follows is
unsigned", matching `%lld`/`%llud`; non-PLAN9PORT (ANSI C) mode treats
bare 'u' as its OWN terminal verb ("print an unsigned int in decimal"
right there). `PLAN9PORT` is never `#define`d anywhere in this tree
(grepped, not assumed), so it's silently in ANSI mode -- meaning
`%llud` parses as: __ifmt('u') consumes the arg, prints it in decimal,
and returns; the trailing 'd' is then just ordinary un-consumed
literal text the outer dofmt() loop copies through verbatim. Explains
the exact "number, then stray d" symptom precisely.

NOT fixed here: naively defining PLAN9PORT (or just re-registering 'u'
to `__flagfmt` in the `knownfmt[]` table) is NOT safe globally --
lib_toolchain/libmach/5db.c's own ARM disassembler mnemonic templates
(`"MOV%u%C%p"` etc, `bprint()` -> `vseprint()` -> this same fmt
engine) rely on bare `%u` terminating as its own verb the way it
already does; flipping global 'u' semantics would silently corrupt
disassembly output there while fixing ls.c/wc.c/mv.c. A real fix needs
either auditing every `%u`-using call site tree-wide first, or a more
surgical dofmt.c change (peek at the character right after 'u' and
only treat it as a flag when a length-modifier-shaped verb -- d/x/o/b/
i -- immediately follows) -- out of scope for what was meant to be a
"simple, useful for utilities/files" pass.

**** gap: most Plan9-shaped syscall wrappers return the raw negative errno on failure, not -1
claude:
Found via utilities/files/rm.c: `remove(f) != ERROR_NEG1` (ERROR_NEG1
is literally `(-1)`) took the SUCCESS branch after `rm
nonexistent-file`, silently exiting 0 with no error printed. Root
cause: port/remove.c returned whatever _sysrmdir() gave back on
failure -- the raw negative Linux errno (-2 for ENOENT, -13 for
EACCES, ...), not -1. Real Plan9 syscalls always fail with EXACTLY -1
(the failure detail is conveyed separately, via errstr()) -- every
Plan9-shaped API in include/os/*.h (open(), remove(), create(), ...)
is documented/expected to honor that same contract, and code ported
verbatim from real Plan9 sources (rm.c, mv.c) checks failure with an
exact `== -1`/`ERROR_NEG1` comparison specifically because of it, not
just `< 0`.

Fixed ONLY for remove() (port/remove.c) -- the one call this session's
utilities/files work actually exercised with an exact -1 check
(rm.c/mv.c both use it). The SAME gap almost certainly exists in every
other os/$GOOS/*.c Plan9-shaped wrapper across every arch --
os/linux/open.c's own open()/create() are a confirmed instance (traced
while diagnosing remove(), not fixed: `return (fdt)_sysopen(...)`
returns the raw negative errno directly, no -1 normalization at all).
A full fix means auditing/normalizing every os/$GOOS/*.c file's
Plan9-shaped entry points (not the raw syscall/ wrappers themselves,
which should keep returning the real errno for anything that DOES
want it, e.g. future errno-bridging work) -- out of scope for what
was meant to be a small, targeted utilities/files fix.

Directly connects to port/errstr.c's own already-documented gap ("no
caller in this tree currently reports failures via werrstr()"): even
after the -1 fix above, `rm nonexistent.txt` prints "rm:
nonexistent.txt: " (empty reason -- errstr() has nothing to report)
AND still exits 0 -- rm.c's own `exits(errbuf)` treats an empty
errbuf as success, and errbuf only ever gets non-empty content from a
real errstr() call, which is empty because nothing calls werrstr() at
the syscall-failure site. Two gaps compounding into one visible
symptom (wrong exit status), not two different bugs: fixing "syscalls
call werrstr() on failure" (a real, separate, larger undertaking --
would touch the same os/$GOOS/*.c files as the -1-normalization gap
above, natural to do together) would fix both errbuf's content AND
the exit status in one pass.
